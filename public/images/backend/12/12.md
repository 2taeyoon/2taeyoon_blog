## 🦮 이벤트 삭제를 안전하게 만드는 휴지통 패턴

관리자가 목록 화면에서 '선택삭제'를 누르면 데이터가 사라지는 기능이 있다고 가정해 보겠습니다.

문제는 <strong>같은 버튼을 눌렀는데, 일부 데이터는 휴지통으로 가고 일부는 바로 영구 삭제</strong>되는 경우입니다.  
UI 는 동일하지만 실제 동작이 달라서 운영자 입장에서 위험하고 직관적이지 않습니다.

<img src="/images/backend/12/main_image.webp"/>

이 글에서는 <strong>일반적인 휴지통 패턴</strong>을 예시 코드와 함께 정리합니다.

- 현재 구조를 개념적으로 이해하기
- 삭제(휴지통 이동) 흐름 따라가 보기
- 도메인 로직에서 회원/비회원(또는 타입별) 동작을 통일하기
- 최종 동작과 운영상의 장점 정리

---

## 🦮 1. 목록 화면에서 "선택삭제"가 하는 일

### 🦄 버튼과 체크박스

어떤 기술 스택이든, 보통은 다음과 같은 패턴을 가집니다.

```html
<button type="button" id="btnMoveToTrash" class="btn btn-danger">
    선택삭제
</button>
```

목록 각 행에는 체크박스가 있고, 사용자는 여러 건을 선택한 뒤 이 버튼을 눌러 삭제(또는 휴지통 이동)를 실행합니다.

<img src="/images/backend/12/images1.webp"/>

### 🦄 프론트엔드에서의 추상적인 흐름

실제 구현 언어나 라이브러리(jQuery, React 등)는 다를 수 있지만, 흐름은 거의 비슷합니다.

```javascript
// 예시: 프레임워크에 상관없는 의사 코드
function handleMoveToTrashClick() {
  const ids = getCheckedRowIds(); // 체크된 행의 ID 목록

  if (ids.length === 0) {
    alert("선택한 항목이 없습니다.");
    return;
  }

  const confirmed = window.confirm("선택한 항목을 휴지통으로 이동하시겠습니까?");
  if (!confirmed) {
    return;
  }

  // 실제 엔드포인트 경로나 통신 방법은 서비스마다 다를 수 있습니다.
  httpClient.post("/api/items/move-to-trash", { ids }).then(() => {
    refreshList(); // 목록 다시 불러오기
  });
}

bindClickEvent("#btnMoveToTrash", handleMoveToTrashClick);
```

이 코드의 포인트는 <strong>"프론트엔드는 어떤 항목을 삭제할지 결정만 하고, 실제 삭제 방식은 서버에 위임"</strong>한다는 점입니다.

---

## 🦮 2. 서버에서 요청을 받는 방식 (컨트롤러 레벨)

백엔드의 기술 스택(PHP, Node.js, Java, Go 등)에 따라 코드는 달라지지만, 책임은 비슷합니다.

```php
// 예시: 기술 스택에 독립적인 흐름 설명
POST /api/items/move-to-trash

handler(request):
    ids = parseIds(request.body.ids)

    TrashService.moveToTrash(ids, actorType = currentUser.role)

    return 204 No Content
```

여기서 컨트롤러(또는 핸들러)는 다음 두 가지만 담당합니다.

1. 요청에서 ID 목록과 사용자 정보를 꺼낸다.
2. 도메인 서비스를 호출하고, 성공/실패에 따라 적절한 응답 코드를 돌려준다.

실제 휴지통 로직은 <strong>TrashService</strong> 같은 도메인/서비스 레이어에서 처리합니다.

## 🦮 3. 도메인 로직: 회원/비회원 삭제 동작 통일하기

### 🦄 좋지 않은 패턴 (개념 예시)

현실 서비스에서는 종종 다음과 같은 패턴이 섞여 있습니다.

```php
// 개념을 설명하기 위한 예시 코드입니다.
function moveToTrash(ids):
    for each id in ids:
        item = findItemById(id)

        if item.ownerType == "guest":
            // 게스트 데이터는 바로 영구 삭제
            deleteFromDatabase("items", id)
            deleteFromDatabase("guests", item.ownerId)
        else:
            // 회원 데이터는 휴지통 플래그만 변경
            update("items", id, {
                isTrashed: true,
                trashedBy: "admin",
                updatedAt: now()
            })
```

- <strong>회원</strong>: 플래그만 바꾸고 휴지통에서 복원 가능  
- <strong>비회원(게스트)</strong>: 관련 데이터까지 바로 `DELETE`  

동일한 UI 인데도, 데이터 타입에 따라 결과가 완전히 달라집니다.
운영자가 "실수로 게스트 건을 삭제했는데…"라고 느끼는 순간,
이미 물리적으로 삭제되어 복구할 수 없는 상태가 됩니다.

### 🦄 우리가 만들고 싶은 목표

1. <strong>같은 UI 에서는 같은 경험</strong>을 주기  
   → 선택삭제 버튼을 눌렀을 때, 회원/비회원(또는 타입별) 모두 먼저 휴지통으로 이동

2. <strong>삭제를 2단계로 나누기</strong>  
   - 1단계: 목록에서 휴지통으로 이동 (`isTrashed = true`)  
   - 2단계: 휴지통 화면에서 "완전 삭제"를 눌렀을 때 실제 `DELETE`

### 🦄 리팩터링된 휴지통 도메인 로직 (개념 예시)

<img src="/images/backend/12/images3.webp"/>

```php
function moveToTrash(ids, actorType):
    for each id in ids:
        item = findItemById(id)

        params = {
            isTrashed: true,
            trashedBy: actorType,   // "admin", "user" 등
            updatedAt: now()
        }

        // 소유자 타입(회원/비회원 등)에 상관없이 일단 휴지통으로만 보낸다.
        logTrashAction(itemId = id, meta = params)
        update("items", id, params)

    return true
```

핵심은 다음과 같습니다.

- <strong>어떤 타입의 데이터도 "선택삭제" 버튼에서는 영구 삭제하지 않는다.</strong>
- 회원/비회원, 타입과 상관없이 `isTrashed = true` 로만 변경해 휴지통으로 이동.
- 실제 레코드 삭제는 별도의 "완전 삭제" 기능에서 명시적으로 수행.

## 🦮 4. 휴지통 화면과 완전 삭제 플로우

위와 같이 도메인 로직을 정리했다면, 휴지통 화면은 매우 단순해집니다.

<img src="/images/backend/12/images4.webp"/>

### 🦄 휴지통 목록 조회 조건 (개념 SQL)

```sql
SELECT *
FROM items
WHERE is_trashed = TRUE
  AND deleted_at IS NULL;
```

기술 스택에 따라 ORM 이나 쿼리 빌더로 바꿔 쓰면 됩니다.
포인트는 <strong>"휴지통에 있는 데이터는 실제 삭제된 것이 아니라, 특정 플래그로 구분한다"</strong>입니다.

### 🦄 휴지통 화면의 버튼들

```html
<!-- 휴지통 화면 예시 -->
<button type="button" id="btnRestore">복원</button>
<button type="button" id="btnDeleteHard">완전삭제</button>
```

- <strong>복원</strong>: `isTrashed` 를 `false` 로 되돌리고, `restoredAt` 같은 로그를 남길 수 있습니다.  
- <strong>완전삭제</strong>: 이때 실제로 `DELETE` 하거나, `deletedAt` 을 채워 소프트 삭제를 완료합니다.

이렇게 하면:

- 목록 화면의 "선택삭제" 버튼은 <strong>항상 휴지통 이동</strong>만 담당하고,
- 실제 물리 삭제는 휴지통 화면의 "완전삭제" 버튼에서만 일어납니다.

## 🦮 5. 전체 플로우와 운영상의 장점

<img src="/images/backend/12/images5.webp"/>

### 🦄 최종 동작 흐름 (개념)

1. 등록 리스트에서 여러 건 선택 → <strong>선택삭제 버튼 클릭</strong>  
2. 프론트엔드가 선택된 ID 들을 모아서 `/api/items/move-to-trash` 같은 엔드포인트로 전송  
3. 도메인 서비스 `moveToTrash()` 가
   - 데이터 타입(회원/비회원, 게스트, 기타)을 확인하더라도,
   - 결과적으로는 모두 `isTrashed = true` 로만 변경  
4. 기본 리스트에는 `isTrashed = false` 인 항목만 보이므로, 삭제된 항목은 화면에서 사라짐  
5. 휴지통 탭에서 `isTrashed = true` 인 항목을 모두 확인 가능  
6. 휴지통에서:
   - <strong>복원</strong> → `isTrashed = false`  
   - <strong>완전삭제</strong> → 실제 삭제(하드 삭제 또는 소프트 삭제 마무리)

### 🦄 이 패턴의 장점

- <strong>일관된 UX</strong>  
  같은 "선택삭제" 버튼을 눌렀을 때, 어떤 타입의 데이터든 모두 휴지통으로만 이동합니다.

- <strong>실수에 대한 안전망</strong>  
  비회원/게스트 데이터도 휴지통에서 복구할 수 있어,
  "실수로 잘못된 항목을 지워버린" 상황에 대응할 수 있습니다.

- <strong>책임 있는 삭제 프로세스</strong>  
  목록 → 휴지통 → 완전삭제의 2단계 구조 덕분에,
  실제 물리 삭제는 항상 의도적으로, 한 번 더 확인한 뒤에만 이루어집니다.

- <strong>확장성</strong>  
  동일한 패턴을 주문, 게시글, 문의글, 파일 등 다양한 도메인에 그대로 적용할 수 있습니다.

## 🦮 마무리

휴지통/삭제 로직을 설계할 때는 다음 세 가지만 명확히 그려 두면 됩니다.

1. <strong>어디에서 어떤 버튼을 누르면</strong> (UI 레벨)  
2. <strong>어떤 프론트엔드 함수가 어떤 엔드포인트를 호출하고</strong> (프론트엔드 레벨)  
3. <strong>도메인 서비스가 어떤 기준으로 휴지통 이동과 완전 삭제를 나누는지</strong> (백엔드 레벨)

이 세 가지를 분리해서 생각하면,
회원/비회원, 게스트/정회원, 기타 타입에 상관없이 <strong>예측 가능한 삭제 정책</strong>을 만들 수 있습니다.

이 글에서 정리한 내용은 어떤 기술 스택에도 적용할 수 있는 일반적인 패턴입니다.  
이 패턴을 기준으로, 자신의 프로젝트 삭제/복원 정책을 점검해 보는 계기로 삼으면 좋습니다.
