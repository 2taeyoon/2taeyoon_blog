## 🎯 도허티 임계값(Doherty Threshold)

> <strong>도허티 임계값</strong>은 <strong>“사용자와 시스템이 서로를 기다리지 않을 만큼, 400ms 이내로 반응할 때 생산성이 급격히 올라간다”</strong>는 원리입니다.

저는 인터랙션을 설계할 때,  
기능이 정확히 동작하는지만 보던 예전과 달리 요즘은 <strong>“얼마나 빨리 반응하는가”</strong>를 따로 떼어 놓고 보려고 합니다.  
사용자는 1~2초 정도만 기다려도 이미 <strong>“느리다”</strong>라고 느끼고,  
400ms 안에 피드백이 돌아오면 “생각보다 부드럽네?” 하는 인상을 받는 경우가 많기 때문입니다.

그래서 저는 화면을 점검할 때,  
<strong>“클릭 이후 400ms 안에 눈에 보이는 변화가 있는가?”</strong>를 하나의 기준으로 삼으려고 합니다.

## 🦮 핵심 요약 (Takeaways)

### 🦄 1. 400ms 안에 피드백이 오면 집중이 끊기지 않습니다

1. 도허티 임계값에 따르면, <strong>400ms 이내에 시스템 피드백이 오면</strong>  
   사용자는 기다린다는 느낌 없이 자연스럽게 다음 행동으로 넘어갈 수 있습니다.  
2. 이 한계를 넘기기 시작하면, 사용자의 주의는 다른 곳으로 새기 쉬워지고  
   “이게 된 건가?”라는 불안이 쌓이기 시작합니다.

<img src="/images/blog/design/28/images1.webp"/>

### 🦄 2. 실제 속도뿐 아니라 “체감 속도”도 설계할 수 있습니다

- 서버 처리 시간이 길더라도, <strong>즉시 피드백과 진행 표시</strong>를 잘 설계하면  
  사용자는 상대적으로 덜 지루하게 느낍니다.  
- 저는 그래서 느린 작업일수록 “바로 응답할 수 있는 범위”와  
  “처리가 끝나는 범위”를 나누어 생각하려고 합니다.

<img src="/images/blog/design/28/images2.webp"/>

## 🦮 도허티 임계값, 제가 이해한 방식

### 🦄 1. 왜 2초가 아니라 400ms인가?

예전에는 “2초 이내로 응답하면 괜찮다”는 기준이 많이 쓰였습니다.  
하지만 도허티와 타다니의 연구에서는,  
<strong>400ms 이내로 응답하는 시스템이 훨씬 더 중독적으로 느껴진다</strong>는 결과를 보여 주었습니다.

저는 이걸 이렇게 받아들이고 있습니다.

- 2초는 “참을 수 있는 기다림”의 기준에 가깝고  
- 400ms는 “거의 기다렸다는 감각이 없는” 기준에 가깝습니다.

UX 관점에서 보면, 우리는 가능하면 후자를 목표로 삼아야 합니다.

### 🦄 2. “입력-응답-다음 행동” 루프의 끊김 여부

도허티 임계값은 단순히 한 화면의 로딩 속도 문제가 아니라,  
사용자가 반복하는 <strong>입력 → 응답 → 다음 입력</strong> 루프 전체에 영향을 줍니다.

- 이 루프 안에서 응답이 빠르게 돌아오면, 사용자는 흐름을 유지한 채 “몰입 상태”로 들어갑니다.  
- 반대로 매번 응답이 느리면, 행동을 할 때마다 작은 마찰이 쌓여 결국 이탈로 이어집니다.

저는 그래서 폼 제출, 검색, 필터 변경 같이 자주 반복되는 동작일수록  
“이 루프가 400ms 안에서 끊기지 않는가?”를 특히 의식하려고 합니다.

## 🦮 UX에서 제가 쓰는 실전 패턴들

### 🦄 1. “즉시 피드백”과 “실제 완료”를 분리하기

긴 작업에서 저는 보통 이렇게 나누어 생각합니다.

- <strong>즉시 피드백</strong>: 400ms 안에 “요청을 잘 받았다”는 신호를 주기  
  - 버튼 상태 변경, 스켈레톤 UI, 로딩 인디케이터 등  
- <strong>실제 완료</strong>: 서버 처리나 대용량 연산이 끝나는 시점

예를 들어 업로드 기능이라면,

- 클릭 즉시 버튼 상태를 “업로드 중”으로 바꾸고  
- 바로 진행률 바나 스켈레톤을 보여 주어  
  “시스템이 일하고 있다”는 사실을 분명히 보여 주는 식입니다.

### 🦄 2. 로딩을 “의미 있는 기다림”으로 바꾸기

진행 표시만으로 부족할 때는,  
로딩 중에 <strong>맥락 있는 정보를 함께 보여줘서 기다림의 가치를 높이는 방법</strong>을 고민해 봅니다.

- 예: 분석 리포트를 생성하는 동안,  
  “지금 어떤 단계를 계산 중인지”를 단계별로 보여주기  
- 예: 추천 콘텐츠를 불러오는 동안,  
  사용자가 선택한 필터 요약이나 다음에 할 수 있는 행동 힌트를 보여주기

이렇게 하면 실제 시간은 같아도, 사용자는 <strong>“그냥 멍하니 기다렸다”는 느낌</strong>을 덜 받습니다.

<img src="/images/blog/design/28/images4.webp"/>

### 🦄 3. 불필요한 동기화와 블로킹 작업 줄이기

도허티 임계값을 지키려면,  
프론트엔드와 백엔드에서 <strong>괜히 사용자를 기다리게 만드는 지점</strong>을 줄이는 것이 중요합니다.

- 동기 호출 대신 <strong>비동기 처리</strong>로 전환할 수 없는지  
- 화면 전체를 막기보다는, <strong>일부 영역만 잠시 비활성화</strong>해도 되는지  
- 꼭 서버 응답을 기다려야 하는 데이터인지, <strong>캐시나 추정 값</strong>으로 먼저 보여줄 수 있는지

저는 이런 관점으로 기존 플로우를 다시 살펴보면,  
생각보다 쉽게 체감 속도를 올릴 수 있는 지점이 자주 보인다고 느꼈습니다.

## 🦮 실수하기 쉬운 안티 패턴들

### 🦄 1. “로딩 스피너 하나면 충분하겠지”라고 생각하기

단순 스피너만 넣어 두고,  
로딩이 2초, 3초씩 길어지는 경우를 종종 봅니다.

- 스피너만 돌고 있으면 사용자는 <strong>“멈춘 건지, 진행 중인지”</strong>를 알기 어렵습니다.  
- 특히 여러 번 같은 경험을 반복하면, <strong>시스템에 대한 신뢰</strong>가 금방 떨어집니다.

저는 가능하면 <strong>진행률, 단계, 남은 작업</strong> 중 적어도 하나는 보여주려고 합니다.

### 🦄 2. 느린 작업을 아무 설명 없이 바로 실행시키기

대량 데이터 처리나 외부 API 호출처럼 시간이 오래 걸릴 수 있는 작업을  
별다른 안내 없이 실행시키면, 사용자는 중간에 <strong>“멈춘 줄 알고 다시 시도”</strong>할 수 있습니다.

- 이때 중복 요청이 쌓이거나,  
  예기치 못한 부하가 생길 수 있다는 점도 신경 써야 합니다.

그래서 저는 이런 작업일수록,

- 예상 소요 시간이나,  
- “중간에 새로고침하지 말아 달라”는 안내,  
- 작업이 끝났을 때의 결과 요약 등을 <strong>명확하게 보여주는 작은 마이크로카피</strong>를 준비하려고 합니다.

## 🦮 마무리: 제가 스스로에게 던지는 체크리스트

도허티 임계값을 떠올리면서, 화면을 검수할 때 제가 확인하고 싶은 질문들을 정리해 보겠습니다.

1. 사용자가 버튼이나 링크를 눌렀을 때, <strong>400ms 안에 눈에 보이는 변화</strong>가 항상 있는가?  
2. 서버 응답이 느릴 수 있는 플로우에서, <strong>즉시 피드백과 진행 표시</strong>를 별도로 설계했는가?  
3. 스피너만 던져 놓고, <strong>얼마나 걸리는지·무엇을 하는지</strong>를 숨겨 놓은 부분은 없는가?  
4. 비동기 처리나 캐시를 활용해서, <strong>사용자가 굳이 기다리지 않아도 되는 구간</strong>을 줄일 수는 없는가?  
5. 사용자가 자주 반복하는 입력-응답 루프에서, <strong>작은 지연들이 누적되어 흐름을 끊고 있지는 않은가?</strong>

저는 앞으로도 새로운 기능을 만들 때마다,  
단순히 “정확하게 동작하는가?”에서 멈추지 않고  
<strong>“사용자가 기다린다고 느끼지 않을 만큼 빠르게 반응하는가?”</strong>를 같이 확인하면서  
도허티 임계값을 더 잘 활용해 보고 싶습니다.
