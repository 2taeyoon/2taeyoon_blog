## 🦮 AI Agent에게 일을 맡기는 업무 프로세스

기능을 하나 더 만드는 일이 아니었다. 사람이 중간에서 파악해서 지시하지 않게, 일을 넘기는 과정을 정해 보는 일이었다.

슬랙으로 요청을 건네던 방식을 버리고, Github Issue와 15분 loop로 바꿨다. 코드를 어떻게 짜는지는 접어 두고, 일을 어떤 단위로 자르고, 어떤 말로 맡기고, 끝난 것을 무엇으로 확인하는지를 정리해 둔다.

한 줄로 줄이면 이렇다. **대화로 일을 옮기지 않는다. Github Issue로 남기면, 15분 loop가 보고, 요청하고, 고치고, 확인해서 dev에 넣는다. 나는 방향이 갈릴 때만 고른다.**

---

## 🦮 1. 용어부터 정리

작업하면서 계속 나온 말이다. 이 정도는 알아야 보고를 읽고 판단할 수 있다.

### 🦄 loop

**loop**는 같은 확인을 일정 시간마다 다시 하는 반복 업무다. 나는 15분마다 돌렸다. 채팅에 한 번 말하고 끝나는 일이 아니다.

반복할 내용이 길어지면, 그 문장을 저장소의 `loop.md`에 적어 둔다. 창을 열 때마다 긴 문장을 다시 붙이지 않기 위해서다. 다만 `/loop 15m`만 치면, 그 파일 대신 기본 반복이 돌 수 있다. 파일을 읽으라고 문장에 같이 적어야 그 규칙으로 돈다.

### 🦄 Github Issue와 Github Label

**Github Issue**는 업무 요청 게시판이다. 슬랙에 "이거 해 주세요"라고 적는 대신, 여기에 적는다. 받는 쪽이 자기 차례에 읽고, 끝나면 글이 닫힌다.

**Github Label**은 그 글이 누구 일인지 붙이는 이름표다. 라벨마다 맡는 범위가 다르다.

| Github Label | 맡는 범위 |
|---|---|
| to-agent | 분석, 메일, 공용 데이터, 동작 설정 |
| to-backend | 서버 API |
| to-frontend | 화면 |
| to-mcp | 모니터링 연결, 지표 |
| to-infra | 공통 규칙, 문서, 실행 환경 |

Github Label이 없으면, 글을 봐도 자기 일인지 모른다.

### 🦄 Notion 작업현황표

**Notion 작업현황표**는 요구사항 한 줄이 일 한 건인 진행 표다. Github Issue가 비었을 때, loop가 다음 일을 여기서 집는다.

| 칸 | 담는 것 |
|---|---|
| 요구사항 ID | 그 줄의 번호 |
| 작업 내용 | 그 줄에서 할 일 |
| 진행상황 | 대기, 진행 중, BLOCKED, 완료 |
| 담당자 | 그 줄을 처리한 사람의 라벨 |
| 비고 | 묶음, 작업 번호, PR. 묶음은 필수, 선택, 이후 |

loop가 줄을 끝내면 담당자 칸에 내 라벨이 남고, 진행상황이 완료가 된다. 내가 표를 열어 찍지 않는다.

### 🦄 응답에 쓰는 상태

요청을 받은 AI Agent는 침묵하지 않고, 상태 중 하나로 답한다.

- **accepted**: 수락. 이대로 진행한다.
- **counter**: 대안. 요청 그대로는 어렵고, 다른 안을 제안한다.
- **in-progress**: 진행 중.
- **needs-human**: 사람 판단이 필요해서 멈춤.

### 🦄 Worktree

**Worktree**는 같은 저장소를 폴더 하나 더 열어 두는 일이다. 루프용 폴더와 작업용 폴더를 나눈다. 한 폴더에서 창을 둘 열면, 한쪽이 작업 줄을 바꾸는 순간 다른 쪽 작업이 날아간다.

### 🦄 contracts

**contracts**는 파트 사이의 약속 문서다. 화면과 서버, 서버와 분석이 주고받는 모양을 적어 둔다. 이 문서를 바꾸는 PR은 관련 파트 두 명의 확인이 필요하다. 한 파트가 약속을 혼자 바꾸면, 다른 파트 결과물이 한꺼번에 어긋난다.

### 🦄 CI와 merge queue

이건 데모 뒤에 붙이기로 한 다음 단계 용어다.

- **CI**: 사람이 보기 전에 자동으로 도는 검사. 형식, 테스트, 빌드, 안전 규칙이 여기 있다.
- **merge queue**: 검사에 통과한 PR을 한 줄로 세워, 합친 상태로 한 번 더 검사한 뒤 넣는 줄.

## 🦮 2. 한 번 맡기면, 그다음부터는 loop가 가져간다

바꾸기 전 요청은 이렇게 흘렀다.

1. 요청하는 쪽이 슬랙으로 받는 쪽에게 일을 보낸다
2. 받는 쪽이 "이거 어떻게 해?"라고 묻는다
3. 요청하는 쪽이 지시문을 작성한다
4. 받는 쪽이 그 문장을 작업 창에 붙인다
5. 결과물이 나오면 받는 쪽이 슬랙으로 "됐어요"라고 알린다

사람이 다섯 번 끼어 있다. 그중 누가 자리를 비우면 일이 멈춘다.

그래서 매일 시킬 말을 나누지 않았다. 저장소에 규칙을 한 번 남기고, loop에 이렇게 맡겼다.

> "저장소와 열린 Github Issue를 보고, 네 범위의 일은 알아서 처리해. 다른 쪽이 필요하면 네가 Github Issue로 남겨. 검사는 네가 돌리고, 통과하면 dev에 넣어. Issue가 없으면 Notion 작업현황표에서 대기인 필수 줄의 다음 한 건을 하고, 끝나면 담당자 칸에 네 라벨을 남기고 진행상황을 완료로 바꿔. 크리티컬한 문제는 needs-human으로 남기고 멈춰."

이 문장 안에 요청, 처리, 확인, 멈춤이 같이 들어 있다. 나는 칸을 찍어서 부탁하지 않는다. 무엇을 요청할지도 loop가 저장소를 보고 정한다. 로그인만은 내가 한다. 그 창은 loop가 대신 열지 못한다.

loop 한 회차는 이 순서다.

1. 최신 상태를 받는다. 어제 기억으로 판단하지 않는다
2. 자기 Github Label의 Issue를 본다. 수락하거나 대안을 적고, 수락한 것은 진행해서 PR을 올린다
3. 다른 범위가 필요하면, 그 라벨로 Github Issue를 자기가 남긴다. 받는 쪽 loop가 다음 회차에 읽는다
4. 자기 PR에 변경 요청이 있으면 고쳐서 다시 올리고, 검사가 통과하면 dev 머지를 예약한다
5. 자기 범위로 온 리뷰는 검사를 직접 돌린 뒤에만 승인하거나 변경을 요청한다. 실패하면 승인하지 않는다
6. 크리티컬한 문제는 needs-human으로 남기고 멈춘다
7. 이슈가 없으면 Notion 작업현황표에서 대기인 필수 줄의 다음 한 건을 진행한다. 끝나면 담당자 칸에 내 라벨을 남기고 진행상황을 완료로 바꾼다

줄을 내가 골라 주지 않는다. 비고 앞머리가 묶음이고, loop는 순서대로 필수이면서 대기인 줄만 집는다.

| 묶음 | 지금 표의 줄 | 언제 집나 |
|---|---|---|
| 필수 | 223 | 먼저 집는다. 이 가운데 대기인 줄만 다음 일이다 |
| 선택 | 61 | 필수가 끝난 뒤에 집는다. 지금은 전부 대기 |
| 이후 | 58 | MVP 다음에 집는다. 지금은 전부 대기 |

표를 열어 완료를 찍지 않는다. 끝난 줄에는 담당자 칸의 라벨과 완료가 같이 남아 있다.

밤에도 loop가 켜져 있으면 아침에 결과가 dev에 올라가 있다. 만드는 일만 맡기면 PR이 쌓인다. 확인과 dev에 넣는 일까지 같은 회차에 있어야 쌓이지 않는다. 실제로 승인만 사람에게 남겨 두니, 열린 PR이 서른 개까지 쌓이고 밤사이 머지는 0건이었다.

## 🦮 3. 누가 할지는 라벨이 정하고, 해결도 loop가 한다

"누가 해야 하지?"를 회의에서 정하지 않는다. Github Label이 범위다.

| Github Label | 맡는 범위 |
|---|---|
| to-agent | 분석, 메일, 공용 데이터, 동작 설정 |
| to-backend | 서버 API |
| to-frontend | 화면 |
| to-mcp | 모니터링 연결, 지표 |
| to-infra | 공통 규칙, 문서, 실행 환경 |

리뷰어도 내가 고르지 않는다. "관련 담당자"라고 적으면 알맞은 라벨을 고른다. 범위와 리뷰 라벨을 규칙 안에 적어 두면, loop가 그 표로 배정한다. 작성자 자신은 빠진다.

약속 문서(contracts)가 바뀌면 관련 라벨 두 곳의 loop가 확인한다. 한 범위가 약속을 혼자 바꾸면 다른 결과물이 같이 어긋난다. 앞선 PR 위에 다음 PR을 쌓았으면, 앞의 것이 dev에 들어간 뒤에 다음 것을 dev 기준으로 다시 맞추고 넣는다. 그 전에 쌓으면 결과가 다른 줄로 들어간다. 한 번 그렇게 들어가서 loop가 따로 정리했다.
