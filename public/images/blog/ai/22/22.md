## 🦮 데모 날, AI Agent에게 하루를 맡긴 기록

데모 당일이었다. 코드를 한 줄도 직접 쓰지 않았다. 내가 한 일은 세 가지다. 일을 어떤 단위로 자를지 정하고, 그 일을 어떤 문장으로 맡길지 쓰고, 끝난 결과를 무엇으로 확인할지 정했다.

오늘 한 일은 크게 네 덩어리다. 모니터링 서버(Zabbix)와 우리 화면을 실제로 연결했다. 데모 흐름을 초 단위로 재는 리허설을 했다. RAG라는 새 기능을 기획부터 PR까지 끌고 갔다. 그 사이사이 막힌 곳을 풀었다.

한 줄로 줄이면 이렇다. **짧게 떠오른 요청을, 에이전트가 오해 없이 끝낼 수 있는 업무 지시로 바꾸는 일이 내 일이다. 확인은 "됐어요"라는 말이 아니라 숫자와 화면으로 받는다.**

## 🦮 1. 용어부터 정리

오늘 보고를 읽고 판단하려면 이 정도는 알아야 했다. 구현 원리는 몰라도 된다. 무엇을 가리키는 말인지만 알면 지시가 정확해진다.

### 🦄 Zabbix 웹 (`http://<팀 서버 주소>/zabbix`)

**Zabbix**는 PC와 서버의 CPU, 메모리, 디스크, 네트워크를 감시하는 모니터링 서버다. 웹 화면에서 두 메뉴를 가장 많이 봤다.

| 메뉴 | 보는 것 |
|---|---|
| Monitoring → Latest data | PC별 최신 수집 값. 값이 들어오는지 여기서 확인한다 |
| Monitoring → Problems | 지금 열린 장애(알람). 우리 제품이 가져가는 원본이다 |

팀 서버 주소는 글과 문서에 적지 않는다. 주소, 계정, 토큰은 정해진 채널로만 주고받는다.

### 🦄 로컬 사이트 (`http://localhost:5173`)

우리 제품 화면을 내 PC에서 띄운 것이다. 현황 홈, 장애 상세, AI 어시스턴트 채팅이 여기 있다. 같은 화면이라도 뒤에서 어떤 데이터를 쓰느냐에 따라 두 모드가 있다.

- **목 모드**: 가짜 데이터로 돈다. 서버 없이 화면만 확인할 때 쓴다.
- **실연동 모드**: 실제 팀 Zabbix와 실제 LLM에 붙는다. 데모는 이 모드로 한다.

### 🦄 LLM, 임베딩, RAG

- **LLM**: 문장을 만드는 AI 모델이다. 우리는 Gemini 무료 등급의 가벼운 모델(lite)을 붙였다.
- **임베딩**: 문장을 숫자 묶음으로 바꾼 것이다. 뜻이 비슷한 문장끼리 숫자도 가깝게 나온다. 이 숫자로 "의미가 비슷한 글"을 찾는다.
- **RAG**: 질문이 들어오면 먼저 우리 자료에서 관련 내용을 찾아 근거로 붙인 뒤 답하는 방식이다. AI가 기억에 의존해 지어내지 않게 하는 장치다.
- **청킹**: 긴 문서를 검색하기 좋은 크기로 자르는 일이다. 너무 크면 엉뚱한 부분까지 딸려 오고, 너무 작으면 앞뒤 맥락이 끊긴다.

### 🦄 MCP

**MCP**는 AI가 외부 시스템을 조회할 때 거치는 정해진 창구다. AI가 서버나 DB를 마음대로 건드리지 못하게, "이 창구로 이 조회만 해"라고 범위를 좁힌다. 우리 제품의 AI는 MCP 창구로만 Zabbix를 조회한다. 오늘 만든 지식 검색도 같은 방식으로 창구를 하나 더 열었다.

### 🦄 서브에이전트와 worktree

- **서브에이전트**: 메인 에이전트가 일을 떼어 맡기는 보조 에이전트다. 반복이 많거나 오래 걸리는 일을 넘기면 메인은 다른 일을 계속한다. 노션 360개 줄의 번호를 다시 매기는 일을 이렇게 넘겼다.
- **worktree**: 같은 저장소를 폴더 하나 더 열어 두는 일이다. 서브에이전트가 한 폴더에서 사이트를 띄우는 동안, 메인은 다른 폴더에서 PR을 고쳤다. 한 폴더를 둘이 쓰면 한쪽이 브랜치를 바꾸는 순간 다른 쪽 작업이 엎어진다.

### 🦄 결정 문서와 계약 문서

- **결정 문서**: 팀이 정한 것을 결정, 이유, 기각한 대안 세 줄로 남긴 기록이다. 오늘은 "알람 목표 시간 120초"와 "RAG 범위" 두 건을 남겼다.
- **계약 문서(contracts)**: 파트끼리 주고받는 모양을 적은 약속이다. 바꾸려면 관련 파트 두 명이 확인해야 한다.

### 🦄 리허설과 합격선

**리허설**은 데모 흐름을 실제로 한 번 돌려 시간을 재는 일이다. 우리 합격선은 이렇다. **CPU 부하를 주고 담당자 메일이 오기까지 3분 이내, 그것도 2회 연속.**

## 🦮 2. 오늘의 흐름

| 시간대 | 한 일 | 에이전트에게 맡긴 방식 |
|---|---|---|
| 오전 | 팀원 슬랙 요청 묶음 처리. 리뷰, 머지, 노션 체크, 알람 목표 결정 | 슬랙 글을 통째로 붙여 "내 담당만 처리" |
| 점심 무렵 | 내 PC를 팀 Zabbix에 연결, 로컬 사이트 띄우기 | 관리자 권한이 필요한 일은 스크립트만 받아 내가 실행 |
| 오후 초반 | 로컬 사이트를 실연동으로 전환, LLM 연결, 채팅 답변 개선 | `.env` 두 줄만 내가 고치고 나머지는 에이전트 |
| 오후 중반 | 리허설 1회차 계측, 노션 정리 | 측정은 에이전트가 DB 기록으로, 번호 정리는 서브에이전트 |
| 오후 후반 | RAG 기획, 노션 14줄, 순서대로 14개 처리 | 기획 → 표 → 줄마다 브랜치·PR |
| 저녁 | 리뷰 변경 요청 반영, 자동 머지 대응, 데일리 로그, 이 글 | 리뷰 글을 붙여 "막힌 곳 풀어 줘" |

## 🦮 3. 짧은 지시를 업무 지시로 바꾸기

오늘 가장 많이 배운 부분이다. 머릿속에 떠오른 요청은 대개 한 줄이다. 그 한 줄을 그대로 던지면, 에이전트는 빈칸을 자기 추측으로 채운다. 아래는 실제로 짧게 던진 말과, 같은 의도를 에이전트가 오해 없이 끝낼 수 있게 늘려 쓴 지시다.

### 🦄 "dev pull 받고 로컬로 사이트 띄워봐"

> "dev 브랜치 최신을 받고 로컬 사이트를 실연동 모드로 다시 띄워 줘. 지금 떠 있는 서비스는 예전 코드라서, 우리 서비스 다섯 개만 내리고 다시 올려. 다른 프로그램은 끄지 마. 비밀값 파일은 열지 말고 프로그램이 직접 읽게만 해. 다 띄우면 각 서비스의 상태 확인 주소와, 로그인한 뒤 연결 상태 화면이 전부 정상인지 확인하고, 현황 숫자 몇 개와 로그인 정보를 보고해. 실패한 게 있으면 로그 마지막 몇 줄을 같이 붙여."

**왜 이렇게 늘렸나.** "띄워 봐"만 쓰면 이미 떠 있는 옛 서비스를 그대로 두고 "떠 있습니다"로 끝날 수 있다. 무엇을 내리고 무엇을 건드리지 말지, 어디까지 확인해야 끝인지를 적어야 한다. 끝의 보고 형식까지 정해 두면 다시 묻지 않아도 된다.

### 🦄 "RAG 이용해서 서비스 하나 더 기획해 줘"

> "우리 장애 대응 시스템에 RAG를 써서 붙일 만한 서비스를 하나 기획해 줘. 조건은 우리 원칙을 그대로 지키는 것이다. 근거 없는 답을 하지 않고, 실행은 미리보기로만 하고, 위험 등급은 규칙 파일이 정한다. 어떤 자료를 모을지, 어떻게 자를지, 어디에 저장할지, AI가 어떤 창구로 찾을지, 화면에 어떻게 보일지, 안전 장치와 평가 기준까지 나눠서 작업 단위로 쪼개. 작업마다 요구사항 ID를 붙여 노션 작업표 227번 아래에 한 줄씩 넣고, 담당 후보 파트를 비고에 적어. 정해지지 않은 값은 지어내지 말고 '추후결정'으로 비워 둬."

**왜 이렇게 늘렸나.** "RAG 해 줘"는 기능 이름일 뿐 범위가 없다. 원칙을 먼저 박아 두지 않으면 "AI가 과거 사례를 보고 조치를 실행한다" 같은 위험한 안이 나올 수 있다. 결과물의 형태(노션 행, 요구사항 ID, 위치)를 지정하면 그대로 다음 지시의 입력이 된다.

### 🦄 "노션에 아래 처리해 줘 순서대로"

> "노션의 RAG 작업 14줄을 위에서부터 순서대로 구현해. 한 줄에 브랜치 하나, PR 하나다. 앞 줄의 결과가 뒤 줄의 입력이면 앞 브랜치 위에 쌓고, PR 본문에 머지 순서를 적어. 내 담당 폴더가 아닌 일(화면, 서버 API, 스케줄러)은 직접 고치지 말고 담당 파트에 업무 요청 Issue로 남겨. 파트 사이 약속 문서를 바꿔야 하면 그 PR을 먼저 올려. 줄마다 검사를 돌려 통과한 결과를 PR에 적고, 노션 그 줄의 상태와 PR 링크를 갱신해."

**왜 이렇게 늘렸나.** "순서대로"에는 함정이 있다. 순서대로 처리하다 남의 폴더를 고치면 팀 규칙을 어긴다. 그래서 "내 몫은 구현, 남의 몫은 요청"이라는 선을 지시 안에 넣었다. 그 결과 14줄 중 내 몫 11줄은 PR이 됐고, 남의 몫 3곳은 Issue로 넘어갔다.

### 🦄 "LLM 연결해, GEMINI_API_KEY로 하면 됨"

> "로컬 AI 분석기에 Gemini를 붙여 줘. 키는 내가 비밀값 파일에 넣어 둔 값을 프로그램이 읽게만 하고, 너는 값을 보거나 출력하지 마. 먼저 이 키로 쓸 수 있는 모델 목록을 확인하고, 후보 두세 개를 짧게 호출해서 응답 시간과 형식이 맞는지 본 다음 골라. 연결한 뒤에는 상태 확인 화면에 모델 이름이 나오는지, 채팅이 실제로 LLM 답을 하는지 확인해. 팀 공용 설정은 바꾸지 말고 내 PC 실행에만 적용해."

**왜 이렇게 늘렸나.** 모델 이름을 내가 정해 주면 이미 없어진 모델일 수 있다. 실제로 후보 중 하나는 응답이 없었고, 하나는 이미 없는 모델이었다. "확인하고 골라"라고 맡기니 에이전트가 직접 호출해 보고 3초대에 정상 형식으로 답하는 모델을 골랐다. 나중에는 무료 등급이라 더 가벼운 lite 모델로 바꿨다.

### 🦄 "통신 끊긴 서버 있어?"

이건 지시가 아니라 질문이었는데, 답이 "확인할 수 없음"으로 나왔다. 여기서 배운 것이 있다. **AI가 "모른다"고 하면, 데이터가 없는 건지 AI에게 맥락을 안 준 건지부터 가른다.**

> "채팅이 '통신 끊긴 서버'를 확인할 수 없다고 했어. 실제로 그런 서버가 있는지 읽기 전용 조회로 직접 확인하고, 채팅이 왜 그렇게 답했는지 원인을 설명해. 고칠 수 있으면 지금 범위 안에서 할 수 있는 방법과, 범위를 넘는 방법을 나눠서 제안해."

확인해 보니 8대 모두 정상이었다. 채팅이 모른 이유는 AI에게 장애 목록만 넘기고 호스트 상태는 넘기지 않았기 때문이다. 틀린 답은 아니었지만 쓸모없는 답이었다.

### 🦄 슬랙 글을 통째로 붙이며 "아래 다 처리해 줘"

> "아래는 팀 채널에서 나에게 온 요청들이다. 내 담당인 것만 골라 처리해. 각 요청이 이미 처리됐는지 먼저 저장소와 노션에서 확인하고, 남은 것만 해. 저장소를 바꾸는 일은 일마다 새 브랜치로 하고, 내가 결정해야 하는 항목은 근거와 함께 결정 문서로 남겨. 사람만 할 수 있는 일(관리자 권한, 로그인)은 실행할 명령으로 정리해서 넘겨."

**왜 이렇게 늘렸나.** 슬랙 글에는 이미 끝난 일, 남의 일, 내가 결정할 일이 섞여 있다. "확인부터, 내 몫만, 결정은 문서로" 세 가지를 붙이면 에이전트가 이미 머지된 PR을 다시 고치는 헛일을 하지 않는다. 오늘은 알람 목표 시간 결정이 이 지시에서 나왔다.

## 🦮 4. Zabbix 웹과 로컬 사이트, 둘을 같이 보는 이유

제품 화면은 결과이고, Zabbix 웹은 원본이다. 둘 중 하나만 보면 문제가 어디서 생겼는지 모른다.

### 🦄 Zabbix 웹에서 한 일

**내 PC가 수집되지 않던 문제.** 에이전트(수집 프로그램)가 서버에 붙어도 "그런 호스트 없음"이라는 답만 돌아왔다. 처음에는 추측으로 이름을 바꿨다가 틀렸다. 그래서 방식을 바꿨다.

> "이름을 추측해서 바꾸지 마. 서버에 같은 요청을 직접 보내서, 후보 이름마다 서버가 받아 주는지 거절하는지 응답으로 판정해. 받아 주는 이름이 나오면 그 이름으로만 바꾸는 스크립트를 만들어 줘. 설정 파일은 관리자 권한이 필요하니 내가 실행할게."

서버 응답으로 정확한 등록 이름을 찾았다. 내가 관리자 창에서 스크립트를 한 번 돌렸고, Latest data에 CPU 값이 들어오는 것을 화면으로 확인했다.

**서버가 아예 응답하지 않던 시간.** 오전에 팀 서버의 DB가 멈췄다. 새벽에 자동 업데이트가 돌면서 같이 멈춘 것으로 추정됐고, 서버 담당자가 복구했다. 그 사이 에이전트에게 맡긴 일은 하나였다. **내 쪽 문제와 서버 쪽 문제를 가르는 것.** 내 PC에서 서버로 연결은 되는데 응답이 없다는 증거를 정리해 서버 담당 Issue에 남겼다. 서버가 돌아오자 바로 판정이 났다.

### 🦄 로컬 사이트에서 한 일

**목 모드에서 실연동으로.** 처음엔 가짜 데이터로 띄웠다. 실연동으로 바꾸는 데 필요한 건 비밀값 파일 두 줄이었고, 그건 내가 직접 고쳤다. 에이전트는 비밀값 파일을 열지 않는다. 바꾼 뒤 화면에 팀 PC들의 실제 장애 21건과 감시 호스트 8대가 떴다.

**화면에 '확인할 수 없음'이 가득할 때.** 숫자 자리마다 "확인할 수 없음 · TOOL_ERROR"가 떴다. 화면이 고장 난 게 아니라 화면 뒤의 서비스가 죽은 것이었다. PC 메모리가 모자라 서비스 네 개가 한꺼번에 꺼져 있었다. 이 화면이 보이면 이렇게 지시한다.

> "화면 숫자가 전부 확인할 수 없음이야. 화면 뒤 서비스들이 살아 있는지 포트와 상태 확인 주소로 먼저 봐. 죽어 있으면 남은 메모리를 확인하고, 같은 설정으로 다시 띄운 뒤 화면 숫자가 돌아왔는지 확인해."

**채팅이 쓸모없는 답을 할 때.** 장애 화면을 열지 않고 물으면 AI가 아무 맥락 없이 답했다. 지금 열린 장애 목록을 같이 넘기도록 고쳤다. 그런데 팀원 리뷰에서 구멍이 나왔다. "수집이 멈춰도 오래된 목록을 지금 사실처럼 답한다." 그래서 마지막 수집이 10분보다 오래됐으면 AI를 부르지 않고, 코드가 "확인할 수 없음"과 마지막 수집 시각으로 답하게 바꿨다.

### 🦄 둘을 대조하는 습관

화면이 말한 것을 Zabbix 원본과 맞춰 본다. "통신 끊긴 서버" 질문도 그랬다. 채팅 답만 믿지 않고, 에이전트에게 원본을 직접 조회해 대조하라고 했다. 보낸 메일의 "확인할 수 없음: 없음"도 같은 식으로 확인했다. 그 줄은 "AI가 확인 못 한 항목이 없다"는 뜻이었다. 메일에 실제 수치 칸이 없어서 생긴 오해라, 메일 담당에게 수치 칸 추가를 요청했다.

## 🦮 5. 리허설: "됐어요" 대신 초 단위 숫자

데모가 잘 될지는 말로 확인하지 않는다. 구간마다 시간을 잰다.

> "내 PC에서 CPU 부하를 3분 주입해 리허설 1회차를 해. 주입 시작, 알람 발생, 우리 DB에 장애가 저장된 시각, AI 리포트 저장, 메일 기록 시각을 화면이 아니라 DB 기록으로 재. 못 본 칸은 '확인 못 함'으로 두고 추정치를 적지 마. 끝나면 정리 스크립트를 돌리고, 결과를 기록표에 한 줄로 추가해 PR로 올려."

| 구간 | 주입 후 |
|---|---|
| 알람(High) 발생 | 115초 |
| 우리 DB에 장애 저장 | 132초 |
| AI 리포트 저장 | 153초 |
| 담당자 메일 기록 | **179초 (2분 59초)** |

합격선 3분을 1초 남기고 통과했다. 같은 날 데모 PC에서 서버 담당자가 두 번 더 쟀다. 2분 27초, 1분 32초로 두 번 연속 통과였다.

**숫자가 목표를 넘을 때는 목표를 고칠지, 시스템을 고칠지를 결정 문서로 정한다.** 어제 실측한 알람 시간은 104초로 목표 90초를 넘었다. 알람 기준을 낮추면 빨라지지만, 같은 설정을 팀 PC 여섯 대가 같이 쓴다. 평소에도 알람이 울리고 AI가 그걸 전부 분석해 데모 화면이 잡음으로 찬다. 그래서 목표를 120초로 현실화했고, 기각한 대안까지 세 줄로 남겼다.

## 🦮 6. RAG를 기획에서 PR까지: 기획자의 관점

오늘 가장 큰 일이었다. 기능 자체보다 일을 어떻게 나눴는지가 남길 만하다.

### 🦄 무엇을 만들었나

새 장애가 뜨면 과거 장애 리포트, 운영 문서(런북), 조치 규칙 설명, 사람이 쓴 해결 메모에서 비슷한 사례를 찾는다. 그리고 **근거 번호와 함께** 보여 준다. 분석 리포트에는 "과거 유사 사례" 항목이 붙고, 채팅에서 "전에 어떻게 해결했어?"라고 물으면 인용으로 답한다.

### 🦄 일을 자른 방식

| 단계 | 한 일 | 누구 몫 |
|---|---|---|
| 기획 | 범위·구조·담당을 결정 문서로 | 나 |
| 수집 → 청킹 → 저장 → 임베딩 → 검색 | 한 단계에 PR 하나씩, 앞 단계 위에 쌓음 | 내 폴더 |
| AI 창구 | 약속 문서 먼저, 구현은 그다음 | 약속은 두 파트 승인 |
| 분석·채팅 연동 | 근거가 없으면 붙이지 않음 | 내 폴더 |
| 화면 카드, 메모 입력, 야간 재색인 | 업무 요청 Issue | 화면·서버·스케줄러 담당 |
| 안전, 평가 | 민감정보 가리기, 질문 20개 평가 | 내 폴더 |

### 🦄 평가는 숫자로

"검색이 잘 된다"는 말로 넘기지 않았다. 질문 20개를 만들어 쟀다.

| 지표 | 결과 | 뜻 |
|---|---|---|
| Recall@5 | 0.944 (17/18) | 정답 자료가 상위 5개 안에 든 비율 |
| 관련 없는 질문 정확도 | 1.00 (2/2) | "고양이 사료 추천" 같은 질문에 결과를 0건으로 냈는가 |
| 응답 시간 | 평균 0.5초, 최대 2.3초 | 목표 3초 이내 |

놓친 질문 하나도 그대로 적었다. 영어로 된 장애 제목과 한국어 질문의 어휘 차이로 추정한다. 실패를 기록해야 다음 지시를 정확히 쓸 수 있다.

### 🦄 막힌 곳: 범위 판정

PR을 올리자 리뷰가 막았다. 이유는 코드가 아니라 범위였다. "RAG는 데모 이후 범위인데 왜 지금 넣나", "DB 파일은 두 개로 정했는데 세 번째가 왜 있나". 둘 다 맞는 지적이다. 에이전트에게 맡긴 답은 코드 수정이 아니었다.

> "리뷰어가 지적한 범위 문제마다, 왜 이번에는 예외인지 근거를 결정 문서에 명시해. 데모 이후 착수 근거, 세 번째 파일이 원본 데이터가 아니라 언제든 다시 만들 수 있는 색인이라는 점, AI 문장을 만드는 곳은 여전히 한 곳뿐이라는 점을 적어. 그다음 각 PR에 지적 하나하나에 대한 답을 달고 다시 리뷰를 요청해."

**배운 것.** 큰 기능은 코드보다 결정 문서가 먼저 머지돼야 한다. 근거가 저장소에 없으면 리뷰어는 막을 수밖에 없다.

## 🦮 7. 에이전트가 멈췄을 때

멈춘 곳이 오히려 지시를 다듬는 지점이었다.

| 멈춘 상황 | 원인 | 대응 |
|---|---|---|
| 비밀값 파일 읽기 거부 | 에이전트의 안전 장치 | 값은 내가 넣고, 프로그램이 직접 읽게만 함 |
| 관리자 권한 작업 거부 | 권한을 올리는 행동은 막힘 | 에이전트가 스크립트를 만들고 내가 관리자 창에서 실행 |
| 외부 프로그램 설치 거부 | 남의 코드를 PC에 까는 일 | 설치 전에 그 코드를 읽어 위험 동작이 없는지 확인하게 한 뒤 진행 |
| 연결 코드 만료 | 5분짜리 1회용 코드 | 설치를 먼저 끝내고 새 코드를 받아 바로 연결 |
| 서비스 일괄 종료 | PC 메모리 부족 | 남은 메모리 확인 후 같은 설정으로 재기동 |
| 승인이 사라짐 | PR에 새 커밋을 올리면 승인이 초기화됨 | 재승인 요청을 같이 남김 |
| 자동 머지 BLOCKED | 새 검사 규칙이 생기기 전의 PR은 검사가 안 돎 | dev를 합쳐 다시 올리면 검사가 돌고 머지 큐로 감 |

**중요한 원칙.** 에이전트가 막혔을 때 우회하라고 하지 않는다. 막힌 이유를 확인하고, 사람이 해야 할 부분과 에이전트가 할 부분을 다시 나눈다. 우회하라고 시키면 안전 장치를 내 손으로 끄는 셈이다.

한 가지 더 있다. 오늘 팀 채널에 비밀번호와 API 키가 그대로 올라온 적이 있었다. 이 글을 쓸 때도 에이전트에게 "주소, 비밀번호, 키, 개인 메일은 넣지 말라"고 먼저 적었다. 비밀값은 정해진 1:1 채널과 비밀값 파일에만 둔다.

## 🦮 8. 역할 분담과 검증

| 누가 | 하는 일 |
|---|---|
| 나 | 방향과 범위 결정, 결정 문서 승인, 비밀값 입력, 관리자 권한 실행, 최종 화면 확인 |
| 메인 에이전트 | 조사, 구현, 테스트, PR, 리뷰 답글, 노션 갱신, 결과 보고 |
| 서브에이전트 | 오래 걸리거나 반복이 많은 일. 노션 번호 정리, 사이트 재기동, 프로필 정리 |
| 팀원(과 그 에이전트) | 리뷰, 자기 범위 Issue 처리, 서버·화면·메일 담당 일 |

검증은 이렇게 받는다.

- **결과는 증거로 받는다.** "됐어요" 대신 상태 확인 결과, 테스트 개수, 초 단위 기록, 화면 캡처를 받는다.
- **건드리면 안 되는 곳은 비교로 확인한다.** 프로필 소개 글을 정리할 때 "주석과 연락처, 통계 칸은 건드리지 말라"고 했다. 에이전트가 정리 전후를 글자 단위로 비교했고, 하나라도 다르면 올리지 말라고 지시해 두었다.
- **추정은 추정이라고 쓰게 한다.** 원인을 단정하지 않고 "(추정)"을 붙이게 했다. 서버 DB가 멈춘 원인도 확정하지 않고 그렇게 남았다.
- **기록은 남긴다.** 끝난 일은 PR, Issue, 노션 줄, 데일리 로그로 남긴다. 오늘은 데일리 로그도 에이전트가 정리해 등록했다.

## 🦮 9. 오늘 정리한 지시 원칙

1. **한 줄 요청을 받으면, 범위·하지 말 것·끝의 기준·보고 형식을 붙인다.** 에이전트는 빈칸을 추측으로 채운다.
2. **원칙을 지시 첫머리에 둔다.** "근거 없이 답하지 않는다, 실행은 미리보기로만"을 먼저 적어야 위험한 안이 나오지 않는다.
3. **확인부터 시킨다.** 이미 끝난 일, 남의 일, 내가 결정할 일을 먼저 가르게 한다.
4. **추측 대신 측정을 시킨다.** 이름, 모델, 원인 모두 실제 응답으로 판정하게 한다.
5. **내 몫은 구현, 남의 몫은 요청이다.** 다른 파트 폴더는 고치지 않고 Issue로 넘긴다.
6. **결정은 문서로 남긴다.** 목표를 바꾸거나 규칙에 예외를 둘 때는 결정, 이유, 기각한 대안을 적는다.
7. **막히면 우회하지 않는다.** 사람의 몫과 에이전트의 몫을 다시 나눈다.
8. **길고 반복적인 일은 서브에이전트로, 동시에 할 일은 폴더를 나눠서** 맡긴다.

코드는 한 줄도 직접 쓰지 않았지만 하루 종일 판단을 했다. 무엇을 맡길지, 어떤 말로 맡길지, 끝난 걸 무엇으로 볼지. 이게 바이브 코딩에서 내가 맡은 일이다.
