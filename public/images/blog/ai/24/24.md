## 🦮 AI 에이전트를 하나의 레포에서 운영한 방법

ax-company-hq는 가상 e커머스 회사의 부서별 AI 에이전트를 연결한 AX 플랫폼이다. 백엔드 저장소 `ax-backend`에는 부서 폴더 15개가 있고, 팀원 6명이 담당 폴더를 나눠 관리한다. 나는 finance(재무·정산)와 safety(안전 규칙)를 맡았다.

이 글에서는 Git과 GitHub 작업을 자동화한 방법을 정리한다. 에이전트에게 준 지시, GitHub 설정, 자동화 절차와 각각의 설정이 필요한 이유를 설명한다.

---

## 🦮 1. 자동화가 필요했던 이유

코드는 팀원뿐 아니라 각자의 PC에서 실행하는 Claude Code와 GitHub Actions의 Claude도 작성한다. 팀원 6명과 여러 에이전트가 같은 저장소를 수정하자 두 가지 문제가 생겼다.

- **담당하지 않은 폴더까지 수정했다.** 에이전트가 요청 범위를 넓혀 다른 부서 폴더까지 고치면 해당 부서의 코드와 테스트에 영향을 준다.
- **사람의 리뷰가 AI의 작업 속도를 따라가지 못했다.** 에이전트가 만든 PR은 빠르게 늘지만, 모든 PR을 사람이 직접 승인하면 처리 시간이 길어진다.

목표는 명확했다. **자동 검사로 담당 폴더 밖의 변경을 차단하고, 다른 부서 에이전트가 리뷰하며, 필수 검사를 모두 통과하면 자동으로 병합한다.** 사람은 자동화 규칙을 변경하거나 결과를 최종 확인할 때만 참여한다.

## 🦮 2. GitHub 조작 권한과 Claude 실행 권한 분리

GitHub Actions에서 사용하는 권한을 두 종류로 나눴다. GitHub Environments에 `bot`과 `claude` 환경을 만들고 각각 필요한 인증 정보만 등록했다.

### 🦄 GitHub App 봇 (environment bot)

`ax-company-hq-bot`은 GitHub App으로 만든 봇이다. 브랜치 push, PR 생성과 병합, 이슈 라벨·댓글 작성, 커밋 상태 기록처럼 GitHub 데이터를 변경하는 작업을 맡는다. `bot` 환경에는 이 봇의 인증 정보만 저장했다.

### 🦄 팀원별 Claude 토큰 (environment claude)

GitHub Actions에서 Claude Code를 실행할 때는 팀원 각자의 구독 계정 토큰을 사용한다. Claude는 코드 작성과 다른 부서 PR 리뷰를 맡는다. `claude` 환경에는 팀원 6명의 토큰만 저장했다.

Claude를 실행하는 잡에는 GitHub 쓰기 권한과 셸을 주지 않았다. Claude는 패치와 JSON 형식의 결과만 생성한다. 다음 잡이 결과를 검사한 뒤 GitHub App 봇이 저장소에 반영한다.

### 🦄 인증 정보는 dev 브랜치에서만 사용

두 환경 모두 배포 브랜치를 `dev`로 제한했다. `dev` 브랜치의 워크플로만 인증 정보를 사용할 수 있다. 다른 브랜치에서 워크플로 파일을 수정하더라도 인증 정보에 접근할 수 없다. `main`에는 사람과 에이전트 모두 직접 push하지 않도록 설정했다.

### 🦄 AX_* 변수로 자동화 기능 제어

저장소 변수 `AX_AUTOMATION`, `AX_RELEASE` 등으로 자동화 기능의 활성화 여부를 관리한다. 처음에는 모두 `off`로 두고, 각 단계를 검증한 뒤 하나씩 `on`으로 바꿨다. 현재 `AX_AUTOMATION`은 `on`이고, `main` 릴리스를 허용하는 `AX_RELEASE`는 `off`다.

<img src="/images/blog/ai/24/images1.webp"/>

저장소 Settings → Secrets and variables → Actions의 Variables 탭이다. `AX_AUTOMATION`만 `on`이고 `AX_RELEASE`, `AX_TASKS` 등은 `off`다. 역할별로 쓸 Claude 모델도 `AX_MODEL_*` 변수로 정해 둔다.

## 🦮 3. 팀원별 Claude 토큰 등록

각 팀원은 자신의 Claude 토큰을 `claude` 환경에 등록했다.

1. PowerShell에서 실행한다.

```text
claude setup-token
```

2. 출력된 토큰(`sk-ant-oat...`로 시작)을 임시로 메모장에 복사한다.
3. 두 저장소에 한 번에 등록한다. `<이름>`에는 자신의 영문 식별자를 넣는다. 예: `CLAUDE_TOKEN_TEAM_MEMBER`

```text
foreach ($r in "ax-backend","ax-frontend") { gh secret set CLAUDE_TOKEN_<이름> --repo ax-company-hq/$r --env claude }
```

4. `Paste your secret:`이 두 번 표시되면 각각 토큰을 붙여 넣고 Enter를 누른다.

**끝나면 메모장의 토큰은 지운다.**

팀원별 토큰을 사용하는 이유는 리뷰를 담당한 부서 팀원의 계정으로 Claude를 실행하기 위해서다. 예를 들어 finance 에이전트가 data PR을 리뷰하면 finance 담당자의 토큰을 사용한다. 비용과 사용량이 한 계정에 집중되지 않고 6명에게 분산된다. 팀원마다 하루에 실행할 수 있는 Claude 잡의 최대 횟수도 따로 설정했다.

<img src="/images/blog/ai/24/images2.webp"/>

Settings → Environments에서 `claude` 환경을 연 화면이다. 배포 브랜치는 `dev` 하나만 허용되어 있고, 환경 시크릿에는 팀원 6명의 `CLAUDE_TOKEN_<이름>`이 등록되어 있다. 시크릿 값은 GitHub에서도 다시 볼 수 없다. 다른 팀원의 이름은 가렸다.

## 🦮 4. 로컬에서도 담당 폴더 외 변경 차단

GitHub Actions에서만 변경 범위를 검사하면 push한 뒤에야 문제를 알 수 있다. 로컬 Claude Code가 다른 부서 폴더를 수정하지 못하도록 같은 제한을 로컬에도 적용했다.

ax-backend의 dev를 받은 뒤 설정 파일을 복사한다.

```text
cp .claude/settings.local.example.json .claude/settings.local.json
```

그리고 `"AX_DEPTS"`에 자기 부서 id를 적는다. 쉼표로 구분하고 공백은 넣지 않는다.

| 사람 | AX_DEPTS |
|---|---|
| 팀원 1 | `data,memory` |
| 나 | `finance,safety` |
| 팀원 2 | `hr,orchestrator,agent-template,infra,contracts` |
| 팀원 3 | `planning,dejafix` |
| 팀원 4 | `support,dashboard-api` |
| 팀원 5 | `marketing,shop-api` |

Claude Code 훅은 이 값을 기준으로 파일 쓰기와 push를 제한한다.

- **파일 쓰기:** 담당 부서 폴더와 해당 부서의 메모 폴더만 수정할 수 있다. **`AX_DEPTS`가 없으면 모든 파일 쓰기를 차단한다.**
- **push:** 아래 형식만 허용한다. `dev`·`main` 직접 push, force push, 다른 부서 이름을 사용한 브랜치 push는 차단한다.

```text
git push -u origin <부서>/<기능>
```

로컬과 CI에 같은 규칙을 적용하면 잘못된 변경을 push 전에 확인할 수 있다. 다만 로컬 훅은 셸 명령으로 파일을 수정하는 모든 경우를 감지하지 못한다. 따라서 GitHub Actions에서도 변경 범위를 다시 검사한다.

## 🦮 5. 이슈 생성부터 자동 병합까지의 처리 절차

### 🦄 다른 부서의 작업은 이슈로 요청

에이전트에게 준 첫 번째 규칙은 다음과 같다. **담당 부서 폴더만 수정한다. 다른 부서의 변경이 필요하면 직접 수정하지 않고 `to:<부서>` 요청 이슈를 만든다.**

사람과 에이전트 모두 같은 형식으로 요청한다. 수정 대상, 위치, 적용할 규칙, 제외할 작업을 적고 `to:<부서>` 라벨을 붙인다. 에이전트가 작업 중에 다른 부서의 변경이 필요하다고 판단하면 직접 수정하지 않고 결과에 요청 내용을 포함한다. 봇은 그 내용을 바탕으로 담당 부서 이슈를 만든다.

다른 부서 폴더를 직접 수정하면 담당자가 변경을 확인하지 못할 수 있다. 이슈로 요청하면 담당 부서의 에이전트가 해당 부서의 규칙과 테스트에 따라 작업하며, 요청과 처리 기록도 남는다. 요청에서 다시 다른 요청을 만들 수 있는 횟수는 최대 3회로 제한했다. 부서 간 요청이 계속 생성되는 상황을 막기 위한 설정이다.

<img src="/images/blog/ai/24/images3.webp"/>

아래 실행 결과에 나오는 요청 이슈 #24다. 본문에 요청, 위치, 입력·출력, 규칙, 테스트, 하지 않는 것을 적었다. 작성자가 `to:data` 라벨을 붙이자 봇이 `in-progress`와 재시도 횟수 라벨(`retry-1`)을 달았다. 작성자 이름은 가렸다.

### 🦄 자동 처리 순서

```text
to:<부서> 이슈 (사람 또는 에이전트가 작성)
   → 봇이 상태를 in-progress로 변경
   → 그 부서 Claude가 작성 → 봇이 <부서>/<이슈번호>-<제목>-r<재시도> 브랜치로 PR
   → 다른 부서 에이전트가 리뷰
   → 필수 검사 통과
   → dev에 자동 머지, 이슈 닫힘
```

<img src="/images/blog/ai/24/images4.webp"/>

이슈 #24로 봇이 만든 PR #30이다. 작성자는 `ax-company-hq-bot`, 브랜치는 `data/24-dep-data-02-r1`이다. 본문의 `Closes #24` 덕분에 병합되면 이슈가 함께 닫히고, 작성 부서를 나타내는 `by:data` 라벨이 붙어 있다.

리뷰는 변경된 부서의 결과를 사용하는 부서가 맡는다. 예를 들어 data가 바뀌면 finance가 리뷰한다. finance의 손실 보고서가 data에서 만든 숫자를 사용하기 때문이다. Claude의 리뷰 기준도 미리 정했다. 요구사항 충족 여부, 계약 준수 여부, 리뷰 부서가 사용하는 입출력의 호환성, 테스트가 실제 동작을 검증하는지를 확인한다. **코드 스타일이나 개인 취향은 거절 사유로 사용하지 않는다.**

PR이 열리면 자동 병합을 설정한다. 아래 검사가 모두 통과하면 `dev`에 병합된다.

| 필수 검사 | 확인하는 내용 |
|---|---|
| ci, contracts-compat, automation-tests | 테스트·lint, 계약 하위 호환, 자동화 자체 테스트 |
| folder-guard | 담당 부서 밖의 파일이나 자동화 파일을 수정했는지 |
| test-guard | 기존 테스트를 삭제하거나 축소했는지 |
| dev-health | dev 브랜치의 테스트가 정상적으로 통과하는지 |
| agent-review | 다른 부서 에이전트가 승인했는지 |

자동화 파일(`.github/`, `.claude/`, `CLAUDE.md` 등)을 바꾸려면 사람 code owner의 승인이 필요하다. 에이전트가 검사 규칙을 수정해 자신의 PR을 통과시키는 것을 방지하기 위한 설정이다.

### 🦄 실제 실행 결과

팀원 1이 data 부서에 “영향 분석 숫자 집계 함수를 만들어 달라”는 `to:data` 이슈를 등록했다. 처음 두 번은 토큰 설정과 lint 문제로 실패했다. 팀원 1이 워크플로를 수정한 뒤 다시 실행했고, 세 번째 실행에서 봇이 PR을 만들었다. finance 에이전트는 내 토큰으로 PR을 리뷰하고 승인했다. **PR 생성부터 병합까지 2분 24초가 걸렸고, 그 과정에서 사람이 추가로 버튼을 누르지 않았다.**
