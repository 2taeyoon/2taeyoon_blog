## 🦮 1. 과제 개요

### 🦄 GAIA란?

[GAIA](https://huggingface.co/spaces/gaia-benchmark/leaderboard)는 범용 AI 어시스턴트의 문제 해결 능력을 평가하기 위한 벤치마크입니다.

사람에게는 비교적 간단한 문제처럼 보이지만, AI가 해결하려면 **웹 검색, 파일 분석, 멀티모달 이해, 다단계 추론** 등 여러 능력을 종합적으로 활용해야 합니다.

이번 과제에서는 GAIA Level 1 Validation 세트에 포함된 **20개 문제**를 사용합니다.

문제 유형은 다음과 같습니다.

| 유형 | 예시 |
|---|---|
| 웹·위키 검색 | 특정 가수가 2000~2009년에 발표한 스튜디오 앨범 수 확인 |
| 유튜브 영상 | 영상 속 등장인물이 특정 질문에 답한 내용 확인 |
| 이미지 | 체스판 이미지를 분석해 승리할 수 있는 수 찾기 |
| 음성 | 음성 메모를 듣고 파이 재료 목록 정리 |
| 코드·엑셀 | 첨부된 파이썬 코드의 출력값 확인, 엑셀 매출 합계 계산 |
| 논리 | 연산표에서 교환법칙의 반례 찾기, 거꾸로 작성된 문장 해석 |

### 🦄 채점 방식

과제의 채점은 코스 전용 채점 API를 통해 진행됩니다.

- 코스 전용 채점 API(`agents-course-unit4-scoring.hf.space`)에서 문제를 가져와 답안을 제출합니다.
- 정답은 **Exact Match(완전 일치)** 방식으로 판정합니다.
- 예를 들어 정답이 `"3"`이라면 `"3 albums"`라고 제출해도 오답으로 처리됩니다.
- 제출할 때는 Hugging Face 사용자 이름, 공개된 에이전트 코드 링크, 답안 목록을 전달해야 합니다.

제출 데이터는 다음과 같은 JSON 형식입니다.

```json
{
  "username": "2tyoon",
  "agent_code": "https://huggingface.co/spaces/2tyoon/Final_Assignment_Agent/tree/main",
  "answers": [
    {
      "task_id": "...",
      "submitted_answer": "..."
    }
  ]
}
```

## 🦮 2. 에이전트 설계

### 🦄 전체 구성

이번 과제에 사용한 기술 스택과 주요 설정은 다음과 같습니다.

- **프레임워크**: [smolagents](https://github.com/huggingface/smolagents)의 `CodeAgent`
- **LLM**: Claude
- **모델 연동**: LiteLLM
- **최대 실행 단계**: 15 Steps

LiteLLM을 통해 모델을 연결했기 때문에 환경변수인 `MODEL_ID`만 변경하면 Gemini나 OpenAI 모델로도 교체할 수 있도록 구성했습니다.

`CodeAgent`는 일반적인 Tool Calling Agent처럼 JSON 형식으로 도구를 호출하는 대신, **직접 파이썬 코드를 작성하고 실행하는 방식**으로 문제를 해결합니다.

계산이나 표 처리, 문자열 조작처럼 코드 실행이 유용한 GAIA 문제에 적합한 방식이라고 판단했습니다.

### 🦄 사용한 도구

문제 유형에 따라 필요한 기능을 직접 도구로 구현했습니다.

| 도구 | 역할 |
|---|---|
| `DuckDuckGoSearchTool` | 웹 검색 |
| `VisitWebpageTool` | 웹페이지 본문을 마크다운 형식으로 가져오기 |
| `WikipediaSearchTool` | 위키피디아 검색 |
| `youtube_transcript` | 유튜브 영상 자막 가져오기 |
| `analyze_image` | 비전 모델을 활용한 이미지 분석 및 체스판 판독 |
| `transcribe_audio` | 로컬 Whisper를 이용한 음성 받아쓰기 |
| `read_excel` | 엑셀·CSV 파일의 전체 시트를 표 형태로 읽기 |
| `read_text_file` | 코드 및 텍스트 파일 읽기 |

도구는 smolagents의 `@tool` 데코레이터를 사용하면 간단하게 구현할 수 있습니다.

smolagents는 함수의 Docstring과 타입 힌트를 바탕으로 도구의 기능과 매개변수 정보를 LLM에 전달합니다.

예를 들어 유튜브 자막을 가져오는 도구는 다음과 같이 정의할 수 있습니다.

```python
@tool
def youtube_transcript(url: str) -> str:
    """Fetch the spoken transcript (captions) of a YouTube video.

    Args:
        url: The YouTube video URL.
    """
    ...
```

### 🦄 Exact Match 평가에 맞춘 프롬프트 설계

이번 과제에서 특히 신경 쓴 부분은 **정답을 어떤 형식으로 출력할 것인가**였습니다.

채점 방식이 Exact Match이기 때문에 정답 자체를 찾는 것뿐만 아니라, 채점 서버가 요구하는 형식에 맞춰 답을 제출하는 것도 중요합니다.

이를 위해 시스템 프롬프트에 다음과 같은 출력 규칙을 추가했습니다.

```text
- Call final_answer() with ONLY the answer: no explanation, no "FINAL ANSWER" prefix.
- A number: plain digits, no thousands separators, no $ or % unless asked.
- A string: as few words as possible, no articles, no abbreviations unless asked.
- A list: comma-separated, following any ordering/format the question asks for.
```

여기에 별도의 후처리 단계도 추가했습니다.

에이전트가 반환한 답변이 60자를 초과하거나 줄바꿈 또는 태그가 포함된 경우, LLM을 한 번 더 호출해 **최종 답안만 추출하도록 처리**했습니다.

정답을 찾고도 불필요한 설명 때문에 오답 처리되는 상황을 방지하기 위한 장치입니다.

### 🦄 실행 구조

반복 실행과 제출 과정을 효율적으로 관리하기 위해 `run_local.py`라는 로컬 실행 스크립트를 별도로 만들었습니다.

전체 실행 과정은 다음과 같습니다.

1. 채점 API에서 GAIA 문제 20개를 가져옵니다.
2. 문제를 하나씩 해결하고 결과를 `answers.json`에 캐시합니다.
3. 실패하거나 오답인 문제만 `--only 3 9 11`과 같은 옵션으로 선택해 다시 실행합니다.
4. `--submit` 옵션을 사용해 캐시된 답안을 채점 서버에 한 번에 제출합니다.

이 구조를 적용한 가장 큰 이유는 **문제 20개를 매번 처음부터 다시 실행하지 않아도 되도록 하기 위해서**입니다.

LLM 호출은 시간이 오래 걸리고 API 비용도 발생하기 때문에, 문제별 결과를 저장하고 필요한 문제만 재실행하는 방식이 효율적이었습니다.

## 🦮 3. 트러블슈팅

이번 과제에서 가장 많은 시간을 사용한 부분입니다.

실제 개발 및 실행 과정에서 발생했던 문제와 해결 방법을 순서대로 정리했습니다.

### 🦄 ① Hugging Face 로그인 버튼을 눌러도 빈 페이지만 표시되는 문제

GAIA 리더보드 페이지에서 `Sign in with Hugging Face` 버튼을 눌렀지만, 별다른 반응 없이 빈 페이지만 표시됐습니다.

확인 결과, **해당 리더보드 페이지의 로그인은 과제 제출에 필요하지 않았습니다.**

- 코스 점수는 GAIA 공식 리더보드가 아닌 코스 전용 채점 API에서 계산합니다.
- 채점 API는 Hugging Face username을 입력받는 방식이므로 별도의 로그인 없이 스크립트에서 바로 제출할 수 있습니다.
- 빈 페이지가 발생한 정확한 원인은 확인하지 못했습니다. Space 내부 iframe에서 로그인 팝업을 호출하는 과정에서 브라우저의 서드파티 쿠키 제한에 영향을 받았을 가능성이 있다고 추정했습니다.

결과적으로 리더보드 로그인을 해결하는 데 시간을 더 쓰지 않고, 채점 API를 직접 호출하는 방식으로 진행했습니다.

### 🦄 ② `temperature=0` 파라미터가 지원되지 않는 문제

모델 응답의 재현성을 높이기 위해 `temperature=0`을 설정했지만, 다음과 같은 오류가 발생했습니다.

```text
UnsupportedParamsError: claude-sonnet-5-5 does not support temperature=0.
```

사용 중인 Claude 모델이 해당 파라미터를 지원하지 않는 것이 원인이었습니다.

해결 방법은 간단했습니다. 요청에 포함했던 `temperature=0` 설정을 제거했습니다.

### 🦄 ③ 무료 계정으로 Gradio Space를 생성할 수 없는 문제

코스에서 제공하는 템플릿은 Gradio Space를 복제해 사용하는 방식이었습니다.

하지만 무료 계정으로 Space를 실행하려고 하자 다음과 같은 오류가 발생했습니다.

```text
402 Payment Required
Hosting Gradio and Docker Spaces on free cpu-basic requires a PRO subscription.
```

확인 결과, 당시 무료 계정에서는 Gradio 및 Docker Space를 호스팅할 수 없었습니다.

대신 **무료로 사용할 수 있는 Static Space에 코드를 공개하는 방식**으로 변경했습니다.

- Static Space에 에이전트 코드를 공개합니다.
- 실제 에이전트 실행은 로컬 환경에서 진행합니다.
- 채점 서버에는 공개된 코드 링크와 답안을 제출합니다.

과제 제출에 필요한 것은 공개된 코드 링크였기 때문에 이 방식으로도 충분히 진행할 수 있었습니다.

### 🦄 ④ 첨부파일 404 오류와 이어진 403 오류

이번 과제에는 이미지, MP3 파일 2개, 파이썬 코드, 엑셀 파일 등 첨부파일이 포함된 문제가 총 5개 있었습니다.

그런데 채점 API에서 첨부파일을 가져오는 과정에서 `404 Not Found` 오류가 발생했습니다.

먼저 GAIA 원본 데이터셋인 `gaia-benchmark/GAIA`에 동일한 파일이 존재한다는 점을 확인했습니다.

이에 채점 서버에서 파일을 가져오지 못하면 원본 데이터셋에서 동일한 첨부파일을 다운로드하도록 대체 경로를 추가했습니다.

하지만 이번에는 `403 Forbidden` 오류가 발생했습니다.

원인은 GAIA 데이터셋이 **사용 약관에 동의해야 접근할 수 있는 Gated Dataset**이었기 때문입니다.

데이터셋 페이지에서 사용 약관에 동의한 뒤 다시 실행하자 정상적으로 파일을 가져올 수 있었습니다.

이 과정에서 중요한 점은 데이터셋에서 **첨부파일만 가져왔으며, 정답이 포함된 메타데이터는 사용하지 않았다는 것**입니다.

파일 다운로드 로직은 다음과 같이 구성했습니다.

```python
resp = requests.get(f"{API_URL}/files/{task_id}", timeout=60)

if resp.ok:
    ...
    return path

# 채점 서버에 파일이 없으면 GAIA 데이터셋의 동일한 첨부파일로 대체
return hf_hub_download(
    "gaia-benchmark/GAIA",
    f"2023/validation/{file_name}",
    repo_type="dataset",
    local_dir=FILES_DIR
)
```

### 🦄 ⑤ API 응답 대기 중 10분 타임아웃 발생

문제를 해결하는 과정에서 LLM 응답을 기다리다가 기본 타임아웃인 600초를 초과하는 상황이 발생했습니다.

응답이 오래 걸리는 문제를 무작정 기다리는 대신, 빠르게 실패 처리한 뒤 재시도하도록 설정을 변경했습니다.

```python
timeout=180
num_retries=2
```

기존 600초에서 180초로 타임아웃을 줄이고, 최대 2회 재시도하도록 변경했습니다.

이를 통해 응답이 지연되는 상황에서 불필요하게 대기하는 시간을 줄일 수 있었습니다.

### 🦄 ⑥ 최종 답변 형식이 깨지는 문제

일부 문제에서는 정답을 정확하게 찾았음에도 최종 출력 형식이 잘못되는 상황이 발생했습니다.

대표적인 사례는 두 가지였습니다.

- 정답인 `80GSFC21M0002`를 찾았지만, 설명 문장까지 포함해 전체 내용을 답안으로 제출하는 경우
- 최종 답변 대신 도구 호출 태그인 `<invoke name="final_answer">`가 그대로 출력되는 경우

두 문제 모두 정답 자체보다는 최종 출력 형식에서 발생한 오류였습니다.

앞서 설명한 **답변 추출 후처리 단계**를 추가해 불필요한 설명이나 태그가 포함되지 않도록 처리했습니다.

### 🦄 ⑦ Whisper 실행 중 메모리 부족

음성 파일을 분석하는 과정에서 PC 메모리가 부족해 Whisper 프로세스가 강제 종료되는 문제가 발생했습니다.

처음에는 `small` 모델을 사용했지만, 메모리 사용량을 줄이기 위해 `base` 모델로 변경했습니다.

이번 과제에 포함된 두 음성 파일은 비교적 명확하게 녹음되어 있었기 때문에 모델 크기를 낮춰도 받아쓰기 정확도에는 문제가 없었습니다.

## 🦮 5. 배운 점

이번 과제를 통해 얻은 경험은 크게 네 가지입니다.

1. **에이전트 성능은 모델뿐만 아니라 도구 구성에 크게 좌우됩니다.**  
   유튜브 자막 추출, 음성 받아쓰기, 이미지 분석, 엑셀 파일 처리와 같은 도구가 없다면 성능이 뛰어난 LLM을 사용하더라도 해결하기 어려운 문제가 많았습니다. 에이전트가 다양한 작업을 수행하려면 모델 자체의 성능뿐만 아니라 문제에 적합한 도구를 제공하는 것이 중요하다는 점을 확인했습니다.

2. **Exact Match 평가에서는 답변 형식도 정답만큼 중요합니다.**  
   정답을 정확하게 찾아놓고도 불필요한 설명이나 출력 형식 때문에 오답 처리될 뻔한 사례가 있었습니다. 프롬프트에서 출력 규칙을 명확하게 지정하고, 별도의 후처리 단계까지 추가해 이중으로 대응하는 방식이 효과적이었습니다.

3. **캐싱과 부분 재실행은 에이전트 개발에서 중요합니다.**  
   LLM 에이전트는 실행 시간이 길고 API 비용이 발생하며, 외부 서비스나 모델 상태에 따라 간헐적으로 실패할 수도 있습니다. 문제별 실행 결과를 저장해 두면 전체 과정을 반복하지 않고 실패한 문제만 다시 실행할 수 있어 개발 효율이 크게 높아집니다.

4. **에러 메시지를 정확하게 읽는 것이 문제 해결의 출발점입니다.**  
   이번 과제에서는 `404`, `403`, `402` 오류를 각각 경험했습니다. 각 오류는 파일을 찾을 수 없는 문제, Gated Dataset의 약관 미동의, PRO 구독이 필요한 호스팅 환경이라는 서로 다른 원인을 가리키고 있었습니다. 오류 메시지를 단순히 넘기지 않고 원인을 구분해 접근한 것이 해결에 도움이 됐습니다.
