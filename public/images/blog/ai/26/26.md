## 🦮 AX 솔루션에 장애 분석과 실제 데이터 A2A를 붙인 방법

데모 쇼핑몰(고객사) 쪽에서 부서별 AI 에이전트를 만들고, 팀이 그 레포를 함께 운영하는 방법을 정리했다. 이번에는 그 에이전트들을 **우리가 파는 제품인 AX 솔루션 안으로 옮기는 작업**을 했다. 아침에 팀 채널에 올린 할 일은 세 줄이었다.

```text
1. 깃 자동화 및 loop 설정
2. 장애 분석 시스템은 그대로 두고, AX 솔루션 장애 대응 탭에 현재 장애만 띄우기 (AX 솔루션이 장애 분석 시스템의 데이터를 가져온다)
3. 데모 쇼핑몰 대시보드에 있는 AI 에이전트 전부를 AX 솔루션 탭으로 옮기기
```

하루가 끝났을 때는 여기에 하나가 더 붙어 있었다. 녹화본이나 가짜 데이터 없이, **데모 쇼핑몰의 실제 주문·결제 데이터로 AI끼리 A2A로 일을 주고받고, 그 대화를 화면에서 그대로 보는 것**이다. 이 글은 그 순서대로 정리한다.

| 이름 | 정체 |
|---|---|
| AX 솔루션 | 우리가 만드는 제품. 고객사가 필요한 AI 서비스를 골라 쓰는 화면과 에이전트 서버 |
| 데모 쇼핑몰 | AX 솔루션을 쓰는 고객사 역할의 온라인 서점 (`shop-web`, `shop-api`) |
| 장애 분석 시스템 | Zabbix가 잡은 장애를 AI가 분석하는 시스템. 별도 레포, 별도 팀 |

### 🦄 먼저 알아 두면 좋은 용어

이 글에는 개발 용어가 많이 나온다. 처음 보는 사람도 읽을 수 있게 자주 나오는 것만 먼저 풀어 둔다.

| 용어 | 쉽게 말하면 |
|---|---|
| 에이전트 | 맡은 일을 스스로 처리하는 AI 프로그램. 이 글에서는 "재무 AI", "마케팅 AI"처럼 부서 하나를 맡은 AI |
| A2A (Agent-to-Agent) | AI끼리 직접 일을 부탁하고 결과를 돌려주는 방식. 사람이 중간에서 전달하지 않는다 |
| API | 프로그램끼리 데이터를 주고받는 약속된 창구. "이 주소로 물어보면 이런 모양으로 답해 준다"는 규칙 |
| 레포 (Repository) | 프로젝트의 코드를 모아 두는 저장소 |
| PR (Pull Request) | "내가 고친 코드를 합쳐 주세요"라는 요청. 다른 사람이 확인한 뒤 합친다(머지) |
| 목(Mock) 모드 | 진짜 데이터 대신 미리 만들어 둔 가짜 데이터로 돌리는 모드. 개발할 때 편하지만 실제 문제를 숨길 수 있다 |
| Zabbix | 서버와 PC 상태(CPU, 메모리, 서비스 실행 여부 등)를 감시하다가 이상이 있으면 알려 주는 모니터링 도구 |
| LLM | ChatGPT, Gemini 같은 대형 언어 모델. 에이전트의 "두뇌" 역할 |

## 🦮 1. 화면은 한 곳에만 둔다

### 🦄 같은 화면이 두 곳에 살아 있었다

데모 쇼핑몰 레포에는 쇼핑몰(`shop-web`) 옆에 AI 대시보드(`dashboard-web`)가 있었다. 그런데 이 대시보드 화면 15개는 이미 AX 솔루션에도 특정 시점의 복사본으로 들어와 있었다. 두 곳에 같은 화면이 있으니 버그를 고칠 때마다 "어디를 고쳐야 하지?"가 먼저 나왔다.

그래서 방향을 하나로 정했다. **데모 쇼핑몰에는 고객이 보는 쇼핑몰만 남기고, AI는 전부 AX 솔루션이 관리한다.** 데모 쇼핑몰은 AX 솔루션을 "쓰는" 고객사이지, AI 화면을 따로 가지는 회사가 아니기 때문이다.

```text
  [지금]                                     [바뀐 뒤]
데모 쇼핑몰 ├ shop-web       쇼핑몰         데모 쇼핑몰 └ shop-web  쇼핑몰만
            └ dashboard-web  AI 대시보드    AX 솔루션   └ AI 7개 전부 여기서 관리
```

옮긴 AI는 총괄 · 고객지원 · 재무 · 데이터분석 · 인사 · 마케팅 · 기획개발 7개다. 메뉴도 서비스가 아니라 **AI 기준**으로 바꿨다. 고객이 사는 단위는 서비스지만, 화면에서 "누가 이 일을 하나"를 먼저 보여 주는 게 AI 솔루션답다고 봤다.

```text
총괄
고객지원 AI  ▾  고객 문의 / 클레임·보상 / 리뷰·지식
재무 AI
데이터분석 AI
인사 AI      ▾  인수인계 / 결정 기록
마케팅 AI
기획개발 AI  ▾  요청·기획서 / 개발·배포
──────────
장애 대응 · PC·서버 연결 · AI 대화방 · AI 오피스
```

### 🦄 고객사 계정은 시스템 관리자 하나로

처음 화면에는 인프라·개발·CS·재무처럼 직무별 예시 계정이 있었고, 계정마다 보이는 탭이 달랐다. 그런데 데모를 보는 사람은 결국 계정을 바꿔 가며 탭을 찾아야 했다. 직무별 권한은 고객사가 정할 일이지 데모 화면이 미리 정할 일이 아니라서, **고객사 계정은 시스템 관리자 하나**로 합치고 모든 탭이 보이게 했다.

대신 AX 솔루션 운영팀이 쓰는 관제 센터(`/control`)는 그대로 분리했다. 여기에는 고객사에 연결 키를 발급하는 것 같은 솔루션 운영자용 정보가 있어서, 고객 화면에 섞이면 안 된다.

## 🦮 2. 장애 분석 시스템의 장애를 AX 솔루션 장애 대응 탭에 띄우기

### 🦄 화면이 아니라 데이터를 가져온다

원래 AX 솔루션 장애 대응 탭은 장애 분석 시스템 화면 전체를 iframe으로 띄우고, 상단바 문구는 그 화면의 글자를 0.5초마다 읽어 오고 있었다.

> **iframe**은 웹페이지 안에 다른 웹페이지를 창문처럼 끼워 넣는 기능이다. **DOM**은 브라우저가 화면을 그릴 때 쓰는 구조(어떤 글자가 어떤 상자 안에 있는지)인데, "DOM 긁기"는 그 구조에서 글자를 직접 뽑아 오는 것을 말한다.

이 방식은 장애 분석 시스템 쪽에서 디자인용 이름(CSS 클래스) 하나만 바뀌어도 우리 화면이 **아무 오류 없이 조용히 깨진다.** 다른 팀이 만드는 시스템의 내부 구조에 기대는 셈이다.

그래서 원칙을 정했다. **다른 시스템의 화면(iframe·DOM 긁기)은 가져오지 않는다. 데이터만 받고, 화면은 AX 솔루션이 그린다.** 장애 분석 시스템에는 이미 API 계약 문서(`contracts/api.md`)가 있었고, 거기 적힌 API를 쓰면 상대 팀이 화면을 바꿔도 계약이 바뀌지 않는 한 우리는 안전하다.

> **API 계약**은 "이 주소로 요청하면 이런 형태의 데이터를 준다"를 문서로 약속해 둔 것이다. 두 팀이 이 약속만 지키면 서로의 내부 코드를 몰라도 된다.

| 화면 영역 | 쓰는 API |
|---|---|
| 현재 장애 목록 | `GET /api/incidents?status=problem` (진행 중만) |
| 요약 (진행 중 · 높음 이상 · 정상 호스트 · 오늘 리포트) | `GET /api/dashboard/summary` |
| 언제 · 어디서 장애가 났나 | `GET /api/incidents` (해결 포함 최근 100건) → 호스트 × 시간 분포 |
| 장애 상세 | 장애 상세 API (AI 초동 분석 · 원인 후보 · 변경 계획 · 근거 · 메일 기록) |

> `GET`은 "데이터를 읽기만 하겠다"는 요청 방식이다. 데이터를 바꾸는 요청은 `POST`, `PUT` 같은 다른 방식을 쓴다. **호스트**는 감시 대상이 되는 PC나 서버 한 대를 말한다.

복사해 두었던 장애 분석 시스템 빌드본(약 1.5MB)과 iframe, 글자 긁기 코드는 전부 지웠다.

### 🦄 로그인은 개발 서버가 대신 한다

처음 붙였을 때 화면에 "로그인 정보가 없거나 만료됐습니다"가 떴다. 장애 분석 시스템은 **모든 API에 로그인 토큰(JWT)을 요구**한다.

> **JWT**는 이 출입증을 만드는 대표적인 형식이고, **Bearer 토큰**은 요청을 보낼 때 `Authorization: Bearer <토큰>`처럼 " 토큰을 가진(bear) 사람에게 허락해 달라"는 방식으로 붙이는 것을 말한다. 토큰은 일정 시간이 지나면 만료된다.

가장 쉬운 방법은 토큰을 화면 환경변수(`VITE_INCIDENT_TOKEN`)에 넣는 것인데, Vite는 `VITE_`로 시작하는 값을 브라우저 코드에 그대로 싣는다. 장애 정보를 읽는 출입증이 누구나 볼 수 있는 JS 파일에 들어가는 것이다. 그래서 Vite 개발 서버에 작은 프록시(`frontend/incident-proxy.ts`)를 붙였다.

> **프록시**는 중간에서 요청을 대신 전달해 주는 "대리인"이다. 브라우저는 프록시에게만 말하고, 프록시가 비밀값을 붙여서 진짜 서버에 대신 물어본 뒤 답을 돌려준다. 그래서 비밀값이 브라우저까지 내려가지 않는다.

```text
브라우저 ── /incident-api/* ──▶ AX 솔루션 개발 서버 ── 로그인 + Bearer 토큰 ──▶ 장애 분석 시스템 백엔드
```

- 아이디·비밀번호는 `frontend/.env`의 `INCIDENT_USERNAME`·`INCIDENT_PASSWORD`. `VITE_` 접두사가 없어서 화면 코드에 실리지 않는다
- 장애 대응 탭은 읽기만 하므로 **GET만 넘긴다.** 이 프록시로 장애 분석 시스템의 상태를 바꿀 수 없다
- 토큰이 만료돼 401이 오면 한 번만 다시 로그인한다
- 화면 제목 옆에 "실시간" / "데모 녹화본"을 붙였다. 지금 보는 숫자가 진짜인지 헷갈리지 않게 하려는 표시다
- 502(장애 분석 시스템 백엔드를 못 찾음)와 401(계정 문제)은 원인이 다르니 안내 문구도 따로 보여 준다

> **401, 502** 같은 숫자는 서버가 돌려주는 상태 코드다. 200은 "성공", 401은 "로그인(인증)이 안 됐다", 502는 "중간 서버가 뒤쪽 서버와 연결을 못 했다"는 뜻이다.

### 🦄 장애 분석 시스템 현황 화면의 세 영역을 다시 그리기

장애 분석 시스템 현황 화면에서 운영자가 실제로 먼저 보는 것은 세 가지였다. 그래서 그 세 영역을 같은 데이터로 AX 솔루션에 다시 그렸다.

- **가장 급한 장애**: 진행 중 장애 중 심각도 높은 순, 같으면 최근 시작 순으로 1건
- **요약**: 진행 중 · 높음 이상 · 정상 호스트 · 오늘 리포트
- **언제 · 어디서 장애가 났나**: 최근 24시간 호스트 × 시간 칸. 칸에 마우스를 올리면 호스트·시간·건수 말풍선, 누르면 그 장애로 간다

<img src="/images/blog/ai/26/images2.webp"/>

표는 심각도 순 10건만 보여 주고, 나머지는 "나머지 · 해결된 장애 N건" 접힘 목록으로 내렸다. 진행 중 43건을 한 화면에 다 펼치면 정작 급한 장애가 묻힌다.

장애를 누르면 상세(`/infra/<번호>`)로 간다. AI 초동 분석, 원인 후보와 근거, 변경 계획 미리보기, 메일 발송 기록까지 장애 분석 시스템이 만든 데이터를 그대로 보여 준다.

### 🦄 긴 제목과 오탐은 원래 시스템에서 고쳤다

실데이터를 붙이자 두 가지 문제가 바로 보였다.
첫째, 제목이 너무 길었다. Zabbix 트리거(경보 조건) 이름에는 템플릿 접두사와 서비스 ID가 두 번 들어간다.

```text
전: Windows: "GoogleUpdaterService157.0.8089.0" (Google 업데이터 서비스 (GoogleUpdaterService157.0.8089.0)) is not running ...
후: Google 업데이터 서비스 is not running (startup type automatic)
```

이걸 AX 솔루션에서만 줄이면 두 시스템의 화면 제목이 달라진다. 그래서 장애 분석 시스템에 먼저 제목 정리 함수(`readableTitle()`)를 넣는 PR을 올리고, AX 솔루션은 **같은 규칙**을 그대로 옮겼다. 번역하거나 문장을 새로 만들지 않고 중복만 덜어 내며, 원문은 마우스 오버와 상세 화면에 남긴다.

둘째, 목록 대부분이 Google 업데이터 장애였다. Google 업데이터는 필요할 때만 잠깐 켜지는 서비스라 평소 멈춰 있는 게 정상인데, Windows 템플릿의 제외 목록에 새 이름(버전이 붙은 `GoogleUpdater…Service157…`)이 빠져 있어서 PC마다 2건씩 잡히고 있었다. 화면에서 숨기면 끝나는 문제가 아니라 **수집 단계의 오탐**이라, 제외 정규식을 정리해 Zabbix 담당 팀원에게 요청했다.

> **오탐**은 문제가 아닌데 문제라고 잘못 잡는 것이다. **템플릿**은 Zabbix에서 "Windows PC는 이런 항목들을 감시한다"를 묶어 둔 설정 묶음이다. **정규식**은 글자의 패턴을 표현하는 문법인데, 아래 식은 "이 이름들과 맞는 서비스는 감시에서 빼라"는 뜻이다.

```text
|GoogleUpdater(?:Internal)?Service.*|WSLService|WslInstaller
```

장애 분석 시스템은 운영 Zabbix를 조회만 한다는 원칙이 있어서 서버 설정은 직접 건드리지 않았다. 서버 템플릿은 담당자가 반영했고, 레포의 데모 템플릿 파일도 같은 값으로 맞추는 PR을 올렸다. 레포를 안 맞추면 나중에 템플릿을 다시 가져올 때 오탐이 되살아난다.

같은 날 장애 분석 시스템 현황 목록이 상단 배너와 다른 장애를 보여 주는 문제도 고쳤다. 목록은 최근 시작 50건 안에서만 진행 중 장애를 골라서, 오래전에 시작한 높은 심각도 장애가 목록에서 빠지고 있었다. 진행 중 장애는 배너와 같은 조회(`status=problem`)를 쓰게 바꿨다.

## 🦮 3. 목 모드 없이 쇼핑몰 실제 데이터로 A2A

### 🦄 A2A가 뭔가

A2A(Agent-to-Agent)는 **AI끼리 직접 일을 부탁하고 결과를 돌려주는 방식**이다. 사람이 중간에서 전달하지 않는다. AX 솔루션 백엔드는 기존 에이전트 백엔드를 가져와 서비스 단위로 나눈 구조다. 고객사가 서비스를 골라서 사기 때문에, 에이전트도 서비스마다 하나씩 띄운다.

| 구분 | 내용 |
|---|---|
| `services/` | 서비스 에이전트 (총괄 8000, 고객 문의 8102, 공지·쿠폰 8103, 재무 8105, 데이터 분석 8106, 장애 대응 8107 …) |
| `shared/` | 계약(contracts), 에이전트 틀, 안전 관문(safety), 회사 기억(memory), 화면 중계(dashboard-api), 쇼핑몰 서버(shop-api) |
| 부르는 방법 | `call_agent("finance", req)` 한 줄. skill(에이전트가 할 수 있는 일 목록)을 보고 맡은 서비스로 보낸다 |

규칙이 하나 있다. 업무 로직(`domains/`)끼리는 서로 코드를 직접 가져다 쓰지(import) 않고 **A2A로만** 부른다. 그래야 고객사가 어떤 서비스를 안 샀을 때, 그 호출만 다른 곳으로 돌릴 수 있다.

### 🦄 실제 모드에서 막혀 있던 것

"AI 대화방에서 AI들이 실제 데이터로 일하는 걸 보고 싶다"가 출발점이었다. 그런데 백엔드는 지금까지 목 모드로 돌아서, 목을 끄자 곳곳이 막혔다.

| 막혀 있던 것 | 고친 것 |
|---|---|
| 목 모드가 아니면 A2A가 전부 거부됨 | 켤 때마다 에이전트 토큰 명부(`AX_AGENT_TOKENS`)를 새로 만들어 서로 검증 |
| 총괄이 목 모드가 아니면 501(아직 구현 안 됨) | 7개 부서를 모두 실제 서비스로 부르고, Redis로 쇼핑몰 장애 신호(`shop.degraded`)를 받아 사건을 연다 |
| 안전 관문이 서비스 이름(`coupon`·`dev`)을 몰라 쿠폰·공지를 "등록 안 된 일"로 보류 | 서비스가 보낸 요청을 원래 부서 이름으로도 인정 |
| 화면 API가 목 전용(사용자·주문·집계) | 쇼핑몰 서버(shop-api)와 고객지원 실제 데이터로. 출처 없는 지식·후기는 지어내지 않고 빈 목록 |

> **Redis**는 아주 빠른 메모리 저장소인데, 여기서는 AI들이 신호를 주고받는 통신으로 쓴다. **안전 관문**은 돈이 나가거나 상태가 바뀌는 일을 실행하기 전에 위험도를 매겨, 위험한 일은 사람 승인을 받게 하는 장치다.

### 🦄 장애 워크플로우

장애는 화면 버튼이 아니라 운영자 명령으로 넣는다. 처음에는 AI 대화방에 "장애 시나리오" 버튼이 있었는데, 고객사 화면에 "장애 넣기" 버튼이 있는 것 자체가 말이 안 돼서 지웠다.

```text
bash backend/scripts/shop_fault.sh failure   # 해제: clear, 상태: status
```

그다음은 사람이 손대지 않고 흘러간다.

```text
1. 쇼핑몰 고객이 주문 → 결제가 실제로 실패 (PG_UNAVAILABLE)
      │
2. 쇼핑몰 감시가 "결제 실패가 20초 넘게 이어짐"을 감지
      │   → shop.degraded 신호 (+ 장애가 시작된 시각 since)
      ▼
3. Redis (AI들이 신호를 주고받는 우체통)
      │
4. 총괄 AI가 사건을 열고, 7개 AI에게 A2A로 일을 나눈다
      ├─ 장애 대응 AI   원인 진단
      ├─ 데이터분석 AI  이번 장애 구간의 실패 주문·영향 고객·피해 금액
      ├─ 기획개발 AI    관련 PR 찾기 → 사건에 연결
      ├─ 마케팅 AI      점검 공지 초안 → 쇼핑몰 배너 게시
      ├─ 고객지원 AI    피해 고객 보상 → 마케팅 AI에 다시 A2A로 "쿠폰 지급 부탁해요"
      ├─ 재무 AI        나간 쿠폰을 장부에 기록, 보상 합계 정리
      └─ 인사 AI        사건 기록
      │
5. 돈이 나가거나 상태가 바뀌는 일은 안전 관문이 먼저 등급을 매긴다
      ├─ A등급  바로 실행 (쿠폰 2,000원, 공지 게시, 기록)
      └─ C등급  사람 승인 대기 🚩
      │
6. 원인 배포를 못 찾으면 롤백하지 않고 사람에게 넘긴다 → 사건 상태 "사람 확인 필요"
      │
7. 모든 요청·결과가 공통 로그에 남고, AI 대화방이 그걸 채팅처럼 보여 준다
```

1번에서 고객이 보는 화면은 이렇다. 결제가 실패했고, 금액은 빠져나가지 않았고, 이 주문으로 바로 문의할 수 있다.

<img src="/images/blog/ai/26/images4.webp"/>

6번은 의도한 동작이다. 데모 쇼핑몰에는 배포 기록이 없어서 장애 대응 AI가 "어느 배포 때문인지"를 특정할 수 없다. 원인을 모르는 상태에서 AI가 아무 배포나 되돌리면 장애를 하나 더 만든다. 그래서 확신이 없으면 **멈추고 사람에게 넘기는 쪽**이 맞다. 총괄 탭에서 보면 사건 하나가 단계별로 어느 AI에게 갔고, 어디서 사람에게 넘어갔는지가 한눈에 보인다.

<img src="/images/blog/ai/26/images6.webp"/>

처음 실제로 돌렸을 때 약 25초 뒤 사건이 열렸고, 7개 부서 사이에서 A2A가 113건 오갔다. 데이터분석 AI는 실제 실패 주문을 세서 "실패 8건, 영향 고객 6명, 피해 304,600원"을 냈고, 마케팅 공지 게시, 보상 쿠폰 발급, PR 연결, 사건 기록이 모두 실제로 실행됐다.

## 🦮 4. AI 대화방을 사람이 읽을 수 있게

### 🦄 코드 말 대신 사람 말

A2A 기록을 그대로 보여 주면 이렇게 나온다. `결제 장애 — 서버 오류(5xx) 급증`, `coupon Agent`, `쿠폰 지급: 진행 중`, `undetermined`. 개발자는 읽을 수 있지만 AX 솔루션을 쓰는 고객사 관리자는 못 읽는다. 데이터는 그대로 두고 **보여 주는 말만** 바꿨다.

| 전 | 후 |
|---|---|
| 결제 장애 — 서버 오류(5xx) 급증 | 결제가 서버 오류로 자꾸 실패해요 |
| 일부 미완료 | 사람 확인 필요 |
| coupon Agent · claims Agent | 마케팅 AI · 고객지원 AI |
| 쿠폰 지급: 진행 중 | 쿠폰 지급 부탁해요 / 쿠폰 지급 끝났어요 |
| undetermined | 원인을 특정하지 못함 |
| 장애 #6527c1a7eadd | 결제 장애 · 오후 4:46 |

<img src="/images/blog/ai/26/images5.webp"/>

### 🦄 이번 장애만 계산하도록

테스트를 몇 번 돌리고 나니 데이터분석 AI가 "실패 182건"이라고 했다. 이번 장애의 숫자가 아니었다. 데이터분석 AI는 사건 시각 기준 앞뒤 15분을 셌는데, 그 구간에 앞서 넣은 테스트 장애의 실패 주문까지 들어간 것이다.

해결은 숫자를 세는 쪽이 아니라 **신호를 보내는 쪽**에서 했다. 장애가 언제 시작됐는지 가장 정확히 아는 건 쇼핑몰 감시다. 그래서 `shop.degraded` 계약에 `since`(첫 실패 시각, 선택 필드)를 추가하고, 총괄이 그 시각부터만 영향 분석을 부탁하게 했다. 계약은 추가만 하고 바꾸거나 지우지 않는다는 규칙이 있어서 선택 필드로 넣었고, `since`가 없으면 예전처럼 15분 전부터 계산한다. 테스트 기록을 처음부터 지우는 `run_all.sh reset`도 같이 만들었다.

## 🦮 5. 재무 AI가 메인인 장애

결제 장애에서 재무 AI는 거의 보이지 않았다. 나간 쿠폰을 장부에 적을 뿐, 대화에도 안 끼었다. 재무 AI가 제대로 일하는지 보려면 **재무가 먼저 알아채야 하는 장애**가 필요했다. 그래서 환불 남용 시나리오를 만들었다.

```text
bash backend/scripts/shop_fault.sh refund-abuse
```

```text
쇼핑몰 고객 한 명이 주문 N건을 결제하고 전부 "단순 변심" 취소 신청
  → 고객지원 AI 자동 승인 → 상담원 대기열 처리(사람 토큰)
  → 안전 관문 refund_request로 실제 환불
  → 재무 AI 사후 감사가 "같은 고객 반복 환불"을 찾음
  → finance.anomaly_detected 발행
  → 총괄: 재무 사후 감사 → 고객지원 고객 신호 → 인사 사건 기록
  → "같은 고객이 환불을 반복해요" 사건 방이 생긴다
```

돌려 보니 재무 AI가 장부를 하나도 안 쓰고 있었다. 원인은 재무 서비스가 에이전트 템플릿의 `lifespan`을 덮어써서, **이벤트를 받는 루프 자체가 안 돌고 있던 것**이었다.

### 🦄 왜 덮어써졌나

`lifespan`은 서버에 하나만 둔다. 두 개를 적으면 합쳐지지 않고, 나중에 적은 쪽이 앞의 것을 대신한다.
재무 서비스는 켜질 때 자기 일이 필요했다. 장부 데이터베이스를 연결하다가 재무 에이전트 템플릿이 덮어씌워 졌다. 그 순간 lifespan이 통째로 빠졌다. 안에 있던 신호 루프도 같이 빠졌다.

서버는 오류 없이 켜져서 겉으로는 멀쩡했다. 신호는 하나도 못 받으니 장부에는 아무것도 안 적혔다.

목 모드에서는 가짜 데이터가 채워져 있어서 이 버그가 보이지 않았다. 실제 데이터로 돌렸기 때문에 드러난 버그다. 고친 뒤 `coupon.issued`(쿠폰 발급됨)·`payment.refunded`(환불됨) 신호를 실제로 받아 장부에 적는다.

그리고 장부 기록도 AI 대화방에 남기게 했다. 장부는 돈이 움직인 기록이라, 화면에서 "AI가 무엇을 했는지" 볼 때 빠지면 안 된다. 같은 사건·구간의 영향 분석은 5분 동안 다시 묻지 않게 해서, 쿠폰 4장이 나갈 때 영향 분석 요청이 4번 반복되지 않게 했다.

대화방 구조도 함께 정리했다. 전체 방과 부서 간 직통 방을 없애고 **사건 방 + 안전 관문 방**만 남겼다. 사람이 대화방을 여는 이유는 "이 사건에서 무슨 일이 있었나"이지 "재무와 마케팅이 무슨 얘기를 했나"가 아니기 때문이다. 방 위에는 그 사건에 참여한 AI를 고정해 보여 준다.
