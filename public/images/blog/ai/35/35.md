
## 🦮 AI 에이전트 molagents와 LangGraph로 에이전트 만들기

지난 글에서는 AI 에이전트가 **사고 → 행동 → 관찰** 과정을 반복하며 동작한다는 점과, 이 과정을 프레임워크 없이 직접 구현하려면 상당히 많은 작업이 필요하다는 점을 살펴봤습니다.

이번 글에서는 이러한 반복 작업을 대신 처리해 주는 **AI 에이전트 프레임워크** 두 가지를 알아보겠습니다.

- **smolagents:** Hugging Face에서 개발한 경량 에이전트 프레임워크입니다. 모델이 코드를 생성해 도구를 호출하는 방식이 특징입니다.
- **LangGraph:** LangChain 팀에서 개발한 프레임워크입니다. 개발자가 그래프를 구성해 에이전트의 실행 흐름을 직접 설계할 수 있습니다.

강의 예제 중에는 현재 이름이 변경되었거나 최신 버전에서 사용하지 않는 코드도 있어, 관련 내용을 최신 문서 기준으로 정리했습니다.

먼저 두 프레임워크의 차이를 한 문장으로 요약하면 다음과 같습니다.

> smolagents는 모델에게 자유도를 부여하고, LangGraph는 개발자에게 실행 흐름에 대한 통제권을 부여합니다.

---

## 🦮 1. smolagents: 코드로 행동하는 경량 에이전트 프레임워크

`smolagents`는 Hugging Face에서 개발한 가벼운 AI 에이전트 라이브러리입니다. 핵심 코드가 약 1,000줄 수준일 정도로 구조가 단순해 내부 동작을 이해하기 쉽다는 특징이 있습니다.

| 특징 | 설명 |
|---|---|
| 단순한 구조 | 불필요한 추상화가 적어 내부 동작을 파악하기 쉽습니다. |
| 다양한 모델 지원 | Hugging Face 추론 API, OpenAI 호환 API, 로컬 모델 등을 연결할 수 있습니다. |
| 코드 중심 실행 | 모델이 Python 코드로 행동을 표현하므로 별도의 JSON 파싱 과정이 줄어듭니다. |
| Hugging Face Hub 연동 | 직접 만든 도구와 에이전트를 Hub에 공유하거나 불러올 수 있습니다. |

빠르게 프로토타입을 만들거나 비교적 단순한 작업 흐름을 가진 에이전트를 구현할 때 적합합니다.

### 🦄 설치하기

다음 명령어로 설치할 수 있습니다.

```bash
pip install "smolagents[toolkit]"
```

`[toolkit]` 옵션을 추가하면 웹 검색 등 다양한 기본 도구를 함께 사용할 수 있습니다.

### 🦄 두 가지 에이전트: CodeAgent와 ToolCallingAgent

smolagents는 크게 두 가지 방식으로 에이전트를 구성할 수 있습니다.

| 구분 | CodeAgent | ToolCallingAgent |
|---|---|---|
| 행동 표현 | Python 코드 | JSON 형태의 도구 호출 |
| 특징 | 반복문, 변수, 여러 도구의 조합 등을 코드로 표현합니다. | 모델 제공사의 함수 호출 기능을 활용합니다. |
| 적합한 상황 | 여러 단계의 작업이나 복잡한 도구 조합 | 비교적 단순한 도구 호출 |

강의에서는 CodeAgent가 전반적으로 유연한 작업 수행에 유리하다고 설명합니다.

그 이유는 모델이 학습 과정에서 다양한 코드를 접했기 때문에 코드 형태로 행동을 표현하는 데 익숙하고, 도구 실행 결과를 변수에 저장한 뒤 다음 작업에서 재사용할 수 있기 때문입니다.

### 🦄 첫 번째 CodeAgent 만들기

다음은 DuckDuckGo 검색 도구를 연결해 간단한 에이전트를 만드는 예제입니다.

```python
from smolagents import CodeAgent, DuckDuckGoSearchTool, InferenceClientModel

agent = CodeAgent(
    tools=[DuckDuckGoSearchTool()],
    model=InferenceClientModel(),
)

agent.run("파티에 어울리는 신나는 노래를 추천해 줘")
```

에이전트가 실행되면 다음과 같은 과정이 반복됩니다.

1. 지금까지의 실행 기록과 대화 내용을 정리해 모델에 전달합니다.
2. 모델이 다음에 수행할 작업을 Python 코드로 생성합니다.
3. smolagents가 생성된 코드를 실행합니다.
4. 실행 결과를 기록에 추가하고 다음 단계로 넘어갑니다.

지난 글에서 직접 구현했던 **생성 중단 → 파싱 → 실행 → 결과 추가** 과정을 라이브러리가 자동으로 처리하는 것입니다.

### 🦄 다양한 모델 연결하기

smolagents에서는 여러 모델 연결 클래스를 제공하기 때문에 사용 환경에 맞는 모델을 선택할 수 있습니다.

| 클래스 | 연결 대상 |
|---|---|
| `InferenceClientModel` | Hugging Face Inference Providers |
| `OpenAIModel` | OpenAI 및 OpenAI 호환 API |
| `LiteLLMModel` | LiteLLM을 통해 연결할 수 있는 다양한 모델 |
| `TransformersModel` | 로컬 환경에서 직접 실행하는 Transformers 모델 |

강의 자료에 등장하는 `OpenAIServerModel`, `AzureOpenAIServerModel` 등은 최신 문서에서 `OpenAIModel`, `AzureOpenAIModel`이라는 이름으로 정리되어 있습니다.

### 🦄 코드 실행 보안: 허용된 모듈만 가져오기

CodeAgent는 모델이 생성한 코드를 실제로 실행합니다.

따라서 임의의 Python 모듈을 제한 없이 가져올 수 있도록 두는 것은 위험할 수 있습니다. smolagents는 기본적으로 허용된 모듈만 import할 수 있도록 제한하며, 추가로 필요한 모듈은 명시적으로 허용해야 합니다.

```python
agent = CodeAgent(
    tools=[],
    model=InferenceClientModel(),
    additional_authorized_imports=["datetime"],
)
```

위 예제에서는 `datetime` 모듈을 추가로 사용할 수 있도록 설정했습니다.

코드 실행 권한은 보안과 직결되므로 실제 환경에서는 필요한 모듈만 최소한으로 허용하는 것이 좋습니다.

## 🦮 2. smolagents의 도구(Tool) 만들기

에이전트가 사용할 도구를 만들려면 몇 가지 정보가 필요합니다.

- **이름(Name):** 도구를 식별하는 이름입니다.
- **설명(Description):** 도구가 어떤 작업을 수행하는지 설명합니다.
- **입력값(Inputs):** 전달받을 인자의 이름과 자료형, 설명입니다.
- **출력 타입(Output Type):** 도구가 반환하는 데이터의 자료형입니다.

에이전트는 이러한 정보를 바탕으로 어떤 상황에서 어떤 도구를 사용할지 판단합니다.

### 🦄 방법 1: @tool 데코레이터 사용하기

간단한 도구라면 Python 함수에 `@tool` 데코레이터를 추가하는 것만으로 구현할 수 있습니다.

```python
from smolagents import tool

@tool
def suggest_menu(occasion: str) -> str:
    """행사 종류에 맞는 메뉴를 추천합니다.

    Args:
        occasion: 행사 종류. casual, formal, superhero 중 하나입니다.
    """
    menus = {
        "casual": "피자와 간식",
        "formal": "코스 요리와 와인",
        "superhero": "고열량 뷔페",
    }
    return menus.get(occasion, "셰프 추천 메뉴")
```

여기서 중요한 부분은 Docstring입니다.

`occasion`에 어떤 값이 들어올 수 있는지 구체적으로 작성하면 모델이 잘못된 인자를 전달할 가능성을 줄일 수 있습니다.

**도구의 기능뿐 아니라 입력값의 조건까지 명확하게 설명하는 것이 중요합니다.**

### 🦄 방법 2: Tool 클래스 상속하기

입력 구조가 복잡하거나 내부적으로 상태를 관리해야 하는 도구라면 `Tool` 클래스를 상속하는 방식으로 구현할 수 있습니다.

이 방식에서는 다음과 같은 속성을 정의해야 합니다.

- `name`: 도구 이름
- `description`: 도구 설명
- `inputs`: 입력값의 이름, 자료형, 설명
- `output_type`: 반환값의 자료형
- `forward`: 실제 도구 동작을 구현하는 메서드

간단한 함수로 구현하기 어려운 도구를 만들 때 활용할 수 있습니다.

### 🦄 smolagents에서 제공하는 기본 도구

smolagents는 직접 도구를 구현하지 않아도 사용할 수 있도록 여러 기본 도구를 제공합니다.

| 분류 | 도구 |
|---|---|
| 웹 검색 | `DuckDuckGoSearchTool`, `WebSearchTool`, `GoogleSearchTool`, `ApiWebSearchTool`, `WikipediaSearchTool` |
| 웹페이지 읽기 | `VisitWebpageTool` |
| 코드 실행 | `PythonInterpreterTool` |
| 사용자 입력 | `UserInputTool` |
| 최종 답변 | `FinalAnswerTool` |

필요한 도구를 선택해 에이전트에 등록하면 별도의 구현 없이 기능을 확장할 수 있습니다.

### 🦄 MCP 서버의 도구 연결하기

최근에는 필요한 도구를 직접 개발하는 것뿐 아니라, **MCP(Model Context Protocol) 서버에 등록된 도구를 가져와 사용하는 방식**도 널리 활용되고 있습니다.

smolagents 역시 MCP를 지원합니다.

먼저 MCP 기능을 포함해 설치합니다.

```bash
pip install "smolagents[mcp]"
```

다음은 MCP 서버에서 제공하는 도구를 가져와 에이전트에 연결하는 예제입니다.

```python
from smolagents import CodeAgent, InferenceClientModel, ToolCollection

with ToolCollection.from_mcp(server_parameters, trust_remote_code=True) as tool_collection:
    agent = CodeAgent(
        tools=[*tool_collection.tools],
        model=InferenceClientModel(),
        add_base_tools=True,
    )

    agent.run("...")
```

여기서 `trust_remote_code=True`는 외부 서버에서 제공하는 코드를 신뢰하고 실행하겠다는 의미입니다.

따라서 신뢰할 수 있는 MCP 서버인지 확인한 후 사용해야 합니다.

강의에서는 LangChain 도구나 Hugging Face Space를 도구로 가져오는 방법도 소개하지만, 이번 글에서는 MCP를 활용한 연결 방식에 집중하겠습니다.

## 🦮 3. smolagents로 만드는 응용 에이전트

기본적인 에이전트를 만들었다면 이제 여러 도구와 에이전트를 조합해 조금 더 복잡한 시스템을 구현할 수 있습니다.

### 🦄 에이전틱 RAG(Agentic RAG)

일반적인 RAG와 에이전틱 RAG의 가장 큰 차이는 검색 과정을 누가 결정하느냐에 있습니다.

일반적인 RAG는 사용자의 질문이 들어오면 정해진 검색 과정을 거쳐 관련 정보를 가져오고 답변을 생성합니다.

반면 에이전틱 RAG는 **검색을 언제, 어떤 방식으로 수행할지 에이전트가 직접 판단합니다.**

예를 들면 다음과 같습니다.

- 검색어가 적절하지 않다고 판단하면 검색어를 수정해 다시 검색합니다.
- 검색 결과가 부족하면 추가 검색을 진행합니다.
- 여러 검색 결과를 비교하고 질문과 관련이 있는지 검토합니다.
- 충분한 정보를 확보했다고 판단하면 최종 답변을 생성합니다.

웹 검색 도구를 연결하면 웹 기반 RAG를 구현할 수 있고, 사내 문서를 검색하는 도구를 직접 만들어 연결하면 사내 지식 검색 에이전트로 확장할 수 있습니다.

### 🦄 멀티 에이전트(Multi-Agent)

하나의 에이전트에 모든 도구를 등록하는 대신, 각 에이전트에 역할을 나누어 부여하는 방식도 있습니다.

이때 **관리자 에이전트(Manager Agent)**가 전체 작업을 조율하고, 하위 에이전트(Managed Agent)에게 적절한 작업을 전달합니다.

예를 들어 웹 검색을 담당하는 에이전트와 문서 분석을 담당하는 에이전트를 각각 만들 수 있습니다.

```python
web_agent = CodeAgent(
    tools=[DuckDuckGoSearchTool(), VisitWebpageTool()],
    model=model,
    name="web_agent",
    description="웹에서 정보를 검색하고 웹페이지를 읽습니다",
    max_steps=10,
)

manager_agent = CodeAgent(
    tools=[],
    model=model,
    managed_agents=[web_agent],
    planning_interval=5,
)
```

여기서 중요한 것은 하위 에이전트의 `name`과 `description`입니다.

관리자 에이전트는 이 정보를 바탕으로 어떤 작업을 누구에게 맡길지 판단하기 때문에, 각 에이전트의 역할을 구체적으로 정의해야 합니다.

또한 에이전트마다 실행 기록과 메모리가 구분되므로 각 에이전트가 담당하는 작업의 맥락을 분리해 관리할 수 있습니다.

다만 메모리가 분리된다고 해서 항상 토큰 비용이 줄어드는 것은 아닙니다. 실제 비용은 에이전트 간 전달되는 정보와 전체 호출 횟수에 따라 달라집니다.

### 🦄 이미지와 함께 에이전트 실행하기

비전(Vision) 기능을 지원하는 모델을 연결하면 텍스트뿐 아니라 이미지도 입력으로 전달할 수 있습니다.

예를 들어 이미지 분석 작업을 다음과 같이 요청할 수 있습니다.

```python
agent.run("이 사진 속 인물이 누구인지 확인해 줘", images=images)
```

이미지 입력을 지원하는 모델을 사용하면 이미지에 포함된 객체나 장면 등을 분석하는 작업으로 확장할 수 있습니다.

### 🦄 에이전트 실행 기록 추적하기

에이전트가 어떤 순서로 작업을 수행했는지 확인하려면 실행 기록을 추적할 수 있는 도구가 필요합니다.

강의에서는 OpenTelemetry 기반 계측과 Langfuse를 연결해 에이전트의 실행 과정을 확인하는 방법을 소개합니다.

이를 활용하면 다음과 같은 정보를 추적할 수 있습니다.

- 에이전트가 수행한 작업 순서
- LLM 호출 기록
- 도구 호출 내역
- 각 단계의 실행 결과
- 실행 시간과 토큰 사용량

이러한 추적 기능은 에이전트의 오류를 분석하고 성능을 개선할 때 유용합니다.

## 🦮 4. LangGraph: 에이전트의 실행 흐름을 직접 설계하는 프레임워크

### 🦄 smolagents와 LangGraph의 차이

smolagents의 CodeAgent는 모델이 필요에 따라 여러 도구를 조합하고, 실행할 코드를 직접 생성하는 방식입니다.

자유도가 높은 대신 매번 동일한 순서로 작업이 진행된다는 보장은 없습니다.

반면 LangGraph는 개발자가 에이전트의 실행 단계를 그래프로 구성합니다.

**어떤 작업을 먼저 수행하고, 어떤 조건에서 다음 단계로 이동하며, 어디에서 작업을 종료할지 개발자가 직접 설계합니다.**

따라서 다음과 같은 작업에서 LangGraph가 유용합니다.

- 여러 단계를 정해진 순서와 조건에 따라 처리해야 하는 경우
- 단계마다 데이터를 전달하고 상태(State)를 관리해야 하는 경우
- 규칙 기반 로직과 LLM의 판단을 함께 사용해야 하는 경우
- 작업 중간에 사람의 확인이나 승인이 필요한 경우

단순히 `if` 문으로 구현하면 되지 않을까 생각할 수도 있습니다.

하지만 LangGraph는 상태 관리, 실행 흐름 시각화, 실행 기록 관리, 사람의 개입(Human-in-the-loop) 등을 구조적으로 처리할 수 있다는 장점이 있습니다.

참고로 LangGraph는 LangChain과 함께 사용하는 경우가 많지만, LangChain에 종속되지 않으며 독립적으로 사용할 수도 있습니다.

### 🦄 LangGraph의 핵심 구성 요소 네 가지

LangGraph를 이해하려면 먼저 네 가지 핵심 개념을 알아야 합니다.

| 구성 요소 | 역할 |
|---|---|
| State | 그래프 전체에서 공유하고 전달하는 데이터입니다. 개발자가 직접 정의합니다. |
| Node | 실제 작업을 수행하는 Python 함수입니다. State를 입력받아 변경할 데이터를 반환합니다. |
| Edge | 노드와 노드를 연결하는 요소입니다. 일반 엣지와 조건에 따라 경로가 달라지는 조건부 엣지가 있습니다. |
| StateGraph | State, Node, Edge를 구성하는 그래프입니다. `compile()`을 호출하면 실행할 수 있습니다. |

각 요소가 서로 연결되면서 하나의 작업 흐름을 구성합니다.

### 🦄 가장 간단한 LangGraph 만들어 보기

먼저 다음 명령어로 설치합니다.

```bash
pip install -U langgraph
```

이제 세 개의 노드를 연결하는 간단한 그래프를 만들어 보겠습니다.

```python
import random
from typing import Literal
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END


class State(TypedDict):
    graph_state: str


def node_1(state: State):
    return {"graph_state": state["graph_state"] + " 저는"}


def node_2(state: State):
    return {"graph_state": state["graph_state"] + " 행복해요!"}


def node_3(state: State):
    return {"graph_state": state["graph_state"] + " 슬퍼요!"}


def decide_mood(state: State) -> Literal["node_2", "node_3"]:
    # 일반적으로 State의 값을 바탕으로 다음 노드를 결정합니다.
    # 여기서는 이해를 위해 50% 확률로 선택합니다.
    return "node_2" if random.random() < 0.5 else "node_3"


builder = StateGraph(State)

builder.add_node("node_1", node_1)
builder.add_node("node_2", node_2)
builder.add_node("node_3", node_3)

builder.add_edge(START, "node_1")
builder.add_conditional_edges("node_1", decide_mood)

builder.add_edge("node_2", END)
builder.add_edge("node_3", END)

graph = builder.compile()

graph.invoke({"graph_state": "안녕하세요."})
```

이 코드의 실행 흐름은 다음과 같습니다.

1. `START`에서 그래프가 시작됩니다.
2. `node_1`이 실행되어 기존 문장에 "저는"을 추가합니다.
3. `decide_mood` 함수가 다음에 실행할 노드를 결정합니다.
4. 결과에 따라 `node_2` 또는 `node_3`으로 이동합니다.
5. 마지막 노드가 실행되면 `END`에 도달해 종료됩니다.

여기서 `add_conditional_edges()`는 조건부 엣지를 생성하는 함수입니다.

`decide_mood`가 반환하는 노드 이름에 따라 실행 경로가 달라지는 구조입니다.

## 🦮 5. LangGraph 예제 1: 이메일 분류 그래프

강의에서 소개하는 첫 번째 예제는 집사 Alfred가 이메일을 자동으로 분류하는 시스템입니다.

이 예제는 외부 도구를 호출하지 않고 정해진 작업 흐름을 수행하므로 엄밀히 말하면 완전한 에이전트라기보다는 LLM을 활용한 워크플로에 가깝습니다.

하지만 LangGraph의 노드와 조건부 엣지가 어떻게 동작하는지 이해하기에 좋은 예제입니다.

### 🦄 이메일 처리 흐름

전체 작업은 다음과 같이 구성됩니다.

1. **`read_email`:** 이메일 내용을 읽습니다.
2. **`classify_email`:** LLM이 이메일이 스팸인지 판단하고 종류를 분류합니다.
3. **조건 분기:** 스팸이면 `handle_spam`으로, 정상 이메일이면 `draft_response`로 이동합니다.
4. **`draft_response`:** 정상 이메일에 대한 답장 초안을 작성합니다.
5. **`notify_mr_hugg`:** 이메일 처리 결과를 주인에게 알립니다.

스팸 여부에 따라 실행 경로가 달라지는 부분은 조건부 엣지로 구현합니다.

```python
def route_email(state: EmailState) -> str:
    return "spam" if state["is_spam"] else "legitimate"


email_graph.add_conditional_edges(
    "classify_email",
    route_email,
    {
        "spam": "handle_spam",
        "legitimate": "draft_response",
    },
)
```

여기서 `route_email` 함수가 반환하는 값은 세 번째 인자로 전달한 딕셔너리의 키와 정확하게 일치해야 합니다.

### 🦄 개선 사항: LLM 응답을 구조화된 데이터로 받기

강의 예제에서는 LLM의 응답에 `"spam"`이라는 단어가 포함되어 있는지를 문자열로 검사해 스팸 여부를 판단합니다.

하지만 이런 방식은 응답 문장이 조금만 달라져도 잘못된 결과를 만들 수 있습니다.

예를 들어 모델이 "이 메일은 스팸이 아닙니다"라고 답했는데 문자열에 `spam`이 포함되어 있다는 이유로 스팸으로 분류할 수도 있습니다.

이러한 문제를 줄이기 위해 **구조화된 출력(Structured Output)**을 사용할 수 있습니다.

구조화된 출력은 모델이 미리 정의한 데이터 형식에 맞춰 결과를 반환하도록 하는 방식입니다.

다음은 Pydantic을 활용한 예제입니다.

```python
from pydantic import BaseModel
from langchain.chat_models import init_chat_model


class EmailClassification(BaseModel):
    is_spam: bool
    spam_reason: str | None
    email_category: str | None


model = init_chat_model("anthropic:claude-sonnet-5-5", temperature=0)
classifier = model.with_structured_output(EmailClassification)


def classify_email(state: EmailState):
    email = state["email"]

    result = classifier.invoke(
        f"다음 메일이 스팸인지 판단하고, 스팸이 아니라면 종류를 분류하세요.\n"
        f"보낸 사람: {email['sender']}\n"
        f"제목: {email['subject']}\n"
        f"본문: {email['body']}"
    )

    return result.model_dump()
```

이제 문자열을 직접 검사할 필요 없이 다음과 같은 필드로 결과를 받을 수 있습니다.

- `is_spam`: 스팸 여부
- `spam_reason`: 스팸으로 판단한 이유
- `email_category`: 이메일 종류

이처럼 처음부터 정해진 데이터 구조로 결과를 받으면 이후 분기 처리와 데이터 관리가 훨씬 수월해집니다.

## 🦮 6. LangGraph 예제 2: 문서 분석 에이전트

두 번째 예제는 실제로 도구를 사용하는 AI 에이전트입니다.

문서 이미지에서 텍스트를 추출하는 도구와 나눗셈을 수행하는 도구를 연결하고, 사용자의 질문에 답하도록 구성합니다.

전체적인 동작 방식은 이전 글에서 살펴본 ReAct 구조와 같습니다.

**사고 → 행동 → 관찰 → 재추론**

### 🦄 State: 메시지 기록 관리하기

먼저 에이전트의 상태를 정의합니다.

```python
from typing import Annotated, Optional
from typing_extensions import TypedDict
from langchain_core.messages import AnyMessage
from langgraph.graph.message import add_messages


class AgentState(TypedDict):
    input_file: Optional[str]
    messages: Annotated[list[AnyMessage], add_messages]
```

여기서 중요한 부분은 `add_messages`입니다.

일반적으로 State에 새로운 값을 반환하면 기존 값이 교체될 수 있지만, `add_messages`를 사용하면 새로운 메시지를 기존 메시지 목록 뒤에 추가합니다.

즉, 에이전트가 작업을 수행하면서 이전 대화 기록을 계속 유지할 수 있습니다.

### 🦄 그래프 구성: Assistant ↔ Tools 반복

이제 LLM과 도구를 연결해 실제 에이전트의 실행 흐름을 구성합니다.

```python
from langgraph.graph import START, StateGraph
from langgraph.prebuilt import ToolNode, tools_condition


tools = [divide, extract_text]

llm_with_tools = model.bind_tools(
    tools,
    parallel_tool_calls=False
)


def assistant(state: AgentState):
    return {
        "messages": [
            llm_with_tools.invoke(state["messages"])
        ]
    }


builder = StateGraph(AgentState)

builder.add_node("assistant", assistant)
builder.add_node("tools", ToolNode(tools))

builder.add_edge(START, "assistant")
builder.add_conditional_edges("assistant", tools_condition)
builder.add_edge("tools", "assistant")

react_graph = builder.compile()
```

여기서는 두 가지 연결이 핵심입니다.

- **`tools_condition`:** 모델의 마지막 메시지에 도구 호출이 있으면 `tools` 노드로 이동하고, 도구 호출이 없다면 작업을 종료합니다.
- **`tools` → `assistant`:** 도구 실행이 끝나면 결과를 다시 Assistant에 전달합니다.

이 두 연결을 통해 **사고 → 행동 → 관찰**이라는 반복 구조가 만들어집니다.

### 🦄 개선 사항: 간단한 ReAct 에이전트는 create_agent로 구현하기

위 예제처럼 그래프를 직접 구성하면 각 단계의 실행 흐름을 세밀하게 제어할 수 있습니다.

하지만 단순히 도구를 사용하는 ReAct 에이전트만 필요하다면 LangChain v1에서 제공하는 `create_agent`를 활용하는 방법도 있습니다.

기존 강의 자료에서 자주 등장하는 `langgraph.prebuilt.create_react_agent`는 LangGraph v1에서 Deprecated 처리되었으며, 현재는 LangChain의 `create_agent`를 사용하는 방식으로 대체되었습니다.

```python
from langchain.agents import create_agent


agent = create_agent(
    model="anthropic:claude-sonnet-5-5",
    tools=[divide, extract_text],
    system_prompt="당신은 문서를 분석하고 계산을 돕는 집사 Alfred입니다.",
)


agent.invoke({
    "messages": [
        {
            "role": "user",
            "content": "6790을 5로 나눠 줘"
        }
    ]
})
```

기존 방식에서 사용하던 `prompt` 인자도 `system_prompt`라는 이름으로 변경되었습니다.

정리하면, 실행 흐름을 직접 제어해야 한다면 LangGraph로 그래프를 구성하고, 일반적인 도구 호출 에이전트가 필요하다면 `create_agent`를 활용할 수 있습니다.

## 🦮 7. 어떤 프레임워크를 선택해야 할까?

지금까지 살펴본 smolagents와 LangGraph는 모두 AI 에이전트를 구현하기 위한 프레임워크이지만, 접근 방식에는 차이가 있습니다.

| 비교 항목 | smolagents | LangGraph |
|---|---|---|
| 핵심 방식 | 모델이 코드를 생성해 작업 수행 | 개발자가 그래프로 실행 흐름 설계 |
| 자유도 | 높음 | 상대적으로 낮음 |
| 적합한 작업 | 빠른 실험, 검색 및 조사, 유연한 작업 | 정해진 업무 절차, 복잡한 분기, 사람의 승인 |
| 상태 관리 | 에이전트 메모리 중심 | 개발자가 정의한 State 중심 |
| 학습 난이도 | 비교적 낮음 | State, Node, Edge 등의 개념을 먼저 이해해야 함 |

결국 어떤 프레임워크를 선택할지는 에이전트에게 어느 정도의 자율성을 부여할 것인지에 따라 달라집니다.

- **smolagents:** 다음에 무엇을 할지 모델이 스스로 판단해도 되는 작업에 적합합니다.
- **LangGraph:** 반드시 정해진 순서와 규칙에 따라 처리해야 하는 작업에 적합합니다.

예를 들어 웹 검색이나 자료 조사처럼 상황에 따라 실행 과정이 달라지는 작업이라면 smolagents가 유용할 수 있습니다.

반면 기업의 업무 자동화처럼 데이터 검증, 승인, 실행, 결과 확인 등의 절차가 정해져 있다면 LangGraph가 더 적합할 수 있습니다.

강의에서는 LlamaIndex도 함께 다루지만, 이번 글에서는 동작 방식과 설계 철학이 뚜렷하게 다른 두 프레임워크에 집중했습니다.

## 🦮 마치며

두 프레임워크를 직접 살펴보니 결국 공통점이 하나 있었습니다.

바로 지난 글에서 직접 구현했던 **사고 → 행동 → 관찰이라는 반복 구조를 보다 쉽게 구현하고 관리하도록 도와준다는 점**입니다.

다만 두 프레임워크는 실행 흐름을 제어하는 방식이 다릅니다.

smolagents는 모델이 상황에 맞춰 코드를 생성하고 도구를 조합하도록 높은 자유도를 제공합니다.

반면 LangGraph는 개발자가 전체 실행 과정을 그래프로 설계하고, 각 단계의 상태와 실행 조건을 직접 관리할 수 있도록 합니다.

따라서 어느 한쪽이 무조건 더 좋은 프레임워크라기보다는, 만들려는 서비스의 특성과 요구사항에 맞춰 선택하는 것이 중요합니다.

또한 강의 자료는 개념을 이해하기에는 충분하지만, 일부 코드와 API는 최신 버전과 차이가 있습니다. 실제로 따라 해 볼 때는 공식 문서를 통해 클래스와 함수 이름, 사용 방법을 한 번 더 확인하는 것이 좋겠습니다.

다음 학습에서는 이러한 프레임워크를 활용해 실제 AI 에이전트를 어떻게 설계하고 구현할 수 있는지 더 깊이 살펴보겠습니다.
