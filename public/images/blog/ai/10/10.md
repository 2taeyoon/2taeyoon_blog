## 🦮 Cursor 지침, .cursor 폴더는 어떻게 구성해야 할까?

Cursor Agent를 오래 사용하다 보면 같은 말을 반복하게 됩니다.

“이 프로젝트는 일반 CSS만 사용해 주세요.”  
“API를 수정했으면 테스트도 실행해 주세요.”  
“생성 파일은 직접 수정하지 마세요.”

이런 반복 지시를 매번 프롬프트에 적는 대신, Cursor의 `Rules`, `AGENTS.md`, `Skills`, `Subagents`, `Hooks`로 나누어 저장할 수 있습니다.

이 글은 2026년 8월 Cursor 공식 문서를 기준으로, 무엇을 어디에 작성해야 하는지와 실제 프로젝트에 맞게 커스텀하는 방법을 정리한 글입니다.

## 🦮 1. .cursor 전체가 설정 파일은 아니다

`skills-cursor`, `projects`, `에이전트 실행 기록`, `MCP 관련 메타데이터`처럼 여러 파일이 보일 수 있습니다. 하지만 이 파일들은 모두 사용자가 복사해 배포해야 하는 프로젝트 지침이 아닙니다.

특히 아래 항목은 직접 만든 템플릿처럼 취급하지 않는 편이 안전합니다.

1. <strong>skills-cursor</strong>  
   Cursor가 제공하고 관리하는 내장 스킬 영역입니다. 내용을 참고할 수는 있어도 이 폴더를 직접 수정하거나 프로젝트에 복사하는 방식은 피합니다.

2. <strong>프로젝트별 실행 기록과 대화 기록</strong>  
   프롬프트, 파일 경로, 터미널 내용 등 개인 정보나 프로젝트 정보가 포함될 수 있습니다. Git에 올리거나 블로그 예제로 공개하면 안 됩니다.

3. <strong>MCP 서버 메타데이터와 임시 상태</strong>  
   Cursor가 도구를 연결하고 실행하기 위해 관리하는 내부 데이터일 수 있습니다. 공식 설정 형식으로 안내된 파일이 아니라면 직접 편집 대상으로 보지 않습니다.

즉, 다른 컴퓨터의 `.cursor` 폴더를 그대로 복사하는 것이 아니라 <strong>공식적으로 지원되는 구성 요소만 새로 작성</strong>해야 합니다.

---

## 🦮 2. 어떤 지침을 어디에 넣어야 할까?

기준은 단순합니다. <strong>항상 지켜야 하는 규칙인지, 특정 작업을 수행하는 절차인지, 별도 역할이 필요한지, 코드로 강제해야 하는지</strong>를 구분하면 됩니다.

1. <strong>User Rules</strong>  
   모든 프로젝트에 적용할 개인 선호를 적습니다. 답변 언어, 설명 길이, 기본적인 커뮤니케이션 방식이 여기에 어울립니다.

2. <strong>AGENTS.md</strong>  
   별도 메타데이터 없이 프로젝트 지침을 간단한 Markdown으로 관리할 때 사용합니다.

3. <strong>Project Rules</strong>  
   파일 종류나 디렉터리에 따라 세밀하게 적용할 규칙을 `.cursor/rules/*.mdc`에 작성합니다.

4. <strong>Skills</strong>  
   “블로그 글 등록”, “릴리스 준비”, “DB 마이그레이션 검증”처럼 재사용할 수 있는 작업 절차를 만듭니다.

5. <strong>Subagents</strong>  
   조사, 보안 검토, 테스트 검증처럼 별도의 역할과 독립된 컨텍스트가 필요한 작업을 맡깁니다.

6. <strong>Hooks</strong>  
   파일 수정 후 포맷터 실행, 위험한 셸 명령 차단처럼 지침을 넘어 결정적으로 실행하거나 검사해야 하는 동작에 사용합니다.

User Rules는 Cursor의 <strong>Customize → Rules</strong>에서 작성하며 Agent 대화 전반에 적용됩니다. 팀 환경에서는 Team Rules도 함께 적용되고, 공식 문서상 충돌 시 우선순위는 <strong>Team Rules → Project Rules → User Rules</strong> 순서입니다.

처음부터 전부 만들 필요는 없습니다. <strong>AGENTS.md 또는 Rules로 시작하고, 반복되는 작업만 Skill로 옮기는 방식</strong>이 관리하기 쉽습니다.

## 🦮 3. 가장 간단한 시작: `AGENTS.md`

프로젝트 루트에 `AGENTS.md`를 만들면 일반 Markdown으로 지침을 작성할 수 있습니다.

```text
my-project/
├─ AGENTS.md
├─ package.json
└─ src/
```

```markdown
# Project Instructions

## 기본 원칙

- 새 코드는 TypeScript로 작성한다.
- 기존 폴더 구조와 네이밍을 먼저 확인한다.
- 기능 변경 후 관련 테스트와 타입 검사를 실행한다.
- 생성 파일과 빌드 결과물은 직접 수정하지 않는다.

## 답변 방식

- 변경한 파일과 검증 결과를 간단히 정리한다.
- 확인하지 않은 동작을 완료했다고 표현하지 않는다.
```

`AGENTS.md`의 장점은 문법이 단순하고 사람이 읽기 쉽다는 점입니다. 프로젝트가 커지면 하위 디렉터리에도 둘 수 있습니다.

```text
my-project/
├─ AGENTS.md
├─ frontend/
│  └─ AGENTS.md
└─ backend/
   └─ AGENTS.md
```

Cursor는 작업 중인 파일의 경로에 맞춰 상위 지침과 하위 지침을 함께 적용하며, 충돌할 때는 더 구체적인 하위 디렉터리의 지침이 우선합니다.

## 🦮 4. 적용 범위를 제어하는 Project Rules

Project Rules는 `.cursor/rules` 아래의 <strong>`.mdc` 파일</strong>로 작성합니다. `.md` 파일을 이 폴더에 넣으면 Project Rule로 인식되지 않으므로 주의해야 합니다.

```text
.cursor/
└─ rules/
   ├─ project-basics.mdc
   ├─ react-components.mdc
   └─ database-migrations.mdc
```

### 🦄 4.1. 모든 작업에 적용하는 규칙

```markdown
---
alwaysApply: true
---

# 프로젝트 공통 원칙

- 작업 전에 관련 파일과 기존 구현을 먼저 확인한다.
- 사용자가 요청하지 않은 대규모 리팩터링은 하지 않는다.
- 패키지 매니저는 저장소의 lock 파일을 기준으로 선택한다.
- 완료 전에 타입 검사와 관련 테스트를 실행한다.
```

`alwaysApply: true`는 모든 Agent 대화에 포함되므로 정말 공통적인 내용만 넣어야 합니다. 너무 긴 규칙은 매 요청의 컨텍스트를 계속 차지합니다.

### 🦄 4.2. 특정 파일에만 적용하는 규칙

```markdown
---
globs: src/components/**/*.tsx, src/app/**/*.tsx
alwaysApply: false
---

# React UI 규칙

- 기존 디자인 토큰과 공용 컴포넌트를 우선 사용한다.
- 상태가 필요하지 않은 컴포넌트에 불필요하게 client 지시자를 추가하지 않는다.
- 접근 가능한 이름이 없는 아이콘 버튼에는 aria-label을 작성한다.
- 반응형 스타일은 프로젝트에서 사용 중인 CSS 방식에 맞춘다.
```

`globs`는 쉼표로 여러 패턴을 지정할 수 있습니다.

- `**/*.ts`: 모든 폴더의 TypeScript 파일
- `src/**`: `src` 아래의 모든 파일
- `src/**/*.tsx`: `src` 아래의 모든 TSX 파일
- `docs/**/*.md, docs/**/*.mdx`: 문서 폴더의 Markdown과 MDX

### 🦄 4.3. 상황에 따라 Agent가 선택하는 규칙

```markdown
---
description: API 라우트와 서비스 계층을 수정할 때 적용하는 검증 및 오류 처리 규칙
alwaysApply: false
---

- 외부 입력은 서비스 경계에서 검증한다.
- 오류는 프로젝트의 공통 오류 형식으로 반환한다.
- 기존 API 응답 스키마를 임의로 깨뜨리지 않는다.
- 변경된 경로의 통합 테스트를 실행한다.
```

`description`만 있고 `globs`가 없으면 Agent가 설명을 보고 관련성을 판단합니다. 반면 `description`, `globs`가 모두 없고 `alwaysApply`도 `false`라면 채팅에서 해당 규칙을 직접 `@`로 언급했을 때 적용됩니다.

### 🦄 4.4. 기존 `.cursorrules`는 이전하기

프로젝트 루트의 `.cursorrules`는 레거시 방식입니다. 기존 내용을 `.cursor/rules/*.mdc`로 옮기고, 예전처럼 항상 적용해야 한다면 `alwaysApply: true`를 지정합니다. 새 프로젝트에서는 `.cursorrules`로 시작하지 않는 편이 좋습니다.

## 🦮 5. 규칙과 Skill은 무엇이 다를까?

Rule은 <strong>작업 중 계속 지켜야 할 기준</strong>이고, Skill은 <strong>특정 결과를 만들기 위한 재사용 가능한 절차</strong>에 가깝습니다.

예를 들어 “모든 TypeScript에서 `any`를 사용하지 않는다”는 Rule에 어울립니다. 반면 “새 블로그 글을 만들고 데이터에 등록한 뒤 링크를 검사한다”는 여러 단계가 있으므로 Skill이 더 알맞습니다.

Cursor는 다음 위치에서 Skill을 찾습니다.

```text
.cursor/skills/                 # 현재 프로젝트
~/.cursor/skills/               # 내 모든 로컬 프로젝트
.agents/skills/                 # Agent Skills 호환 경로
~/.agents/skills/               # 사용자 전역 호환 경로
```

프로젝트에서 팀과 공유하려면 `.cursor/skills` 또는 `.agents/skills`를 Git에 포함합니다. 개인용 Skill은 `~/.cursor/skills`에 두되, <strong>`~/.cursor/skills-cursor`에는 만들지 않습니다.</strong>

## 🦮 6. 프로젝트에 맞춘 Skill 만들기

블로그 글을 작성하고 등록하는 절차를 예로 들어 보겠습니다.

```text
.cursor/
└─ skills/
   └─ write-blog-post/
      ├─ SKILL.md
      ├─ references/
      │  └─ post-format.md
      └─ scripts/
         └─ validate-post.mjs
```

`SKILL.md`는 YAML frontmatter와 실제 지침으로 구성합니다.

```markdown
---
name: write-blog-post
description: 기존 문체와 데이터 구조를 분석해 새 블로그 글을 작성하고 목록에 등록한다. 사용자가 기술 글 작성이나 기존 원고 재구성을 요청할 때 사용한다.
paths:
  - "content/**/*.md"
  - "src/data/blog/**/*.json"
---

# Write Blog Post

## 🦮 작업 순서

1. 같은 카테고리의 최근 글 2개를 읽어 문체와 구조를 파악한다.
2. 원문을 그대로 복사하지 말고 핵심 개념을 다시 구성한다.
3. 사실과 개인 의견을 구분하고 공식 출처 링크를 남긴다.
4. 기존 파일명과 날짜 형식에 맞춰 글을 생성한다.
5. 목록 데이터에 새 글을 등록한다.
6. `node scripts/validate-post.mjs`로 경로와 필수 필드를 검사한다.

## 🦮 작성 원칙

- 독자가 바로 적용할 수 있는 예제를 포함한다.
- 확인할 수 없는 수치나 기능을 단정하지 않는다.
- 자세한 글 형식은 `references/post-format.md`를 읽는다.
```

여기서 중요한 부분은 `description`입니다. Agent는 이 설명을 보고 Skill을 자동으로 사용할지 판단하므로 <strong>무엇을 하는지와 언제 사용하는지</strong>를 함께 적어야 합니다.

자동 실행을 원하지 않고 `/write-blog-post`로 호출할 때만 사용하려면 frontmatter에 아래 값을 추가합니다.

```yaml
disable-model-invocation: true
```

Agent 입력창에서 `/`를 눌러 Skill을 선택하면 한 메시지에 적용됩니다. Windows에서 Skill을 선택한 뒤 `Alt+Enter`를 누르면 Custom Mode로 사용해 해당 세션 전체에 유지할 수도 있습니다.

새 Skill에서는 파일 범위에 `paths`를 사용합니다. 이전의 `globs`도 호환되지만 공식 문서는 새 Skill에 `paths` 사용을 권장합니다.

세부 문서와 예제가 길어지면 `SKILL.md`를 계속 늘리지 말고 `references`, 반복 실행할 로직은 `scripts`, 템플릿과 정적 파일은 `assets`로 분리합니다. 필요한 자료만 읽는 점진적 로딩 덕분에 컨텍스트도 절약할 수 있습니다.

기존 Slash Command나 지능형 적용 Rule을 작업 절차로 사용하고 있었다면 내장 `/migrate-to-skills`를 통해 Skill로 변환할 수 있습니다. 항상 적용하거나 명확한 `globs`를 가진 Rule은 적용 방식이 다르므로 그대로 유지됩니다.

Commands 자체가 폐기된 것은 아닙니다. 짧은 재사용 프롬프트를 `/명령어`로 직접 실행하는 용도로 여전히 지원됩니다. 다만 스크립트, 참고 문서, 파일 범위까지 필요한 새 워크플로라면 Skill이 더 확장하기 쉽습니다.

## 🦮 7. 별도 역할은 Subagent로 분리하기

Skill이 “어떻게 작업할지”를 알려 준다면, Subagent는 <strong>독립된 컨텍스트에서 한 가지 역할을 수행하는 작업자</strong>입니다.

프로젝트 전용 Subagent는 `.cursor/agents/*.md`, 사용자 전역 Subagent는 `~/.cursor/agents/*.md`에 작성합니다.

```markdown
---
name: verifier
description: 구현 완료 후 실제 동작과 검증 결과를 독립적으로 확인한다. 기능 작업이 끝난 뒤 적극적으로 사용한다.
model: inherit
readonly: true
---

# Verifier

완료되었다는 설명을 그대로 믿지 말고 실제 변경 사항을 확인한다.

1. 요청 사항과 diff를 비교한다.
2. 관련 테스트, 타입 검사, 린트를 실행한다.
3. 구현되지 않은 항목과 회귀 가능성을 찾는다.
4. 통과한 항목과 남은 문제를 구분해 보고한다.
5. 파일은 직접 수정하지 않는다.
```

`readonly: true`를 사용하면 검증 역할이 파일을 직접 변경하지 못하게 제한할 수 있습니다. 조사나 테스트처럼 중간 출력이 많고 메인 대화의 컨텍스트를 크게 차지하는 작업에 특히 유용합니다.

단순한 포맷 변경이나 한 번의 명령 실행까지 모두 Subagent로 만들 필요는 없습니다. 공식 문서도 처음에는 <strong>명확한 역할 2~3개</strong>로 시작하고, 실제로 분리할 이유가 있을 때 추가하는 방식을 권장합니다.

## 🦮 8. 반드시 실행되어야 한다면 Hooks

Rules와 Skills는 Agent에게 주는 지침입니다. 따라서 보안 정책이나 포맷 적용처럼 확실하게 검사해야 하는 작업의 유일한 방어선으로 사용하면 안 됩니다.

Hooks는 Agent의 특정 시점에 스크립트를 실행합니다.

```text
.cursor/
├─ hooks.json
└─ hooks/
   └─ check-edited-files.mjs
```

```json
{
  "version": 1,
  "hooks": {
    "afterFileEdit": [
      {
        "command": "node .cursor/hooks/check-edited-files.mjs"
      }
    ]
  }
}
```

프로젝트 Hook은 프로젝트 루트에서 실행되므로 스크립트 경로도 `.cursor/hooks/...`처럼 프로젝트 루트 기준으로 작성합니다. 사용자 전역 Hook은 `~/.cursor/hooks.json`과 `~/.cursor/hooks/`에 둘 수 있지만, 로컬 사용자 디렉터리를 사용할 수 없는 Cloud Agent에는 프로젝트 Hook이 더 적합합니다.

Hook은 강력하지만 잘못 작성하면 모든 작업을 느리게 하거나 정상 명령까지 차단할 수 있습니다. 처음에는 범위를 좁게 잡고 실제 이벤트에서 동작하는지 확인해야 합니다.

차단용 Hook은 스크립트 오류가 났을 때 기본적으로 작업을 허용할 수 있다는 점도 확인해야 합니다. 반드시 차단해야 하는 정책이라면 동작을 충분히 테스트하고 `failClosed: true` 사용을 검토합니다. Cloud Agent에서는 프로젝트의 command 기반 Hook만 지원되므로 로컬 사용자 Hook이나 prompt 기반 Hook에만 의존하지 않는 편이 안전합니다.

### 🦄 Automation Memories와 혼동하지 않기

공식 문서에서 `MEMORIES.md`로 설명하는 Memories는 일반 Agent 대화의 프로젝트 지침이 아니라 <strong>Cursor Automations가 여러 실행 사이에 정보를 유지하는 기능</strong>입니다. User Rules와도 목적이 다릅니다.

- User Rules: 모든 프로젝트에서 사용할 개인 지침
- Automation Memories: 같은 Automation의 다음 실행에 전달할 지속 메모

외부 메시지나 Webhook을 처리하는 Automation에서는 잘못된 내용이 장기 메모에 남을 수 있으므로, 신뢰하지 못하는 입력을 그대로 Memories에 저장하지 않아야 합니다.

## 🦮 9. 처음 권장하는 구성

처음 구성한다면 아래 정도로 시작하는 것이 좋습니다.

```text
my-project/
├─ AGENTS.md
└─ .cursor/
   ├─ rules/
   │  ├─ project-basics.mdc
   │  └─ frontend.mdc
   ├─ skills/
   │  └─ write-blog-post/
   │     └─ SKILL.md
   └─ agents/
      └─ verifier.md
```

1. `AGENTS.md`에는 프로젝트를 처음 보는 사람도 알아야 할 핵심 구조를 적습니다.
2. `project-basics.mdc`에는 모든 작업에서 반복되는 최소 규칙만 넣습니다.
3. 파일별 제약은 `frontend.mdc`, `database.mdc`처럼 범위를 나눕니다.
4. 반복되는 다단계 작업이 생겼을 때만 Skill을 만듭니다.
5. 독립 검증이 실제로 필요할 때 Subagent를 추가합니다.
6. 반드시 차단하거나 실행해야 하는 동작만 Hook으로 옮깁니다.

해당 구성이 정답은 아닙니다. 중요한 것은 폴더 모양을 따라 하는 것이 아니라 <strong>프로젝트에서 반복되는 실패와 작업 패턴을 지침으로 바꾸는 것</strong>입니다.

## 🦮 10. 잘 작동하는 지침을 작성하는 방법

### 🦄 10.1. 모호한 취향보다 확인 가능한 행동을 쓴다

```text
나쁜 예: 코드를 깔끔하게 작성한다.
좋은 예: 기존 서비스 계층을 재사용하고, 새 공개 함수에는 반환 타입을 작성한다.
```

### 🦄 10.2. 한 파일에 모든 내용을 넣지 않는다

CSS, API, DB, 테스트 지침을 하나의 거대한 Rule로 만들면 관련 없는 작업에도 불필요한 내용이 포함됩니다. 한 가지 관심사와 적용 범위를 기준으로 분리합니다.

### 🦄 10.3. 코드베이스에 이미 있는 내용을 복사하지 않는다

긴 예제 코드를 Rule에 붙여 넣으면 실제 코드가 변경될 때 지침이 오래된 상태로 남습니다. 공식 문서의 권장처럼 기준이 되는 파일을 `@파일명`으로 참조하거나 Skill의 reference 문서로 연결하는 편이 낫습니다.

### 🦄 10.4. 린터가 할 일을 자연어 지침에 맡기지 않는다

포맷, import 순서, 문법 오류처럼 도구로 검사할 수 있는 항목은 ESLint, formatter, 테스트로 검증합니다. Rule에는 “어떤 검증을 언제 실행할지”를 적습니다.

### 🦄 10.5. 반복해서 발생한 실수부터 추가한다

앞으로 생길 수 있는 모든 예외를 미리 작성하면 지침만 복잡해집니다. Agent가 같은 실수를 반복했을 때 짧고 구체적인 규칙을 하나 추가하는 방식이 효과적입니다.

## 🦮 11. 적용되지 않을 때 확인할 항목

1. `.cursor/rules` 파일 확장자가 `.mdc`인지 확인합니다.
2. 지능형 적용 Rule에 `description`이 있는지 확인합니다.
3. 파일별 Rule의 `globs`가 실제 경로와 맞는지 확인합니다.
4. Skill 폴더명과 frontmatter의 `name`이 같은지 확인합니다.
5. 자동 호출하지 않는 Skill에 `disable-model-invocation: true`가 들어갔는지 확인합니다.
6. Customize 화면에서 해당 Rules, Skills, Subagents, Hooks가 발견되었는지 확인합니다.
7. 지침이 Cursor Tab에 적용될 것이라고 기대하지 않습니다. Rules는 Agent에 적용되며, User Rules도 Inline Edit에는 적용되지 않습니다.
8. 기존 `.cursorrules`를 새 프로젝트의 기준으로 사용하고 있지 않은지 확인합니다.

---

## 🦮 마무리

1. <strong>지속적인 기준은 Rule 또는 AGENTS.md</strong>
2. <strong>반복 가능한 작업 절차는 Skill</strong>
3. <strong>독립된 전문 역할은 Subagent</strong>
4. <strong>결정적으로 실행·차단할 동작은 Hook</strong>

이 네 가지를 구분하고 프로젝트에 필요한 내용만 짧게 작성하면 Agent의 결과가 훨씬 일관되어집니다. 처음에는 최소한으로 만들고, 실제 작업에서 반복되는 문제를 발견할 때마다 한 줄씩 개선하는 방식이 가장 현실적입니다.
