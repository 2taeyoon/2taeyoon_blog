## 🦮 AI끼리 장애에 대응하는 AX 솔루션

안녕하세요. 오늘은 저희 팀이 개발하고 있는 **AX 솔루션**을 소개하겠습니다. 핵심 주제는 두 가지입니다. **AI끼리 일을 주고받는 A2A**와 A2A를 기반으로 작동하는 **장애 대응**입니다.

먼저 결론부터 말씀드리겠습니다.

1. **AI 9개를 하나씩 따로 켜고 끌 수 있는 서비스로 만들었습니다.** 고객사가 필요한 AI만 골라 사기 때문입니다.

2. AI끼리는 **A2A 형태의 자체 HTTP 규약**으로 일을 부탁합니다. 어떤 서비스를 샀든 같은 요청을 같은 방식으로 보내기 위해서입니다.

3. 장애가 나면 총괄 AI가 계획을 세우고, 위험한 조치는 **LLM이 아니라 규칙이 막고**, 마지막 결정은 **사람**이 합니다. 장애 상황에서 AI의 판단이 틀리면 피해가 더 커지기 때문입니다.

## 🦮 1. 무엇을 만들었나

이 시스템은 크게 세 가지로 구성됩니다.

| 이름 | 역할 |
|---|---|
| AX 솔루션 | 저희가 파는 제품. 고객사 직원이 AI 서비스를 골라 쓰는 화면과 에이전트 서버 |
| 인프라 AI | Zabbix가 잡은 서버 장애를 분석하는 장애 대응 AI. 별도 팀, 별도 레포 |
| 쇼핑몰 | AX 솔루션을 쓰는 고객사 |

처음에는 쇼핑몰 레포 안에 부서별 AI를 만들었습니다. 그런데 저희가 팔 것은 쇼핑몰이 아니라 AX 솔루션이기 때문에, 에이전트 코드를 AX 솔루션으로 옮기고 쇼핑몰은 고객사 역할만 하도록 정리했습니다.

전체 흐름은 이렇습니다.

<img src="/images/blog/ai/28/images1.webp"/>

위쪽 경로를 순서대로 말로 풀면 이렇습니다.

1. 쇼핑몰이 결제 지연과 오류를 스스로 감시하다가, 기준을 넘으면 `shop.degraded` 신호를 장애 시작 시각과 함께 보냅니다.
2. 신호는 Redis Streams를 타고 모든 서비스에 전달되고, 총괄 AI가 이를 받아 사건을 엽니다.
3. 총괄 AI가 계획을 세워 인프라, 데이터분석, 고객지원, 마케팅, 재무 AI 등에게 A2A로 일을 나눕니다.
4. 각 AI가 상태를 바꾸는 조치를 하려면 안전 관문을 거쳐야 하고, 관문은 A·B·C 등급에 따라 바로 실행하거나, 다른 AI에게 확인받거나, 사람 승인을 기다립니다.

한 가지 먼저 짚고 가겠습니다. 그림에는 **장애 경로가 두 개**입니다.

| 경로 | 무엇을 하나 |
|---|---|
| 쇼핑몰 → 총괄 AI | 쇼핑몰이 직접 감지한 결제 장애를 AI들이 실제로 대응합니다 |
| 인프라 AI → AX 솔루션 화면 | Zabbix가 잡은 서버 장애를 화면에 보여줍니다 |

## 🦮 2. AI를 하나씩 따로 파는 서비스로 만들었습니다

AI는 회사의 역할을 따라 9개로 나눴습니다. 그런데 고객사는 9개를 한꺼번에 사지 않습니다. "고객지원 AI만 필요해요", "인프라 AI만 붙여 주세요"처럼 **필요한 AI만 골라 사기 때문에, AI 하나하나를 따로 켜고 끌 수 있는 독립된 서비스로 만들었습니다.**

| AI | 하는 일 |
|---|---|
| 총괄 AI (orchestrator) | 사건을 열고 계획을 세워 다른 AI에게 일을 나눔 |
| 인프라 AI | 장애 대응 및 원인 진단, 롤백 요청, 복구 확인 |
| 데이터분석 AI | 결제 실패율, 주문 실패 수 같은 지표 계산 |
| 고객지원 AI | 고객 문의·클레임·리뷰 응대와 보상 |
| 마케팅 AI | 장애 공지 작성, 보상 쿠폰 발급 |
| 재무 AI | 비용과 보상 금액을 장부에 기록, 재무재표 |
| 기획 AI | 요청 정리, 롤백 대상 확인 |
| 개발 AI | 배포 이력 확인, 관련 PR 연결 |
| 인사 AI | 조직 변동, 인수인계, 담당자 찾기 |

## 🦮 3. A2A: AI끼리 일을 부탁하는 방법

모든 AI는 똑같이 세 개의 주소만 엽니다.

| 주소 | 용도 |
|---|---|
| `GET /.well-known/agent-card.json` | "나는 이런 일을 할 수 있다"는 자기소개서 (에이전트 카드) |
| `GET /health` | 살아 있는지 확인 |
| `POST /a2a` | 일 요청을 받고 결과를 돌려줌 |

**FastAPI로 같은 모양의 규약을 직접 만들었습니다.**

### 🦄 에이전트 카드에 "누가 나를 부를 수 있는지"까지 적었습니다

에이전트 카드의 기술(skill) 하나에는 이런 정보가 들어 있습니다.

| 항목 | 뜻 |
|---|---|
| `grade` | 이 일의 위험 등급 (조회 / A / B / C) |
| `allowed_requesters` | 이 일을 부탁할 수 있는 AI 목록 |
| `verifier` | B등급일 때 교차 확인할 AI (자기 자신은 안 됨) |
| 입력·출력 스키마 | 주고받는 데이터의 모양 |

위험도와 권한을 카드에 적은 이유는, **"이 일을 해도 되는가"를 대화 중에 AI가 판단하게 두지 않고 미리 정해 두기 위해서입니다.** AI가 그럴듯한 이유를 대면서 권한 밖의 일을 부탁해도, 받는 쪽은 카드에 없는 요청을 거절합니다.

### 🦄 call_agent 하나로 모든 요청을 보냅니다

AI가 다른 AI를 부를 때는 `call_agent` 함수 하나만 씁니다.

```python
result = await call_agent("finance", AgentRequest(
    skill="record_incident_finance",
    input={...},
))
```

요청에는 이런 정보가 함께 실립니다.

| 필드 | 쓰는 이유 |
|---|---|
| `path` | 지금까지 거쳐 온 AI 목록. 순환과 단계 제한을 검사하기 위해서입니다 |
| `deadline` | 마감 시각. 남은 시간이 그대로 HTTP 대기 시간이 되기 때문에 한 AI가 멈춰도 전체가 같이 멈추지 않습니다 |
| `idempotency_key` | 같은 요청을 두 번 보내도 한 번만 실행되게 하는 열쇠입니다. 재시도 때문에 쿠폰이 두 번 나가면 안 되기 때문입니다 |
| `untrusted` | 고객이 쓴 문의처럼 바깥에서 온 글. 프롬프트에 지시문이 아니라 데이터로만 들어갑니다 |
| 요청자 | 본문에 적힌 값은 무시하고 토큰에서만 읽습니다. 다른 AI인 척하는 요청을 막기 위해서입니다 |

결과도 상태값이 정해져 있습니다. `completed`, `rejected`, `failed`, `canceled`, 그리고 누군가의 입력이 필요하다는 `input-required`입니다. 상태를 정해 둔 이유는 **총괄 AI가 결과 문장을 해석하지 않고 상태값만 보고 다음 행동을 정하게 하기 위해서입니다.**

### 🦄 받는 쪽은 8단계를 통과해야 일을 시작합니다

요청을 받은 AI는 일을 시작하기 전에 순서대로 검사합니다.

1. 사건과 고객사 정보가 맞는지
2. 토큰이 진짜인지
3. 같은 AI가 경로에 다시 나오는 순환이 없는지
4. 거쳐 온 단계가 3을 넘지 않는지
5. 요청자가 이 기술을 부를 권한이 있는지
6. 마감 시간이 남았는지
7. 실제 처리
8. 결과가 약속한 스키마에 맞는지

4번 단계 제한을 둔 이유는 **AI가 AI를 부르고, 그 AI가 또 다른 AI를 부르는 연쇄가 끝없이 이어지는 것을 막기 위해서입니다.** 3단계를 넘으면 실패로 끝내지 않고 사람 확인 대기열로 보냅니다.

### 🦄 총괄 AI의 재시도 규칙도 코드로 고정했습니다

| 상황 | 총괄 AI의 행동 |
|---|---|
| `failed` | 2번까지 다시 시도 |
| `canceled` (시간 초과) | 1번 다시 시도 |
| `rejected` | 같은 기술을 가진 다른 서비스에 넘기고, 없으면 사람에게 넘김 |
| 다른 부서의 답이 필요함 | 그 부서에 묻고 답을 받아 다시 요청 |
| 사람의 답이 필요함 | 기다림. 스스로 승인하지 않음 |

마감 시간은 기본 30초이고, 복구 확인만 180초입니다. 복구는 실제로 시간이 지나야 확인되는 일이기 때문입니다.

### 🦄 이벤트는 Redis Streams 하나로 흘립니다

"결제가 느려졌다", "쿠폰이 발급됐다" 같은 신호는 `call_agent`가 아니라 이벤트로 보냅니다. 스트림은 `ax:events` 하나이고, 서비스마다 소비자 그룹을 따로 둬서 **모든 서비스가 모든 이벤트를 받습니다.** 누가 이 신호를 필요로 할지 보내는 쪽이 몰라도 되게 하기 위해서입니다.

처리가 끝나야 확인(ack)하고, 5번 실패하면 실패 보관함으로 옮깁니다. 같은 이벤트가 두 번 와도 `event_id`로 걸러 냅니다. 장애 중에는 서버가 재시작될 수 있어서, 이벤트를 잃어버리는 것보다 두 번 받는 쪽이 안전하기 때문입니다.

## 🦮 4. 장애 대응 흐름: 결제 장애 시나리오

이제 실제로 장애가 나면 어떻게 움직이는지 살펴보겠습니다. 쇼핑몰에서 결제가 실패하는 상황입니다.

### 🦄 1단계: 쇼핑몰이 스스로 장애를 감지합니다

쇼핑몰 API는 응답 시간(p95)과 5xx 오류율을 직접 측정합니다.

| 기준 | 기본값 | 실행 시 |
|---|---|---|
| p95 응답 시간 | 1,000ms 초과 | 같음 |
| 5xx 오류율 | 2% 초과 | 같음 |
| 지속 시간 | 60초 | 20초 |

기준을 넘은 상태가 지속 시간만큼 이어지면 `shop.degraded` 이벤트를 보냅니다. 이때 **장애가 시작된 시각(`since`)을 같이 보냅니다.** 감지한 시각을 쓰면 실제 피해보다 짧게 계산되기 때문입니다.

### 🦄 2단계: 총괄 AI가 사건을 엽니다

총괄 AI는 `shop.degraded`를 받으면 사건을 엽니다. 같은 부품에 이미 열린 사건이 있으면 새로 만들지 않고 합칩니다. 같은 장애로 사건이 여러 개 생기면 공지와 보상도 여러 번 나가기 때문입니다.

### 🦄 3단계: 계획을 데이터로 세웁니다

```text
진단 → 영향 분석 → 비슷한 과거 사건 찾기 → 원인 가설

→ 원인 확인 티켓 → 롤백 요청 → 관련 PR 연결

→ 장애 공지 작성·게시 → 보상 요청 (50명씩)

→ 복구 확인 → 복구 공지 → 재무 기록 → KPI 요약 → 사건 기록
```

계획을 코드 흐름이 아니라 **데이터(단계 목록)로 만든 이유는, 모든 부서 AI가 준비되기 전에도 연동과 개발을 나눠서 동시에 진행하기 위해서입니다.** 아직 없는 서비스의 단계는 사람에게 넘어가고, 서비스가 생기면 같은 계획이 그대로 AI에게 갑니다.

분기도 있습니다. 원인을 못 찾으면 롤백하지 않고 사람에게 넘깁니다. 복구가 확인되지 않으면 "정상화되었습니다" 공지를 보내지 않습니다.

### 🦄 4단계: 원인 진단에는 LLM을 쓰지 않습니다

진단은 규칙으로만 합니다. 최근 60분 안에 배포가 있었는지 보고, 확신도를 정합니다.

| 상황 | 확신도 |
|---|---|
| 후보 배포 1개, 15분 이내 | 높음 |
| 후보 배포 1개, 15분 이전 | 중간 |
| 후보 배포 여러 개 | 가장 최근 것만 중간, 나머지 낮음 |
| 후보 없음 | 원인 미확정 |

**원인과 확신도를 LLM으로 정하지 않은 이유는, 그 결과로 롤백 여부가 정해지기 때문입니다.** 같은 상황이면 언제나 같은 결론이 나와야 나중에 왜 그렇게 했는지 설명할 수 있습니다. 복구 예상 시간도 추측하지 않습니다.

### 🦄 5단계: 롤백은 안전 관문을 거칩니다

롤백 요청은 바로 실행되지 않고 안전 관문으로 갑니다. 그리고 지금의 "롤백"은 **넣어 둔 장애를 해제하는 API 호출**입니다. SSH나 셸, 실제 배포 도구는 부르지 않습니다. 실제 서버를 건드리는 권한은 AI에게 아직 주지 않았기 때문입니다.

### 🦄 6단계: 복구는 두 가지가 모두 정상이어야 인정합니다

30초마다 최대 5번 확인합니다. **인프라 신호(쇼핑몰 장애 상태)와 비즈니스 지표(결제 실패율, 주문 실패 수)가 둘 다 정상이어야 복구로 봅니다.** 서버가 살아나도 결제가 계속 실패하면 고객 입장에서는 장애가 끝난 게 아니기 때문입니다. 지표가 비어서 돌아오면 정상이 아니라 "확인 못 함"으로 봅니다.

복구 시각(`recovered_at`)과 대응 종료 시각(`closed_at`)도 나눠 저장합니다. 장애가 끝난 시각과 사람이 정리를 끝낸 시각은 다르고, 피해 계산에는 앞의 것이 필요하기 때문입니다.

### 🦄 7단계: 보상은 사람이 승인해야 나갑니다

보상 대상 고객을 50명씩 묶어 요청하고, **사람이 승인한 뒤에야 발송 대기열로 넘어갑니다.** 복구 뒤에 새로 피해를 본 고객도 대기열에 추가합니다. 재무 AI는 금액을 기록만 하고 결정하지 않습니다.

## 🦮 5. 안전 관문: 위험한 일은 규칙이 막습니다

상태를 바꾸는 모든 조치는 실행 전에 안전 관문을 거칩니다. 안전 관문은 **LLM을 쓰지 않습니다.**

| 등급 | 처리 |
|---|---|
| A | 바로 실행 |
| B | 다른 AI가 A2A로 교차 확인. 30초 안에 답이 없으면 C로 올림 |
| C | 사람 승인 대기열. 사람 토큰으로만 결정 가능 |

등급은 등록부(조치 100개)와 기준표 중 **더 높은 쪽**으로 정해지고, 이 두 파일은 사람이 PR로만 고칩니다. **등급을 LLM이 아니라 규칙이 정하게 한 이유는, 같은 조치가 언제나 같은 등급을 받아야 검증하고 감사할 수 있기 때문입니다.**

롤백을 예로 들면 이렇습니다.

| 조건 | 등급 |
|---|---|
| 기본 | B. 기획 AI가 롤백 대상이 맞는지 확인 |
| 의심 배포가 2개 이상 | C |
| 확신도가 낮은 후보가 있음 | C |
| 되돌릴 수 없는 변경(DB 마이그레이션 등) 포함 | C |
| 이미 한 번 롤백함 | C |

확인 AI가 롤백 대상을 거절하면 그냥 끝내지 않고 사람에게 넘깁니다. **검증이 거절해도 장애는 계속되고 있기 때문입니다.**

다른 조치도 마찬가지입니다. 쿠폰 총액이 30만 원 이상이거나 1장당 2만 원을 넘으면 C, SNS 게시는 항상 C입니다. 그리고 다음 상황은 모두 **거절**로 처리합니다.

- 등록되지 않은 조치
- 금액 필드가 이상하거나 합계가 맞지 않음
- 확인 AI가 답하지 않음

애매하면 실행하지 않는 쪽으로 정했습니다. 장애 중에 잘못 실행된 조치는 장애를 하나 더 만들기 때문입니다.

한 가지 더 있습니다. 관문의 "실행 가능"은 **"이제 쓰기 도구를 불러도 된다"는 허가**일 뿐입니다. 실제 쓰기는 요청한 AI가 같은 `idempotency_key`로 다시 보내서 합니다. 사람이 승인한 뒤 재요청이 두 번 들어와도 한 번만 실행되게 하기 위해서입니다.

## 🦮 6. 서비스가 없으면 사람에게 넘깁니다

고객사가 인프라 AI만 사고 재무 AI는 안 샀다면, 재무 기록 단계는 어떻게 될까요?

**같은 요청이 AI 대신 사람에게 갑니다.** 대상 서비스가 꺼져 있으면, 그 요청은 대시보드의 "받은 요청" 함에 일감으로 들어갑니다. 조직도에서 담당자를 찾고, 담당자가 없으면 지어내지 않고 "담당자 없음"으로 남깁니다.

사람이 일을 끝내면 `handoff.completed` 이벤트가 오고, 총괄 AI가 멈췄던 계획을 이어 갑니다. 이때 사람이 적은 결과도 `untrusted`로 다룹니다.

이렇게 만든 이유는 **서비스를 하나만 사도 나머지 부서(사람)와 협업이 되게 하기 위해서입니다.** 요청하는 쪽 코드는 하나도 바뀌지 않고, 받는 쪽만 AI에서 사람으로 바뀝니다. 켜고 끄는 설정은 재시작 없이 다시 읽기 때문에, 서비스를 추가로 사면 바로 AI가 받기 시작합니다.

## 🦮 7. 인프라 AI는 화면이 아니라 데이터만 가져옵니다

인프라 AI는 장애 대응을 맡는 AI로, 별도 레포에서 만들고 있습니다. Zabbix가 잡은 서버 장애를 30초마다 가져와 원인 후보와 근거를 정리합니다. 인프라 AI도 서버를 바꾸지 않고 **미리보기만** 만듭니다. 쓰기 도구가 등록되면 에이전트가 아예 켜지지 않게 막아 두었습니다.

AX 솔루션은 인프라 AI의 **화면을 가져오지 않고 데이터만 가져와서 직접 그립니다.** iframe이나 화면 긁기는 상대 화면이 바뀌면 같이 깨지고, 두 제품의 디자인도 어긋나기 때문입니다.

데이터는 AX 솔루션의 작은 프록시 서버를 거쳐 받습니다.

| 결정 | 이유 |
|---|---|
| 프록시를 둠 | 인프라 AI는 모든 API에 로그인 토큰을 요구하는데, 웹 서버(nginx)만으로는 로그인과 토큰 갱신을 할 수 없기 때문입니다 |
| GET만 허용 | AX 솔루션은 보기만 하면 되고, 실수로라도 상대 시스템을 바꾸면 안 되기 때문입니다 |
| 보기 전용 계정 사용 | 프록시가 뚫려도 할 수 있는 일이 조회뿐이게 하기 위해서입니다 |

최근에는 인프라 AI 쪽에 지식 검색(RAG)이 붙었습니다. 비슷한 과거 사건과 해결 메모를 함께 보여 줍니다. 저장소는 SQLite 하나에 전문 검색과 벡터를 같이 넣었습니다. 별도 DB 컨테이너를 늘리지 않기 위해서입니다.
