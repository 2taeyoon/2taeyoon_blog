## 🦮 캣북스 · DejaFix · AXcellent, 세 플랫폼이 함께 일하는 방법

안녕하세요. 지난 글에서는 AI끼리 장애에 대응하는 AX 솔루션을 소개했습니다. 이번 글은 저희가 만든 **세 개의 플랫폼이 어떻게 맞물려 하나의 회사처럼 움직이는지** 정리한 영상을 글로 옮긴 것입니다.

먼저 결론부터 말씀드리겠습니다.

1. **캣북스**는 실제처럼 주문과 결제가 일어나는 가상의 회사입니다. AI가 일할 "현장"이 있어야 AX를 검증할 수 있기 때문입니다.

2. **DejaFix**는 Zabbix 알람을 받아 원인을 정리하는 장애 대응 코파일럿입니다. 서버를 **조회만** 하고, 조치는 **미리보기**까지만 합니다.

3. **AXcellent**는 회사 서버에 설치하는 AI 업무 플랫폼입니다. 총괄 AI 아래 8개 부서 AI가 **A2A**로 일을 주고받고, 위험한 일은 **규칙과 사람**이 막습니다.

4. 실제로 결제 장애를 넣어 돌려 본 결과, 사건은 **2분 47초** 만에 마무리됐고, 같은 장애의 복구 시간은 과거 기록을 재사용해 **22초에서 1초**로 줄었습니다.

## 🦮 1. 세 플랫폼의 관계

<img src="/images/blog/ai/29/images1.webp"/>

| 플랫폼 | 역할 | 한 줄 요약 |
|---|---|---|
| 캣북스 | 가상 고객사 (책·문구 오픈마켓) | 실제처럼 움직이는 회사 |
| DejaFix | 장애 대응 코파일럿 (Zabbix 기반) | 인프라를 지키는 눈 |
| AXcellent | AI 업무 플랫폼 | 회사를 함께 운영하는 AI 동료들 |

캣북스는 AXcellent 위에서 운영되는 고객사입니다. 주문과 결제가 일어날 때마다 이벤트를 남기고, 반품·환불 같은 요청은 A2A로 AXcellent의 고객지원 AI에게 보냅니다. DejaFix는 서버를 지켜보다가 장애를 AXcellent에 알립니다.

세 플랫폼을 나눈 이유는 **"AI를 쓰는 회사"와 "AI를 파는 제품"과 "인프라를 지키는 도구"가 서로 다른 속도로 바뀌기 때문입니다.** 하나로 묶으면 쇼핑몰을 고칠 때 AI 제품이 같이 흔들립니다.

## 🦮 2. 캣북스: AI가 일할 현장

<img src="/images/blog/ai/29/images2.webp"/>

### 🦄 작지만 진짜처럼 움직이는 오픈마켓

캣북스는 책과 문구를 파는 오픈마켓입니다. 책마루, 종이나라, 북앤펜 세 판매자가 8가지 상품을 팔고, 구매자 30명은 **개인정보 없이 가명 ID로만** 존재합니다. 실습용 회사라도 개인정보를 만들지 않는 것부터 지키기 위해서입니다.

### 🦄 금액은 서버가 다시 계산합니다

주문 금액은 화면이 보낸 값을 믿지 않고, 서버가 DB 가격으로 다시 계산합니다.

```text
상품 합계 → + 배송비 (5만 원 미만 3,000원) → − 쿠폰 → − 적립금 = 결제 금액
```

결제는 가짜 결제와 토스 테스트 결제 두 가지를 지원합니다. 그리고 **상태 확인 → 결제 기록 → 상태 변경을 한 트랜잭션에서 처리해서, 같은 주문에 결제가 동시에 들어와도 성공 결제는 1건만** 남깁니다.

### 🦄 모든 거래는 이벤트로 남습니다

주문 생성·취소, 결제 성공·실패는 주문과 같은 트랜잭션에 저장(outbox)된 뒤 Redis Streams로 발행됩니다. 저장과 발행 사이에 서버가 죽어도 이벤트를 잃지 않기 위해서입니다. 그리고 3초마다 실제처럼 주문이 들어오는 트래픽이 돌아서, AI는 항상 살아 있는 데이터를 봅니다.

### 🦄 쇼핑몰이 스스로 장애를 잽니다

| 기준 | 값 |
|---|---|
| 결제 응답 p95 | 1,000ms 초과 |
| 서버 오류(5xx) 비율 | 2% 초과 |
| 지속 시간 | 1분 |

이 상태가 이어지면 쇼핑몰이 직접 `shop.degraded` 이벤트를 보냅니다. 장애를 가장 먼저 아는 쪽이 결제를 처리하는 쇼핑몰이기 때문입니다.

### 🦄 고객 요청은 AI에게, 위험한 일은 사람에게

| 요청 | 처리 방식 |
|---|---|
| 고객 문의 | 쇼핑몰 문의함에 쌓이고, 고객지원 AI가 정해진 간격으로 읽어 감 |
| 반품·환불 신청 | A2A(`create_claim`)로 고객지원 AI에게 바로 전달 |
| 현금 환불 | 고객지원 토큰으로만 실행 가능 |
| 보유기간 삭제 | 기본은 건수만 세는 dry-run, 실제 삭제는 사람이 켬 |

## 🦮 3. DejaFix: 인프라를 지키는 눈

<img src="/images/blog/ai/29/images3.webp"/>

### 🦄 원칙 세 가지

1. **조회만 합니다.** 운영 Zabbix에는 `*.get` 호출만 보냅니다.
2. **변경은 미리보기까지만** 만듭니다. 실행 버튼은 처음부터 없습니다.
3. **근거 없는 값은 "확인할 수 없음"**으로 표시합니다. 지어내지 않습니다.

장애 상황에서 AI가 틀린 조치를 실행하면 장애가 하나 더 생기기 때문에, 판단은 돕되 실행은 사람에게 남겼습니다.

### 🦄 처리 흐름: 순서는 코드가, 분석은 AI가 한 번

스케줄러가 30초마다 Zabbix에서 장애를 가져오면, 에이전트가 정해진 순서로 처리합니다.

```text
대기 → 수집 → 분석(AI 1회) → 검증 → 보고 → 계획 → 완료
```

어떤 도구를 어떤 순서로 부를지는 코드가 정하고, LLM은 모은 자료로 분석을 한 번만 합니다. LLM이 실패해도 규칙 기반 보고서로 대체합니다.

### 🦄 쓰기 도구는 아예 존재할 수 없습니다

Zabbix 조회 도구 5개는 모두 읽기 전용입니다. 허용 목록 밖의 호출은 **네트워크 요청이 나가기 전에** 막히고, 쓰기 도구가 등록되면 **에이전트가 아예 시작되지 않습니다.** "실수로 쓰지 않기"가 아니라 "쓸 수 없게" 만든 것입니다.

### 🦄 분석 화면과 근거

- 화면에는 **무엇이 · 왜 · 어떻게**가 한 장에 정리됩니다.
- 원인 후보는 최대 3개, 확신도는 낮음·보통·높음으로만 표시합니다. 퍼센트는 쓰지 않습니다.
- 수치마다 근거 ID가 붙고, 오래된 값은 "확인할 수 없음"으로 바뀝니다.
- 모든 도구 호출은 근거 기록(EvidenceTrace)으로 남습니다.
- 변경 계획의 등급은 규칙 파일이 정합니다. 조회는 A, 승인이 필요한 변경은 B, 금지된 작업은 C입니다.

지금까지 장애 **521건**을 받아 보고서 **516건**을 만들었고, 도구 호출은 **3,597번** 기록됐습니다. 과거 장애 보고서 479건과 런북을 검색해 비슷한 과거 장애를 근거로 붙이고, 결과는 담당자에게 리포트당 한 번씩 메일로 보냅니다.

## 🦮 4. AXcellent: 회사를 함께 운영하는 AI 동료들

<img src="/images/blog/ai/29/images4.webp"/>

### 🦄 필요한 서비스만 켜서 씁니다

AXcellent는 회사 서버에 설치하는 AI 업무 서비스 모음입니다. 서비스 15개 중 필요한 것만 켜서 쓰고, 총괄 AI 아래 8개 부서 AI가 일합니다.

| 부서 AI | 하는 일 |
|---|---|
| 고객지원 | 문의 분류, 답변 초안 3개, 클레임·환불·보상 |
| 재무 | 장부, 결산, 대사, 장애 비용 기록 |
| 데이터분석 | 장애 영향(실패 주문·영향 고객·피해 금액), 지표 |
| 인사 | 사건 기록, 에이전트 평가 |
| 마케팅 | 공지, 배너, 쿠폰 |
| 기획 | 요청 → 기획서 |
| 개발 | 코드, 검수, 배포 |
| 인프라 | 장애 진단, 복구 확인 (DejaFix 연동) |

### 🦄 A2A: 카드 → 요청 → 회신

1. 모든 에이전트는 **에이전트 카드**에 할 수 있는 일을 공개합니다.
2. 총괄은 카드를 모아 "스킬 → 부서" 표를 만들고, 필요한 스킬을 가진 에이전트에게 요청을 보냅니다.
3. 회신에는 **결과와 근거**가 함께 옵니다. 근거 없는 숫자는 받지 않습니다.
4. 실패하면 재시도하고, 권한이 없으면 같은 스킬을 가진 다른 부서로, 서비스가 꺼져 있으면 **사람의 할 일함**으로 넘깁니다.

이 대화는 전부 한 대화방에 기록되어, 누가 누구에게 무엇을 부탁했는지 언제든 다시 볼 수 있습니다.

### 🦄 안전 관문과 기억

상태를 바꾸는 일은 모두 안전 관문을 지납니다. **A는 바로 실행, B는 다른 AI가 검증, C는 사람 승인**이고, 관문이 응답하지 않으면 사람 승인으로 막습니다.

끝난 사건은 인사 AI가 원인·조치·복구 시간까지 기록합니다. 다음에 비슷한 장애가 나면 임베딩 검색으로 찾고, **유사도가 0.85를 넘으면 그때의 조치를 바로 다시 실행**합니다.

## 🦮 5. 세 플랫폼이 함께 움직이는 장면

<img src="/images/blog/ai/29/images5.webp"/>

실제로 캣북스에 결제 장애를 넣고 돌려 봤습니다.

| 단계 | 누가 | 무엇을 |
|---|---|---|
| 감지 | 캣북스 | `shop.degraded` 발행 (Zabbix 알람은 DejaFix → 인프라 AI 경로로도 들어올 수 있음) |
| 사건 열기 | 총괄 | 같은 부위 신호를 사건 하나로 묶음 |
| 진단 | 인프라 AI | 원인 진단 |
| 과거 사건 | 인사 AI | 비슷한 과거 사건 검색 (유사도 88%, 1초 만에 찾음) |
| 영향 계산 | 데이터분석 AI | 실패 주문 6건, 영향 고객 6명, 피해 156,300원 |
| 조치 | 인프라 AI | 과거와 같은 방식으로 바로 처리, 되돌리기 단계는 건너뜀 |
| 공지·보상 | 마케팅·고객지원 AI | 캣북스에 점검 배너, 영향 고객 전원 보상 요청 |
| 예외 | 총괄 | 복구 확인이 애매해 정상화 공지를 보내지 않고 사람에게 넘김 |
| 기록 | 재무·데이터분석 AI | 장애 비용 장부 기록, 처리 시간 정리 |

**사건이 열린 지 2분 47초 만에 마무리됐고, 같은 장애의 복구 시간은 사람이 처리했던 22초에서 AI가 과거 조치를 재사용한 1초로 줄었습니다.**

복구 확인이 애매할 때 억지로 "정상화되었습니다"를 보내지 않은 부분이 중요하다고 생각합니다. 틀린 공지는 고객에게 장애보다 더 큰 혼란을 주기 때문입니다.

고객 문의에서 환불까지도 같은 방식입니다. 10만 원 미만은 바로 환불되고, 그 이상은 사람이 승인합니다. 새 기능 요청은 기획 AI가 기획서로, 개발 AI가 코드와 검수, 배포까지 이어 가고, 운영 배포만 사람이 승인합니다.

## 🦮 마치며

정리하면, 캣북스는 실제처럼 움직이는 회사, DejaFix는 인프라를 지키는 눈, AXcellent는 그 회사를 함께 운영하는 AI 동료들입니다.

저희가 생각하는 AX는 **AI를 쓰는 것이 아니라, AI가 함께 일하는 회사를 만드는 것**입니다. 그리고 그 회사가 믿을 만하려면 AI가 할 수 있는 일만큼, **AI가 하지 못하게 막아 둔 일**도 분명해야 한다고 생각합니다.
