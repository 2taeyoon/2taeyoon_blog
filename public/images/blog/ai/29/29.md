## 🦮 AI 업무 플랫폼과 장애 대응 시스템

먼저 결론부터 말씀드리겠습니다.

1. **쇼핑몰**은 실제처럼 주문과 결제가 이루어지는 가상의 회사입니다. AI가 일할 수 있는 현장이 있어야 업무 전환(AX)을 검증할 수 있기 때문입니다.

2. **장애 대응 시스템**은 서버 감시 시스템(Zabbix)의 경보를 받아 장애 원인을 정리하는 대응 보조 시스템입니다. 서버 상태를 **조회**하고, 조치는 **실행 전 미리보기**까지만 제공합니다.

3. **AI 업무 플랫폼**은 회사 서버에 설치해 사용하는 부서별 AI 동료 모음입니다. 총괄 AI 아래 8개 부서 AI가 **에이전트 간 통신(A2A)** 으로 업무를 주고받고, 위험한 작업은 **규칙과 사람의 승인**으로 통제합니다.

4. 실제로 결제 장애를 발생시켜 테스트한 결과, 사건은 **2분 47초** 만에 마무리됐고, 같은 장애의 복구 시간은 과거 처리 기록을 재사용해 **22초에서 1초**로 단축됐습니다.

## 🦮 1. 세 플랫폼의 관계

<img src="/images/blog/ai/29/images1.webp"/>

| 플랫폼 | 역할 |
|---|---|
| 쇼핑몰 | 가상 고객사 (책·문구 오픈마켓) |
| 장애 대응 시스템 | 장애 대응 보조 시스템 (Zabbix 기반) |
| AI 업무 플랫폼 | 부서별 AI 에이전트 플랫폼 |

쇼핑몰은 AI 업무 플랫폼을 사용하는 고객사입니다. 주문과 결제가 발생할 때마다 기록을 남기고, 반품·환불 같은 요청은 에이전트 간 통신(A2A)을 통해 플랫폼의 고객지원 AI에게 전달합니다. 장애 대응 시스템은 서버를 감시하다가 장애가 발생하면 플랫폼에 알립니다.

세 플랫폼을 분리한 이유는 **"AI를 사용하는 회사", "AI 제품을 제공하는 회사", "장애 대응 시스템"이 서로 다른 속도로 변경되기 때문입니다.** 하나로 묶으면 쇼핑몰을 수정할 때 AI 제품까지 영향을 받습니다. 실제 코드에서 문제가 발생할 수 있는 지점은 세 가지였습니다.

- **배포가 함께 묶입니다.** 한 서버에서 모든 서비스를 실행하면 쇼핑몰의 결제 화면 하나를 수정해 배포할 때 AI 에이전트들도 함께 재시작됩니다. 이를 방지하기 위해 쇼핑몰 서버와 부서별 AI를 서비스마다 독립된 컨테이너로 실행하고, 특정 서비스를 재시작해도 나머지는 계속 작동하도록 구성했습니다.
- **데이터베이스를 공유하면 구조 변경의 영향이 번집니다.** 재무·데이터분석 AI가 쇼핑몰 데이터베이스를 직접 조회하면 쇼핑몰이 주문 테이블의 열 이름 하나만 변경해도 AI의 조회문이 작동하지 않습니다. 따라서 쇼핑몰 데이터베이스는 쇼핑몰 서버만 읽고 쓰도록 제한하고, 다른 서비스는 쇼핑몰 API나 읽기 전용 데이터 화면을 통해서만 정보를 가져옵니다. 데이터 형식은 별도의 계약 파일로 관리하며, **필드는 추가만 허용하고 기존 필드의 삭제·이름 변경·자료형 변경은 금지한다**는 규칙을 적용합니다.
- **감시하는 시스템까지 함께 멈추면 안 됩니다.** 장애 대응 시스템이 AI 플랫폼 내부에 포함되어 있으면 플랫폼에 장애가 발생했을 때 그 장애를 알려 줄 시스템도 함께 멈춥니다. 따라서 장애 대응 시스템은 별도 저장소에서 버전을 지정해 가져오며, AI 플랫폼은 해당 코드를 수정하지 않습니다. 대신 읽기 전용 API(`GET /api/incidents?status=problem`)를 30초마다 호출하고, 응답 대기 시간은 최대 10초로 제한합니다. 화면도 iframe으로 가져오지 않고 데이터만 받아 직접 표시합니다. 장애 대응 시스템이 응답하지 않으면 해당 주기만 건너뛰고 플랫폼은 계속 작동합니다.

## 🦮 2. 쇼핑몰: AI가 일할 현장

<img src="/images/blog/ai/29/images2.webp"/>

### 🦄 작지만 실제처럼 움직이는 오픈마켓

쇼핑몰은 책과 문구를 판매하는 온라인 오픈마켓입니다. 판매자 3곳이 8가지 상품을 판매하고, 구매자 30명은 **개인정보 없이 가명 식별 번호로만** 존재합니다. 실습용 회사라도 개인정보를 생성하지 않는 원칙부터 지키기 위해서입니다.

### 🦄 금액은 서버가 다시 계산합니다

주문 금액은 화면에서 전달한 값을 그대로 사용하지 않고, 서버가 데이터베이스에 저장된 상품 가격을 기준으로 다시 계산합니다.

```text
상품 합계 → + 배송비 (5만 원 미만 3,000원) → − 쿠폰 → − 적립금 = 결제 금액
```

결제는 가상 결제와 토스 테스트 결제 두 가지를 지원합니다. 또한 **주문 상태 확인 → 결제 기록 저장 → 주문 상태 변경을 하나의 작업 단위로 처리하기 때문에, 동일한 주문에 결제가 동시에 요청되더라도 성공한 결제는 한 건만** 남습니다.

### 🦄 모든 거래는 이벤트로 기록됩니다

주문 생성·취소, 결제 성공·실패는 주문 정보와 동일한 작업 단위로 먼저 저장된 뒤, 레디스 스트림을 통해 발행됩니다. 저장과 발행 사이에 서버가 종료되더라도 이벤트가 유실되지 않도록 하기 위해서입니다. 또한 3초마다 실제 서비스처럼 주문이 발생하는 가상 트래픽이 실행되므로 AI는 항상 최신 데이터가 반영된 환경에서 작동합니다.

### 🦄 쇼핑몰이 스스로 장애를 감지합니다

| 기준 | 값 |
|---|---|
| 결제 응답 시간 상위 5% 기준 | 1,000ms 초과 |
| 서버 오류(5xx) 발생 비율 | 2% 초과 |
| 지속 시간 | 1분 |

위 상태가 지속되면 쇼핑몰이 직접 이벤트를 발행합니다. 결제를 처리하는 쇼핑몰이 장애를 가장 먼저 감지할 수 있기 때문입니다.

### 🦄 고객 요청은 AI에게, 위험한 작업은 사람에게

| 요청 | 처리 방식 |
|---|---|
| 고객 문의 | 쇼핑몰 문의함에 저장되고, 고객지원 AI가 정해진 간격으로 확인 |
| 반품·환불 신청 | 에이전트 간 통신(A2A)을 통해 고객지원 AI에게 즉시 전달 |
| 현금 환불 | 고객지원 전용 인증 권한으로만 실행 가능 |
| 보유기간 만료 데이터 삭제 | 기본적으로 삭제 대상 건수만 확인하고, 실제 삭제는 사람이 활성화 |

## 🦮 3. 장애 대응 시스템

<img src="/images/blog/ai/29/images3.webp"/>

### 🦄 세 가지 원칙

1. **조회만 합니다.** 운영 중인 Zabbix에는 조회 기능(`*.get`)만 호출합니다.
2. **변경은 실행 전 미리보기까지만 제공합니다.** 실제 실행 버튼은 처음부터 존재하지 않습니다.
3. 근거가 없는 값은 "확인할 수 없음"으로 표시합니다. 임의로 만들어 내지 않습니다.

장애 상황에서 AI가 잘못된 조치를 실행하면 또 다른 장애가 발생할 수 있습니다. 따라서 판단과 분석은 돕되 실제 실행 권한은 사람에게 남겼습니다.

### 🦄 처리 흐름: 순서는 코드가, 분석은 AI가 한 번

작업 관리기가 30초마다 Zabbix에서 장애 정보를 가져오면 에이전트가 정해진 순서에 따라 처리합니다.

```text
대기 → 수집 → 분석(AI 1회) → 검증 → 보고 → 계획 → 완료
```

어떤 도구를 어떤 순서로 호출할지는 코드가 결정하고, 대규모 언어 모델(LLM)은 수집된 자료를 바탕으로 한 번만 분석합니다. AI 분석이 실패하더라도 정해진 규칙에 따라 보고서를 생성하도록 대체 처리합니다.

### 🦄 쓰기 도구는 아예 존재할 수 없습니다

Zabbix 조회 도구 5개는 모두 읽기 전용으로 구성되어 있습니다.

| 도구 | 하는 일 | 내부에서 호출하는 Zabbix API |
|---|---|---|
| `zabbix_list_problems` | 현재 장애 목록 (호스트 이름 포함, 최대 100건) | `problem.get`, `trigger.get` |
| `zabbix_get_problem` | 장애 이벤트 한 건과 관련 감지 조건·수집 항목 조회 | `event.get`, `trigger.get` |
| `zabbix_get_host` | 서버 한 대의 가용성·그룹·네트워크 연결 정보·점검 여부 조회 | `host.get`, `hostinterface.get`, `maintenance.get` |
| `zabbix_list_items` | 서버의 수집 항목과 최신값 조회 (오래된 값은 별도 표시) | `item.get` |
| `zabbix_get_history` | 항목별 이력 최대 500개 조회 (24시간이 넘으면 추세 데이터로 대체) | `item.get`, `history.get`, `trend.get` |

허용 목록에 없는 호출은 **네트워크 요청이 전송되기 전에** 차단되며, 쓰기 도구가 등록되면 **에이전트 자체가 시작되지 않습니다.** 실수로 쓰지 않도록 주의하는 것이 아니라 애초에 쓸 수 없도록 설계한 것입니다.

### 🦄 분석 화면과 근거

- 화면 한 장에 **무엇이 발생했는지 · 왜 발생했는지 · 어떻게 대응할지**를 정리합니다.
- 원인 후보는 최대 3개까지 제시하고, 신뢰 수준은 낮음·보통·높음으로만 표시합니다. 백분율은 사용하지 않습니다.
- 모든 수치에는 근거 식별 번호가 붙으며, 오래된 값은 "확인할 수 없음"으로 표시합니다.
- 모든 도구 호출은 근거 기록(EvidenceTrace)으로 저장합니다.
- 변경 계획의 위험 등급은 규칙 파일이 결정합니다. 조회는 A등급, 승인이 필요한 변경은 B등급, 금지된 작업은 C등급입니다.

지금까지 장애 **521건**을 접수해 보고서 **516건**을 생성했으며, 도구 호출은 **3,597번** 기록됐습니다. 과거 장애 보고서 479건과 대응 절차서를 검색해 유사한 과거 장애를 근거로 연결하고, 결과는 담당자에게 보고서당 한 번씩 이메일로 전달합니다.

## 🦮 4. AI 업무 플랫폼: 회사를 함께 운영하는 AI 동료들

<img src="/images/blog/ai/29/images4.webp"/>

### 🦄 필요한 서비스만 켜서 사용합니다

AI 업무 플랫폼은 회사 서버에 설치해 사용하는 AI 업무 서비스 모음입니다.
총 15개 서비스 중 필요한 것만 활성화해 사용하며, 총괄 AI 아래에서 8개 부서 AI가 업무를 수행합니다.

| 부서 AI | 하는 일 |
|---|---|
| 고객지원 | 문의 분류, 답변 초안 3개 작성, 불만·환불·보상 처리 |
| 재무 | 장부 관리, 결산, 거래 대조, 장애 비용 기록 |
| 데이터분석 | 장애 영향 분석(실패 주문·영향 고객·피해 금액), 주요 지표 분석 |
| 인사 | 사건 기록, 에이전트 성능 평가 |
| 마케팅 | 공지, 배너, 쿠폰 관리 |
| 기획 | 요청 사항을 기획서로 작성 |
| 개발 | 코드 작성, 검수, 배포 |
| 인프라 | 장애 진단, 복구 확인 (장애 대응 시스템 연동) |

### 🦄 에이전트 간 통신(A2A): 카드 → 요청 → 회신

1. 모든 에이전트는 **에이전트 카드**에 자신이 수행할 수 있는 업무를 공개합니다.
2. 총괄 AI는 각 카드를 수집해 "기능 → 담당 부서" 연결표를 만들고, 필요한 기능을 보유한 에이전트에게 업무를 요청합니다.
3. 회신에는 **처리 결과와 근거**가 함께 포함됩니다. 근거가 없는 수치는 결과로 인정하지 않습니다.
4. 실패하면 재시도하고, 권한이 없다면 동일한 기능을 수행할 수 있는 다른 부서로 요청을 전달합니다. 서비스가 꺼져 있다면 **사람의 업무함**으로 넘깁니다.

이러한 대화는 모두 하나의 대화방에 기록되므로 누가 누구에게 어떤 업무를 요청했는지 언제든 다시 확인할 수 있습니다.

### 🦄 안전 관문과 기억

상태를 변경하는 모든 작업은 안전 관문을 거칩니다. **A등급은 즉시 실행, B등급은 다른 AI의 검증, C등급은 사람의 승인**을 거치며, 안전 관문이 응답하지 않으면 사람의 승인 단계로 전환해 작업을 차단합니다.

완료된 사건은 인사 AI가 원인·조치·복구 시간까지 기록합니다. 이후 비슷한 장애가 발생하면 임베딩 기반 검색으로 과거 기록을 찾고, **유사도가 0.85를 넘으면 당시의 조치를 다시 실행**합니다.

## 🦮 5. 세 플랫폼이 함께 움직이는 장면

<img src="/images/blog/ai/29/images5.webp"/>

실제로 쇼핑몰에 결제 장애를 발생시켜 테스트했습니다.

| 단계 | 담당 | 처리 내용 |
|---|---|---|
| 감지 | 쇼핑몰 | 이벤트 발행 (Zabbix 경보는 장애 대응 시스템 → 인프라 AI 경로로도 전달 가능) |
| 사건 생성 | 총괄 AI | 동일한 영역에서 발생한 신호를 하나의 사건으로 통합 |
| 진단 | 인프라 AI | 장애 원인 진단 |
| 과거 사건 검색 | 인프라 AI | 유사한 과거 사건 검색 (유사도 88%, 1초 만에 검색) |
| 영향 분석 | 데이터분석 AI | 실패 주문 6건, 영향 고객 6명, 피해 금액 156,300원 산출 |
| 조치 | 인프라 AI | 과거와 동일한 방식으로 즉시 처리하고, 되돌리기 단계는 생략 |
| 공지·보상 | 마케팅·고객지원 AI | 쇼핑몰 점검 배너 게시, 영향받은 고객 전원에 대한 보상 요청 |
| 예외 처리 | 총괄 AI | 복구 여부가 불확실해 정상화 공지를 발송하지 않고 사람에게 전달 |
| 기록 | 재무·데이터분석 AI | 장애 비용 장부 기록, 처리 시간 정리 |

**사건이 생성된 지 2분 47초 만에 처리가 마무리됐으며, 동일한 장애의 복구 시간은 22초에서 AI가 과거 조치를 재사용했을 때 1초로 단축됐습니다.**

복구 여부가 불확실할 때 억지로 "정상화되었습니다"라는 공지를 보내지 않은 점이 중요하다고 생각합니다. 잘못된 공지는 장애 자체보다 고객에게 더 큰 혼란을 줄 수 있기 때문입니다.

고객 문의부터 환불까지도 동일한 방식으로 처리합니다. 10만 원 미만은 즉시 환불하고, 그 이상은 사람이 승인합니다. 새로운 기능 요청이 들어오면 기획 AI가 기획서를 작성하고, 개발 AI가 코드 작성과 검수, 배포까지 이어서 수행합니다. 단, 실제 운영 환경에 배포하는 마지막 단계는 사람이 승인합니다.

## 🦮 마치며

저희가 생각하는 업무 전환(AX)은 **AI를 단순히 사용하는 것이 아니라, AI가 함께 일하는 회사를 만드는 것**입니다. 그리고 그런 회사가 신뢰를 얻으려면 AI가 할 수 있는 일이 명확해야 하는 만큼, **AI의 안전 규칙이 명확해야 한다**고 생각합니다.
