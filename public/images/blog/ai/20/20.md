## 🦮 Zabbix AI 서비스 구성, 역할을 나눈 이유

이 그림은 **Zabbix AI**를 기능 상자 하나로 그리지 않는다. 화면, API, AI Agent, 스케줄러, MCP 서버, 저장소, 바깥의 Zabbix와 AWS와 LLM을 각각 다른 칸에 둔다. 사용자는 웹 화면 하나만 열고, AI Agent는 Zabbix와 AWS를 각자의 MCP 서버로만 조회한다.

이 글은 그림의 상자와 화살표가 무슨 말인지, 왜 이렇게 나누라고 하는지를 적는다. 코드를 붙이는 글이 아니다. 나중에 폴더를 나눌 때 이 경계를 그대로 쓰기 위한 메모다.

## 🦮 1. 그림이 먼저 말하는 것

점선 안은 **컨테이너 내부 네트워크**다. 밖에는 사용자와, 운영 Zabbix, AWS API, LLM 게이트웨이가 있다. 점선 안에서 밖으로 공개되는 웹 화면은 Frontend 하나다.

화살표 이름은 다섯 가지로 줄어 있다.

| 이름 | 뜻 |
|---|---|
| HTTPS | 사용자 브라우저와 웹 화면 사이. 사내 계정으로 로그인한 뒤의 접속 |
| API | 화면이 화면용 API 서버에 일을 부탁하는 선 |
| AI | 그 API 서버가 AI Agent에게 대화와 조회를 넘기는 선 |
| MCP | AI Agent가 Zabbix MCP, AWS MCP를 부르는 선 |
| 조회 | MCP 서버나 스케줄러가 운영 Zabbix, AWS API를 읽기만 하는 선 |

쓰기가 그림에 있는 곳은 하나다. 스케줄러가 공유 데이터 저장소에 **수집 결과 쓰기**를 한다. 그 저장소를 읽는 권한은 Backend라고 적혀 있다.

호출이 향하는 큰 방향은 그림 맨 아래 설계 원칙과 같다. **화면 → API → AI Agent → MCP(Zabbix · AWS).** 화면이 MCP를 바로 부르지 않고, AI Agent가 운영 Zabbix에 바로 붙지 않는다.

## 🦮 2. 왜 한 통으로 만들지 않나

기능을 한 프로세스에 넣으면 처음에는 빠르다. 화면 버튼, 로그인, 메일, Zabbix 조회, AWS 조회, 매일 아침 리포트, LLM 호출이 한 저장소 안에 있다. 상자를 나눈 이유는 그 편이 편해서가 아니다. 고칠 때와 망가질 때의 범위가 다르기 때문이다.

그림의 설계 원칙은 세 줄이다.

1. **서비스별 컨테이너로 분리한다.** 수정, 배포, 호출 방향은 화면 → API → AI Agent → MCP 한 방향이다.
2. **AI Agent 하나만 사이트, Claude, 다른 에이전트와 함께 쓴다.** 다른 시스템은 조회가 필요하면 MCP 서버로만 말한다.
3. **운영 Zabbix는 조회만 한다.** 변경은 계획(미리보기)까지만 만들고, 확인되지 않은 값은 「확인 안 됨」으로 적는다. 「확인 없음」이라고 적지 않는다.

이 세 줄을 풀면 나누는 이유가 보인다.

**고치는 단위가 다르다.** 화면 문구를 바꿀 때마다 Zabbix에 붙는 서버까지 다시 배포할 필요가 없다. MCP 서버는 조회 도구가 안정되면 자주 안 바뀐다. 스케줄러는 하루에 한 번 도는 일이라 웹 요청의 배포 주기와 다르다. 컨테이너로 나누면 그 주기대로 고치고 올린다.

**망가지는 범위가 다르다.** AI Agent가 틀린 도구를 골라도, 그 프로세스가 운영 Zabbix의 설정을 쓰는 권한을 아예 갖지 않으면 운영 쪽은 그대로다. 그림은 운영 Zabbix 칸에 「조회 API만 사용 (설정 변경·쓰기 없음)」이라고 적어 두었다. Backend, Zabbix MCP, Scheduler만 조회한다.

**비밀이 머무는 곳이 다르다.** AWS 자격, Zabbix 조회 계정, LLM 키를 브라우저에 넣으면 페이지를 연 사람이 그 키를 볼 수 있다. 그림에서 브라우저와 닿는 칸은 Frontend뿐이다. AWS MCP는 AWS API만 접근하고, LLM 게이트웨이는 AI Agent만 호출한다.

**밖으로 여는 문이 하나다.** 점선 위 문구가 「외부 공개는 웹 화면 하나」다. Zabbix MCP와 AWS MCP는 컨테이너 안에 있고, 인터넷에 포트를 열지 않는다. 사용자가 MCP 주소로 직접 들어와 서버 목록을 읽는 길을 만들지 않겠다는 뜻이다.

## 🦮 3. 용어

그림에 적힌 말을, 이 구성에서 가리키는 것으로만 적는다.

### 🦄 컨테이너

**컨테이너**는 프로세스와 그 프로세스가 보는 파일, 라이브러리를 한 덩어리로 떼어 실행하는 단위다. 이 그림의 점선 안 칸은 각자 컨테이너다. Frontend, Backend, AI Agent, Scheduler, AWS MCP, Zabbix MCP가 그렇다. 공유 데이터 저장소도 컨테이너 안 칸으로 그려져 있다.

한 운영체제 위에 여러 칸을 올리되, 칸마다 듣는 포트와 환경 변수를 따로 둔다. 「서비스별 컨테이너로 분리」는 폴더를 보기 좋게 나누라는 말이 아니다. 배포와 재시작의 단위를 서비스와 맞추라는 말이다.

### 🦄 Frontend

**Frontend**는 브라우저에 그려지는 웹 화면이다. 그림은 React라고 적었다. 하는 일은 현황, 장애 대응, 비용 절감, 리포트, AI 어시스턴트, 관리자다. 이 중에서 밖으로 공개되는 서비스는 이 칸뿐이다.

화면은 Zabbix에도, AWS에도, LLM에도 직접 붙지 않는다. 붙는 상대는 Backend 하나다. 화살표 이름은 API다.

### 🦄 Backend, BFF

**Backend**는 화면용 API 서버다. 괄호 안 말이 **BFF**다. BFF는 Backend for Frontend, 화면을 위한 백엔드다.

일반 API 서버는 여러 클라이언트가 같이 쓰는 자원 중심으로 경로를 만든다. BFF는 이 웹 화면이 필요한 모양으로 응답을 만든다. 대시보드 숫자, 리포트, 비용 절감, 메일 발송, 장애 알림, 로그인, 권한이 이 칸에 있다. AI와의 대화는 여기서 끝내지 않고 AI Agent로 중계한다.

화면이 MCP를 직접 부르면, 브라우저 요청마다 Zabbix 도구 이름과 인증이 화면에 새어 나간다. BFF를 두면 화면은 「이 대시보드를 달라」「이 질문을 전달해 달라」만 말한다. Zabbix를 어떻게 조회하는지는 화면 코드에 없다.

### 🦄 AI Agent

**AI Agent**는 문장을 바로 완성만 하는 채팅 함수가 아니다. 이번 말에 도구가 필요한지 고르고, 필요하면 도구를 호출하고, 돌아온 결과를 보고 답을 쓴다. 그림에는 「질의응답, 화면 없음」이라고 적혀 있다. 포트를 열어 페이지를 제공하지 않는다.

도구는 LLM과 Zabbix MCP, AWS MCP다. 사이트, Claude, 다른 에이전트와의 호출도 이 칸만 한다. Backend가 Claude를 직접 부르지 않고, Scheduler도 LLM을 부르지 않는다. 모델 키가 퍼지는 칸을 하나로 줄이려는 배치다.

변경은 이 칸에서 **계획(미리보기)** 까지만 만든다. 운영에 바로 쓰지 않는다. 미리보기는 사람이 확인하기 전의 초안이다. 확인 전 초안을 운영 변경으로 실행하지 말라는 말이 설계 원칙 세 번째 줄과 만난다.

### 🦄 MCP

**MCP**는 Model Context Protocol, 모델 컨텍스트 프로토콜이다. 모델이 외부 시스템을 부를 때 쓰는 연결 방식의 이름이다. 함수 이름, 그 함수가 받는 값, 돌려주는 값의 모양을 정해 둔 서버를 하나 띄우고, 모델 쪽은 그 서버의 도구 목록을 읽어 호출한다.

이 그림에서 MCP 서버는 두 개다.

- **AWS MCP**: AWS를 조회한다. 인스턴스 사양, 단가, 적정 크기 권고. 호출자는 AI Agent뿐이다.
- **Zabbix MCP**: Zabbix를 조회한다. 장애, 서버, 지표, 알림 설정. 쓰기 도구는 없다. 호출자는 AI Agent뿐이다.

MCP를 두는 이유는 모델에게 AWS SDK나 Zabbix API 문서를 통째로 맡기지 않으려고다. 모델이 고를 수 있는 행동을, 그 서버에 올려 둔 도구 목록으로 제한한다. Zabbix MCP에 쓰기 도구를 넣지 않으면, 모델이 설정을 바꾸는 선택지 자체가 없다.

다른 시스템이 조회할 때도 운영 Zabbix 주소로 바로 가지 말고 이 MCP 서버로만 말하라는 것이 두 번째 설계 원칙이다. 조회 계정과 허용 도구가 MCP 서버 한곳에 모인다.

### 🦄 스케줄러

**Scheduler**는 사람의 클릭 없이 시간이 되면 도는 작업이다. 그림에는 「정기 수집, 포트 없음」이라고 적혀 있다. 웹으로 접속하는 문이 없다.

하는 일은 하루 한 번 지표를 모으고, 서버 사양을 모으고, 보관 기간이 지난 기록을 지리는 것이다. 결과는 공유 데이터 저장소에 쓴다. 화살표는 「수집 결과 쓰기」다. 대시보드가 열릴 때마다 Zabbix에 같은 집계를 다시 묻지 않게, 밤에 모아 둔 표를 Backend가 읽는다.

스케줄러가 화면이나 에이전트 안에 있으면, 웹 프로세스가 재시작될 때 수집 시각도 같이 흔들린다. 포트를 열지 않는 칸으로 빼면 수집은 요청량과 무관하게 돈다.

### 🦄 공유 데이터 저장소

**공유 데이터 저장소**는 수집된 지표, 대화, 변경 계획을 두는 칸이다. 쓰는 쪽은 스케줄러다. 읽는 쪽은 Backend다. 그림은 「읽기 전용: Backend」라고 적었다.

쓰기를 한 칸으로 모으면, 대시보드용 숫자가 누가 갱신했는지가 분명하다. Backend가 같은 표를 고치기 시작하면 아침 리포트와 화면 숫자가 어떤 쪽이 최신인지 달라진다. 그래서 읽기와 쓰기를 역할로 나눈다.

대화와 변경 계획도 이 저장소 항목에 들어 있다. 변경 계획은 AI Agent가 만든 미리보기이지, 운영에 이미 적용된 값이 아니다.

### 🦄 운영 Zabbix

**Zabbix**는 서버와 서비스의 지표, 장애, 알림을 모아 보는 모니터링 도구다. 그림의 운영 Zabbix는 회사의 실제 모니터링이다. 컨테이너 밖, 외부 서비스 칸에 있다.

이 칸의 사용법은 조회 API뿐이다. 설정 변경과 쓰기는 없다. 조회하는 쪽은 Backend, Zabbix MCP, Scheduler다. AI Agent 이름은 여기 없다. AI Agent는 Zabbix MCP를 통한다.

### 🦄 AWS API

**AWS API**는 아마존 웹 서비스의 조회 인터페이스다. 인스턴스 사양, 적정 크기 권고가 이 글의 범위다. 접근은 AWS MCP만 한다. 화면이나 Backend가 AWS 키를 들고 있지 않다.

### 🦄 LLM 게이트웨이

**LLM**은 Large Language Model, 큰 언어 모델이다. 문장을 받고 문장 또는 도구 호출을 돌려준다. **게이트웨이**는 그 모델로 가는 통로를 한곳에 모은 서버다. 사내 LLM 게이트웨이는 모델 주소, 키, 호출량을 여기서 관리한다.

그림은 「AI Agent만 호출」이라고 적었다. Frontend가 모델 주소로 직접 가면 키가 브라우저 쪽에 있어야 하고, 어떤 화면 기능이 모델을 얼마나 불렀는지 한곳에서 볼 수 없다. Scheduler가 모델을 부르지 않는 이유도 같다. 정기 수집은 조회와 저장이면 되고, 문장 생성은 사람이 질문할 때 AI Agent가 한다.

### 🦄 HTTPS

**HTTPS**는 HTTP를 암호화한 웹 접속이다. 그림에서는 사용자 브라우저와 Frontend 사이에만 적혀 있다. 사내 계정으로 로그인한 뒤의 접속이다. 컨테이너 내부의 API, AI, MCP 선은 이 이름과 따로 그린다. 안의 선은 공개 웹이 아니다.

### 🦄 조회와 쓰기

**조회**는 읽기다. 지표를 가져오고, 인스턴스 사양을 가져오고, 장애 목록을 가져온다. 상대 시스템의 설정을 바꾸지 않는다.

**쓰기**는 이 그림에서 공유 데이터 저장소에 수집 결과를 넣는 일이다. 운영 Zabbix에 대한 쓰기는 그림에 없다. AWS 설정 변경도 없다.

### 🦄 계획(미리보기), 확인 안 됨

**계획(미리보기)** 은 적용 전에 사람에게 보여주는 초안이다. 예를 들어 인스턴스 크기를 줄이자는 문장, 알림 임계값을 바꾸자는 문장이다. AI Agent는 여기까지 만들고, 운영 Zabbix나 AWS에 그 변경을 실행하지 않는다.

**확인 안 됨**은 아직 조회하지 못했거나, 조회 결과가 그 값을 말해 주지 않은 상태다. **확인 없음**은 조회했고 그 항목이 없다고 말한 것처럼 들린다. 그림의 원칙은 확인되지 않은 값을 「확인 없음」으로 적지 말라는 것이다. 없는 것과, 아직 모르는 것을 같은 말로 적으면 장애 대응에서 없는 호스트와 조회가 실패한 호스트가 섞인다.

## 🦮 4. 칸마다 하는 일

### 🦄 사용자 (웹 브라우저)

웹 브라우저로 접속하는 사람이다. 사내 계정으로 로그인한 뒤 Frontend만 본다. Zabbix 화면을 직접 열라는 구성이 아니다. 현황과 리포트와 어시스턴트는 이 서비스의 화면 안에 있다.

### 🦄 Frontend, React

로그인 이후의 페이지다. 현황, 장애 대응, 비용 절감, 리포트, AI 어시스턴트, 관리자. React로 그린다고 적혀 있다. 서버 상태는 Backend가 주고, 어시스턴트 문장은 Backend가 AI Agent에게 중계한 결과다.

### 🦄 Backend, 화면용 API 서버

대시보드, 리포트, 비용 절감, 메일, 장애 알림, 로그인, 권한. 공유 저장소의 수집 결과를 읽어 화면에 맞는 응답으로 바꾼다. 대화는 AI Agent로 넘긴다.

이 칸이 BFF인 이유는 화면 종류가 여럿이기 때문이다. 대시보드와 리포트와 관리자는 필요한 필드가 다르다. Zabbix 원본 응답을 그대로 브라우저에 내리면 화면마다 그 형식을 해석해야 한다. BFF가 화면용 모양으로 맞춘다.

### 🦄 AI Agent

질의응답만 한다. 페이지는 없다. LLM으로 말을 고르고, Zabbix MCP와 AWS MCP로 사실을 조회한다. 변경안은 미리보기 계획으로 남긴다. 사이트와 Claude와 다른 에이전트 호출이 필요하면 이 칸에서만 한다.

### 🦄 Scheduler

포트가 없다. 하루 한 번 지표와 서버 사양을 모으고, 보관 기간이 지난 기록을 지운다. 모아 둔 것은 공유 저장소에 쓴다. 화면이 켜져 있지 않아도 돌아야 하는 일이라 웹 칸 밖에 있다.

### 🦄 AWS MCP와 Zabbix MCP

둘 다 컨테이너 안 MCP 칸이다. AWS MCP는 인스턴스 사양, 단가, 적정 크기 권고를 AWS API에 조회한다. Zabbix MCP는 장애, 서버, 지표, 알림 설정을 운영 Zabbix에 조회한다. 쓰기 도구는 없다. 둘 다 호출자는 AI Agent다.

스케줄러의 정기 수집이 같은 조회를 써야 하는지는 그림의 「다른 시스템은 MCP 서버로만」이라는 원칙과 맞닿아 있다. 운영 Zabbix를 조회하는 이름으로 Backend, Zabbix MCP, Scheduler가 함께 적혀 있으므로, 스케줄러는 조회 주체로는 들어가 있다. 그 조회도 MCP에 올려 둔 도구만 쓰라는 쪽이 두 번째 원칙이다. 스케줄러가 Zabbix 주소와 계정으로 직접 붙는 코드를 따로 두지 않는 편이 이 그림과 맞다.

### 🦄 운영 Zabbix, AWS API, LLM 게이트웨이

셋 다 점선 밖이다. 이 서비스가 그 시스템 자체를 대체하지 않는다. 운영 Zabbix는 원래 쓰던 모니터링이고, AWS API는 인프라 조회이고, LLM 게이트웨이는 사내 모델 통로다. 이 서비스는 그 셋 앞에 화면과 조회 도구와 수집을 붙인 것이다.

## 🦮 5. 요청이 지나가는 길

### 🦄 지금, 이 서버 장애를 물을 때

1. 사용자가 브라우저에서 어시스턴트에 적는다. 접속은 HTTPS, 상대는 Frontend뿐이다.
2. Frontend는 Backend에 API로 그 말을 넘긴다.
3. Backend는 로그인과 권한을 본 뒤 AI Agent로 중계한다.
4. AI Agent는 도구가 필요하다고 보고 Zabbix MCP를 부른다. 선 이름은 MCP다.
5. Zabbix MCP는 운영 Zabbix를 조회만 한다.
6. 돌아온 지표로 AI Agent가 LLM 게이트웨이에 답을 맡긴다. LLM을 부르는 칸은 AI Agent뿐이다.
7. 문장은 Backend를 거쳐 화면에 나온다.

이 길에 쓰기는 없다. 장애 설정을 바꾸는 버튼이 있어도, 그 결과는 계획이 되고 운영 Zabbix에는 쓰지 않는다. 조회에 실패한 항목은 「확인 안 됨」이다.

### 🦄 아침에 대시보드를 열 때

1. 스케줄러가 이미 지표와 서버 사양을 모아 공유 저장소에 써 두었다.
2. 사용자가 Frontend를 연다.
3. Frontend가 Backend에 대시보드를 요청한다.
4. Backend는 공유 저장소를 읽기만 해서 화면용 숫자로 바꾼다.

사람이 페이지를 열 때마다 운영 Zabbix에 같은 하루 치를 다시 묻지 않는다. 실시간 한 건이 필요하면 그때 AI Agent와 Zabbix MCP의 조회가 따로 나간다. 모아 둔 표와, 방금 조회한 값을 한 함수 안에서 뒤섞지 않으려고 칸을 나눈 것이다.

### 🦄 인스턴스 크기를 물을 때

1. 화면 질문이 Backend를 거쳐 AI Agent에 간다.
2. AI Agent는 AWS MCP를 부른다.
3. AWS MCP만 AWS API를 조회한다. 인스턴스 사양, 단가, 적정 크기 권고.
4. 크기를 줄이자는 문장이 필요하면 계획으로 남긴다. AWS 설정을 이 서비스가 변경하지는 않는다.

## 🦮 6. 이렇게 나누지 않으면

화면 컴포넌트 안에 Zabbix 주소와 토큰이 있으면, 그 번들은 브라우저가 받는 파일이다. 개발자 도구로 주소와 토큰이 보인다. Frontend를 API 뒤로 두는 이유가 이것이다.

Backend 핸들러 안에 LLM 호출과 Zabbix 쓰기와 메일 발송이 같이 있으면, 리포트 문구를 고치는 배포가 조회 도구 버그와 같이 나간다. 호출 방향을 화면 → API → AI Agent → MCP로 고정하면, 리포트 수정은 Backend나 Frontend에서 끝나고 MCP 서버는 그대로 둔다.

운영 Zabbix에 쓰기 도구를 넣어 두면, 모델이 도구 목록에서 그 도구를 고를 수 있다. 프롬프트에 「쓰지 마라」고 적는 것보다, 도구를 만들지 않는 편이 강하다. 그림이 Zabbix MCP에 「쓰기 도구 없음」이라고 적은 이유다.

수집을 웹 요청 처리 중에 하면, 사용자가 없을 때는 하루 치가 안 쌓인다. 스케줄러를 포트 없는 칸으로 두고 저장소에 쓴 뒤, Backend만 읽게 하면 화면 접속과 수집 시각이 분리된다.

확인하지 못한 값을 「없음」으로 적으면, 다음 사람은 그 호스트가 없다고 이해한다. 조회 실패와 실제 부재는 다른 사건이다. 그래서 모르는 값은 「확인 안 됨」으로 남긴다.
