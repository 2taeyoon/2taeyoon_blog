## 🦮 앱이 느릴 때 클로드에게 시키는 말 31가지

"사이트가 느려요, 고쳐 주세요"라고만 하면 클로드도 어디서부터 손대야 할지 모릅니다. 반대로 **무엇을 재고, 어떤 후보 중에서 고르고, 고치기 전에 무엇을 보여 달라고 할지**까지 정해서 부탁하면 결과가 확실히 달라집니다.

이번 글은 해외 개발자들이 공유하는 "앱 속도 개선 체크리스트 31가지"를 우리말로 다시 정리하고, 제가 실제로 재무 AI 화면을 Lighthouse로 재고 고친 결과까지 함께 담았습니다.

먼저 결론부터 말씀드리겠습니다.

1. **고치기 전에 먼저 잽니다.** PageSpeed Insights나 크롬의 Lighthouse로 성능 점수와 LCP(가장 큰 내용이 뜨는 시간)를 적어 둡니다.

2. **31가지를 한 번에 붙여 넣되, 전부 하라고 하지 않습니다.** "이 앱에 맞는 것만 골라서, 바꾸기 전에 표로 먼저 보여 달라"고 부탁합니다.

3. **고친 뒤 같은 조건으로 다시 잽니다.** 느린 폰과 느린 인터넷을 흉내 내서 다시 재야 실제 사용자가 느끼는 속도를 알 수 있습니다.

4. 저는 이 방식으로 재무 AI 화면의 성능을 **66점에서 94점**으로, 첫 화면이 뜨는 시간을 **2.7초에서 0.8초**로 줄였습니다.

## 🦮 2. 1단계: 먼저 속도 재기

### 🦄 PageSpeed Insights로 재기

`pagespeed.web.dev`에 접속해서 내 앱 주소를 넣고 **Analyze**를 누릅니다. 1분 정도 지나면 결과가 나옵니다.

결과 화면은 이 순서로 보면 됩니다.

| 항목 | 의미 |
|---|---|
| Mobile · Desktop | 폰 기준과 컴퓨터 기준 결과가 따로 나옵니다. 느린 폰 문제는 **Mobile**부터 봅니다 |
| 성능 점수 | 100점 만점입니다. 잴 때마다 몇 점씩 달라질 수 있습니다 |
| 색 | 빨강 0~49, 주황 50~89, 초록 90~100 |
| FCP (First Contentful Paint) | 화면에 내용이 처음 조금이라도 보이기까지 걸린 시간 |
| LCP (Largest Contentful Paint) | 화면에서 가장 큰 사진·글 덩어리가 뜨기까지 걸린 시간 |
| TBT (Total Blocking Time) | 눌러도 반응하지 못하고 막혀 있던 시간의 합 |
| CLS (Cumulative Layout Shift) | 불러오는 동안 화면이 갑자기 밀린 정도 |
| Speed Index | 내용이 눈에 보이게 채워지는 빠르기 |

**성능 점수와 LCP를 꼭 적어 두세요.** 고친 뒤 이 두 숫자로 비교합니다.

### 🦄 사내 화면은 크롬 Lighthouse로

로그인해야 보이거나 사내망에만 있는 화면은 PageSpeed가 들어갈 수 없습니다. 이럴 때는 크롬에서 그 화면을 열고 개발자 도구(F12, 맥은 Cmd + Option + I)의 **Lighthouse** 탭에서 같은 검사를 돌리면 됩니다. 터미널에서 `npx lighthouse <주소>`로 돌려도 같은 항목을 잴 수 있습니다.

## 🦮 3. 2단계: 클로드 코드에 31가지 붙여 넣기

터미널에서 앱 폴더로 이동한 뒤 클로드 코드를 켭니다.

```bash
cd 내-앱-폴더
claude
```

그리고 입력창에 아래 글을 그대로 붙여 넣습니다.

```text
내 앱이 느려서 사용자가 떠날까 봐 걱정이야.
먼저 코드를 살펴보고, 아래 31가지 중 이 앱에 해당하는 것만 골라 줘.
무엇을 어떻게 바꿀지 표로 먼저 보여 주고, 내가 승인하면 그때 고쳐 줘.

1. 데이터를 받는 동안 뼈대 화면(skeleton)을 먼저 보여 주기
2. 이미지는 WebP나 AVIF로 바꾸기
3. 같은 요청이 동시에 여러 번 나가지 않게 막기
4. 검색·자동 완성은 입력이 멈춘 뒤에 요청하기(debounce)
5. 긴 목록은 페이지로 나눠 받기(pagination)
6. 이미지·글꼴 같은 정적 파일은 CDN으로 보내기
7. 오래 걸리는 작업은 작업 큐로 넘겨 뒤에서 처리하기
8. 반복문 안에서 하나씩 조회하지 말고 한 번에 묶어 조회하기(N+1 쿼리)
9. 텍스트 응답은 Brotli·Gzip으로 압축하기
10. 자주 읽는 데이터는 Redis 같은 캐시에 저장하기
11. 쓰지 않는 패키지와 코드 지우기
12. 외부 API 요청에는 시간 제한(timeout) 걸기
13. AI 응답은 생성되는 대로 흘려보내기(streaming)
14. 서버 응답 전에 화면부터 바꿔 두기(optimistic update)
15. 화면 아래쪽 이미지는 나중에 불러오기(lazy loading)
16. 서로 상관없는 요청은 동시에 보내기(Promise.all)
17. 자주 검색하는 조건에는 데이터베이스 인덱스 만들기
18. 느린 요청을 추적하는 도구 붙이기(OpenTelemetry)
19. 서버는 데이터베이스와 같은 지역(region)에 두기
20. 페이지는 서버나 빌드 단계에서 미리 만들기(SSR·정적 생성)
21. 채팅 위젯·분석 도구 같은 외부 스크립트는 나중에 불러오기(async·defer)
22. 자바스크립트는 페이지별로 나눠서 받기(code splitting)
23. 아주 긴 목록은 보이는 줄만 그리기(virtualization)
24. 데이터베이스에서 필요한 열만 가져오기
25. 데이터베이스 연결은 풀(pool)로 재사용하기
26. 바뀐 게 없으면 다시 그리지 않기(memo)
27. 바뀌지 않는 파일은 브라우저 캐시에 오래 두기(Cache-Control)
28. 사용자가 많으면 여러 서버로 나누기(load balancing)
29. 글꼴 종류와 굵기 수 줄이기
30. 실제 사용자 속도를 계속 지켜보기(성능 모니터링)
31. 느린 폰과 느린 인터넷 조건으로 테스트하기
```

핵심은 첫 세 줄입니다. **"맞는 것만 골라서"**, **"표로 먼저"**, **"승인하면 그때"** 이 세 가지가 들어가야 클로드가 31가지를 전부 적용하다가 화면을 깨뜨리는 일을 막을 수 있습니다.

클로드 코드는 파일을 고치기 전에 매번 허락을 묻습니다.

| 선택지 | 동작 |
|---|---|
| Yes | 이번 수정 하나만 반영합니다 |
| Yes, and don't ask again this session | 이번 대화 동안은 더 묻지 않고 고칩니다 |
| No, and tell Claude what to do differently | 고치지 않고, 어떻게 바꿀지 다시 지시합니다 |

처음에는 **Yes**로 하나씩 확인하는 것을 추천드립니다. 이 31줄은 클로드 전용 문장이 아니라서 다른 코딩 AI에도 그대로 붙여 넣을 수 있습니다.

## 🦮 4. 3단계: 느린 폰 조건으로 다시 재기

### 🦄 PageSpeed나 Lighthouse 다시 돌리기

1단계와 똑같이 다시 재서 성능 점수와 LCP를 비교합니다. 측정 도구와 설정이 같아야 비교가 의미 있습니다.

### 🦄 크롬에서 느린 폰 흉내 내기

1. 개발자 도구의 설정(톱니바퀴)에서 **Throttling** 메뉴로 들어갑니다.
2. **CPU throttling presets**에서 **Calibrate**를 누르면, 내 컴퓨터 기준으로 저가형 폰(Low-tier)과 중급 폰(Mid-tier)이 몇 배 느린지 계산해 줍니다.
3. **Performance** 탭의 환경 설정에서 CPU를 **Mid-tier mobile**(더 가혹하게는 Low-tier mobile)로 고릅니다.
4. 네트워크도 느린 속도로 바꾼 뒤 새로 고침하고, **Local metrics**의 LCP를 확인합니다.

개발용 컴퓨터는 사용자 폰보다 훨씬 빠르기 때문에, 이 과정을 건너뛰면 "제 컴퓨터에서는 빠른데요?"라는 함정에 빠집니다.

### 🦄 "표로 먼저" 부탁하면 이렇게 나옵니다

클로드에게 바꾸기 전에 표를 먼저 보여 달라고 하면, 아래처럼 **지금 값, 바꿀 값, 깨질 수 있는 곳**을 정리해 줍니다. 실제로 재무 화면 밀림을 고칠 때 받은 표입니다.

| 항목 | 지금 | 바꿀 것 | 깨질 수 있는 곳 |
|---|---|---|---|
| 재무 AI 테스트 칸 | 첫 결과 전에는 아무것도 그리지 않다가 약 150px로 나타나 아래 화면 전체가 밀림 | 받는 동안 결과 칸과 같은 틀·높이의 뼈대를 그림 | 처음 몇백 ms 동안 회색 틀이 보임 |

이 표를 받기 전에는 글꼴 때문에 화면이 밀린다고 의심했습니다. 그런데 글꼴을 막고 다시 재도 밀림이 그대로여서, 원인을 이 칸 하나로 좁힐 수 있었습니다.

남은 감점은 권장사항의 **HTTPS**와 성능의 **HTTP/2**입니다. 둘 다 코드가 아니라 서버 설정이라 서버 담당에게 넘겼습니다.

## 🦮 6. 그대로 복사해 쓰는 부탁 5가지

`[ ]` 부분만 내 상황에 맞게 바꿔서 쓰시면 됩니다.

**측정 결과를 통째로 넘기고 싶을 때**

```text
PageSpeed 결과를 저장한 파일을 줄게.
Mobile 성능을 가장 많이 깎아 먹는 것부터 고쳐 줘.
하나 고칠 때마다 다시 재서 무엇이 달라졌는지 알려 줘.
```

**바꾸기 전에 무엇이 바뀌는지 보고 싶을 때**

```text
고치기 전에 무엇을 바꿀지 표로 먼저 보여 줘.
지금 값, 바꿀 값, 바꾸면 깨질 수 있는 곳을 같이 적어 줘.
```

**데이터를 불러오는 화면이 느릴 때**

```text
아무것도 바꾸기 전에, 어떤 쿼리가 느린지와
빠진 인덱스가 무엇인지부터 찾아 줘.
```

느린 화면의 원인이 인덱스 하나인 경우가 생각보다 많습니다. 수십 초 걸리던 조회가 인덱스 하나로 1초 아래로 줄어드는 일도 흔합니다.

**고친 뒤 얼마나 좋아졌는지 보고 싶을 때**

```text
고치기 전과 고친 뒤를 표로 비교해 줘.
성능 점수, LCP, 페이지 무게(MB)를 같이 적어 줘.
```

**느린 폰에서 무엇이 오래 걸리는지 알고 싶을 때**

```text
느린 폰과 느린 인터넷에서 첫 화면이 뜨기까지
무엇이 가장 오래 걸리는지 순서대로 찾아 줘.
```

### 🦄 내 앱에 맞춘 틀

31가지 목록 위에 아래 세 줄을 붙이면, 클로드가 훨씬 좁고 정확하게 고칩니다.

```text
내 [앱 종류] 앱이 [느린 화면]을 열 때 느려서 [사용자]가 떠날까 봐 걱정이야.
PageSpeed Mobile 성능은 [점수], LCP는 [초]야.
아래 31가지 중 이 화면에 맞는 것부터 3개만 골라서, 바꾸기 전에 표로 보여 줘.
```

제 재무 화면이라면 이렇게 채웠을 겁니다.

```text
내 재무 관리 앱이 일일 재무 화면을 열 때 느려서 담당자가 답답해할까 봐 걱정이야.
Lighthouse 성능은 66, LCP는 3.4초야.
아래 31가지 중 이 화면에 맞는 것부터 3개만 골라서, 바꾸기 전에 표로 보여 줘.
```

## 🦮 7. 자주 막히는 곳

### 🦄 점수는 높은데 페이지가 여전히 무거울 때

점수가 90점대여도 이미지가 수 MB씩 되면 느린 인터넷에서는 답답합니다. 이럴 때는 이미지 용량부터 줄이되, **CSS 지우기나 자바스크립트 지연 같은 강한 설정은 화면이 깨질 수 있으니** 하나씩 켜 보는 게 안전합니다.

```text
점수는 높은데 페이지가 무거워.
이미지 용량을 줄이는 방법 중에 화면이 깨지지 않는 것만 골라서,
바꾸기 전에 하나씩 보여 줘.
```

### 🦄 잴 때마다 점수가 다를 때

성능 점수는 측정할 때마다 몇 점씩 흔들립니다. 저도 고치기 전은 브라우저 개발자 도구, 고친 뒤는 Lighthouse CLI로 재서 몇 점 차이는 오차로 봤습니다. **같은 도구, 같은 설정으로 2~3번 재서 평균을 보는 것**이 가장 정확합니다.

---

## 🦮 마치며

정리하면, **재고 → 골라서 고치고 → 같은 조건으로 다시 재는** 세 단계입니다.

31가지를 모두 적용할 필요는 없습니다. 가장 느린 화면 하나를 골라서 틀에 넣어 보고, 고칠 때마다 성능 점수와 LCP를 한 줄씩 기록해 두면 어떤 수정이 얼마나 효과가 있었는지 한눈에 보입니다. 그리고 배포 전에는 느린 폰 조건으로 한 번 더 재 보는 습관을 들이시면 좋겠습니다.
