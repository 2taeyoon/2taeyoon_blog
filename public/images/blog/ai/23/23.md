## 🦮 AI 장애 대응 시스템 MVP

장애 대응 시스템은 장애가 났을 때 AI가 원인 후보와 근거를 정리하고, 규칙이 조치가 안전한지 검토하고, 마지막 결정은 사람이 하는 **장애 대응 코파일럿**이다.

모니터링 도구가 “문제가 생겼다”까지 알려 준다면, 이 시스템은 그다음을 맡는다. 무슨 문제인지 보고, 어떤 조치를 검토할지 정리한다.

다만 지금 구현은 서버를 직접 고치지 않는다. 운영 서버를 조회하고 분석해서 조치 계획을 보여 줄 뿐, 실제 변경은 하지 않는다.

<img src="/images/blog/ai/23/images1.webp"/>

### 🦄 전체 흐름

1. **서버에서 장애 발생:** CPU 사용량이 올라간다.
2. **Zabbix가 장애 감지:** 정해 둔 기준을 넘으면 장애 알람이 뜬다.
3. **AI Agent가 분석:** 데이터를 조회하고 원인 후보를 만든 뒤 근거를 확인한다.
4. **규칙으로 안전성 검사:** 위험도를 정하고 조치 계획 미리보기를 만든다.
5. **담당자가 결과 확인:** 현황 화면, 근거 ID, 리포트, 메일을 본다.

## 🦮 1. 기술 용어

### 🦄 1. 서버(Server)

프로그램이나 웹사이트가 돌아가는 데 필요한 데이터와 기능을 제공하는 컴퓨터, 또는 그 시스템이다. **장애 대응 시스템에서** CPU, 메모리, 디스크 상태를 확인하는 대상이다.

### 🦄 2. Zabbix

서버와 네트워크 장비의 상태를 모으고, 문제가 생기면 알람을 보내는 모니터링 도구다. **장애 대응 시스템에서** 장애를 찾는 쪽은 Zabbix다. AI가 장애를 감지하지 않는다. Zabbix가 잡은 정보를 가져와서 분석한다.

### 🦄 3. 원인 후보(Cause Candidates)

장애를 일으켰을 가능성이 있는 원인이다. 확정된 원인은 아니다. “원인 세 개”보다 “원인 후보 세 개”가 맞다. **예시** CPU를 많이 쓰는 프로세스, 메모리 부족, 특정 작업의 과부하.

### 🦄 4. 영향 범위(Impact Scope)

장애가 어느 서버, 서비스, 업무까지 미치는지다. 예를 들어 웹 서버 장애가 사용자 접속에 영향을 주는지를 보는 것이다. 서비스끼리의 의존 관계나 영향 데이터를 모으지 않았다면 범위를 확정할 수 없다. 확인한 것과 추정한 것을 구분해야 한다.

### 🦄 5. 근거 ID(Evidence ID)

분석 결과가 어느 조회에서 나왔는지 따라갈 수 있게 붙이는 번호다. “CPU 사용량이 높다”에 근거 ID가 있으면, 담당자가 그 데이터를 직접 열어 볼 수 있다. **AI가 한 말에 붙는 출처 번호**라고 보면 된다. 번호가 있다고 그 해석까지 맞다는 뜻은 아니다.

### 🦄 6. LLM (Large Language Model, 대규모 언어 모델)

사람의 말을 이해하고 문장을 만드는 AI 모델이다.

**장애 대응 시스템에서** 모아 둔 장애 데이터로 원인 후보와 설명 문장을 만든다. 지금은 Gemini 무료 모델을 쓰고, OpenAI 호환 인터페이스로 호출한다.

**핵심:** LLM이 시스템 동작을 전부 결정하지 않는다. 조회 순서와 위험도는 코드와 규칙이 정한다.

### 🦄 7. AI Agent(에이전트)

AI 모델에 도구, 데이터, 절차를 붙여 특정 일을 하게 만든 시스템이다.
LLM이 질문에 답하는 데 가깝다면, 에이전트는 정해진 도구로 정보를 모으고 여러 단계를 거쳐 결과를 만든다.
**장애 대응 시스템에서** 장애 정보를 조회하고, LLM에 분석을 맡기고, 결과를 검증한 뒤 리포트를 저장하고 전달한다.

### 🦄 8. Backend(백엔드)

화면 뒤에서 데이터를 처리하고, API를 열고, 로그인이나 메일 같은 서버 기능을 맡는 부분이다.

**장애 대응 시스템에서** 화면 요청을 받고, 공유 데이터 저장소에 있는 정보를 화면에 넘긴다. AI 분석은 별도 Agent가 한다.

### 🦄 9. Frontend(프론트엔드)

사용자가 보고 조작하는 화면이다.
**장애 대응 시스템에서** 장애 현황, 상세 분석, 근거 패널, 조치 미리보기, AI 어시스턴트를 보여 준다.

### 🦄 10. API (Application Programming Interface)

프로그램끼리 정해진 방식으로 요청하고 응답을 주고받게 만든 창구다.
장애 대응 시스템이 Zabbix API에 장애 목록을 요청하면, Zabbix가 그 정보를 돌려준다.

### 🦄 11. 공유 데이터 저장소(Shared Data Store)

여러 구성 요소가 같이 쓰는 데이터를 넣어 두는 곳이다.
Agent와 Scheduler가 기록하고, Backend는 읽기만 한다. Backend가 Agent나 Scheduler를 직접 부르지 않고, 저장해 둔 결과를 읽어서 화면에 올린다.

### 🦄 12. MCP

#### MCP란?

**MCP(Model Context Protocol)는 AI 애플리케이션이 바깥 도구와 데이터에 접근하는 방식을 맞춰 둔 규약**이다. MCP 자체는 AI 모델이 아니다. 장애 대응 시스템에서는 AI Agent가 바깥 데이터로 나가는 통로다.

#### MCP 관련 용어

| 용어 | 쉬운 설명 | 장애 대응 시스템에서의 역할 |
|---|---|---|
| MCP | AI와 도구 사이의 통신 규약 | 바깥 데이터로 나가는 경로 |
| MCP 서버 | 도구를 제공하는 프로그램 | Zabbix 조회 기능 제공 |
| MCP 도구(Tool) | AI가 요청할 수 있는 기능 하나 | 장애 목록 조회, 호스트 조회 등 |
| Zabbix MCP | Zabbix 데이터를 조회하는 MCP 서버 | 운영 데이터 접근 |
| 지식 검색 MCP | 과거 기록을 찾는 MCP 서버 | 과거 장애·런북 검색 |
| 셸(Shell) | 운영체제 명령을 넣는 환경 | Agent의 임의 명령 실행을 막음 |
| SSH | 원격 컴퓨터에 접속하는 방식 | 서버에 직접 들어가는 경로를 막음 |
| 임의 HTTP | 정해진 도구가 아닌 주소로 보내는 HTTP 요청 | 허용하지 않은 외부 통신을 막음 |

#### 12-1. MCP 도구는 등록된 것만 쓴다

AI Agent가 쓸 수 있는 기능은 등록된 것으로 제한한다. 자료에 적힌 기능은 장애 목록·상세, 호스트, 지표 항목, 이력 조회다. 도구 이름과 개수는 구현을 보고 확인해야 한다.

등록이 다섯 개라는 말과, 한 분석에서 네 종만 호출한다는 말이 같이 있다. 둘이 꼭 충돌하는 것은 아니다. 다섯 개는 등록된 수이고, 네 종은 그 흐름에서 실제로 부른 수일 수 있다.

#### 12-2. 쓰기 도구가 보이면 Agent가 기동하지 않는다

프로그램이 시작될 때 MCP가 제공하는 도구 목록을 검사한다. 허용하지 않은 쓰기 도구가 있으면 Agent는 켜지지 않는다.

#### 12-3. 모든 도구 호출이 근거가 된다

Agent가 어떤 도구를 불렀고 어떤 데이터를 받았는지 기록한다. 이 기록을 리포트 근거와 연결하면, 담당자가 분석 결과의 출처를 따라갈 수 있다. 호출 기록과 실제 데이터 값은 다르다. 호출이 남았다고 반환된 값이 맞거나 최신이라는 뜻은 아니다.

### 🦄 13. 가드레일(Guardrails)

AI가 하면 안 되는 행동을 막는 안전장치다. 장애 대응 시스템에서는 조회 허용 목록, 쓰기 도구 차단, 위험도 규칙, 근거 검증이 그 역할을 한다. AI에게 “조심해”라고 말하는 것이 아니라, **위험한 행동을 할 수 없게 만드는 것**이다.

### 🦄 14. 규칙 파일(YAML)

사람이 정한 정책과 설정을 구조로 저장하는 파일이다. YAML은 그 데이터를 읽기 쉽게 적는 문법이다. **장애 대응 시스템에서** `actions.yaml`에 조치 규칙을 두고 위험도를 판정한다. LLM이 위험도를 낮게 봐도, 최종 판정은 코드와 규칙이 한다.

### 🦄 15. 위험도 A·B·C

조치 계획이 얼마나 위험한지 나누는 등급이다. 규칙상 롤백 계획이 없는 변경은 더 엄격한 C로 내린다. A·B·C가 어떤 조건에서 붙고, 등급마다 무엇이 허용되는지는 규칙 파일을 봐야 한다. 등급 이름만으로 뜻을 정하면 안 된다.

### 🦄 16. 회귀 테스트(Regression Test)

기능을 더하거나 코드를 바꾼 뒤, 원래 되던 기능과 안전장치가 그대로인지 확인하는 테스트다.
**장애 대응 시스템에서** 위험한 동작이 실수로 통과되거나, 정상 동작이 쓸데없이 막히는지를 검사한다.

### 🦄 17. 머지(Merge)와 CI

머지는 서로 다른 코드 변경을 한 브랜치에 합치는 일이다. CI(지속적 통합)는 합치기 전에 테스트와 검사를 자동으로 돌리는 방식이다.
**장애 대응 시스템에서** 필수 안전 테스트가 통과하지 못하면 코드가 합쳐지지 않게 해 둔다. 이 통제가 실제로 먹는 범위는 GitHub 보호 규칙과 CI 설정에 따라 다르다.

## 🦮 2. 장애 시스템 워크플로우

서버 사용량이 올라가면 약 2분 뒤 Zabbix에 장애 알람이 뜨고, 현황 화면에도 새 장애가 올라온다.

상세 화면에서 Agent는 모아 둔 데이터로 원인 후보 세 가지와 영향 범위를 정리한다. 숫자에 붙은 근거 ID를 열면, 그 값이 어느 조회에서 나왔는지 볼 수 있다. 아래 조치 계획은 미리보기다. 실행 API와 실행 버튼은 없다. 분석 결과는 지정한 이메일로 전송된다.

어시스턴트에 백업 작업이 원인인지 물으면, 모아 둔 정보만으로 확인할 수 없는 내용은 먼저 `백업 작업이 원인이라는 근거는 수집된 데이터에 없습니다.`이라고 답한다. 이어서 지금 근거로 한 추정과, 더 봐야 할 항목을 안내한다.

이 경로를 만든 이유는, 장애가 나면 작업자 한 명이 화면을 여러 개 오가며 조회하고, 원인을 추정하고, 조치할지 판단하고, 보고서까지 써야 했기 때문이다. AI로 분석은 빨라질 수 있지만, 틀린 정보나 위험한 조치는 장애를 더 키울 수 있다.

그래서 원칙은 세 가지다.

- 운영 Zabbix는 조회만 허용한다.
- 조치는 미리보기까지만 제공한다.
- 근거가 없거나 오래된 값은 채우지 않고 `수집된 데이터에 없습니다.`로 둔다.

기존 AI 운영 도구도 승인과 가드레일을 제공한다. 이 시스템이 맞춘 부분은 기능 목록이 아니라, 지금 구현의 실행을 조회와 미리보기로 제한하고 필수 안전 규칙을 코드와 테스트로 강제하는 쪽이다. LLM이 위험도를 낮게 봐도 최종 판정은 코드와 규칙 파일이 한다. 필수 안전 테스트가 통과하지 못하면 코드는 합쳐지지 않는다.

## 🦮 3. 구성이 나뉘는 이유

Frontend, Backend, AI Agent, 그리고 Agent가 쓰는 MCP 서버 두 개로 나뉜다.

Frontend는 화면이다. Backend는 API, 로그인, 메일을 맡는다. AI Agent는 장애 데이터를 분석하고 리포트를 만든다. 바깥 데이터는 MCP로만 접근한다. 운영 Zabbix로 가는 요청은 조회 전용 경로를 거치고, 허용하지 않은 메서드는 요청을 보내기 전에 막는다.

Scheduler가 주기적으로 장애 정보를 모은다. Backend는 Agent를 직접 부르지 않고, 공유 데이터 저장소에 쌓인 결과를 읽는다. 서비스 사이의 업무 요청은 이 방향으로만 간다. 다만 HTTP 응답이나, 서버가 화면으로 보내는 이벤트까지 없다는 뜻은 아니다.

Agent 안의 순서는 코드가 정한다.

1. 장애, 호스트, 지표, 이력을 정한 순서로 조회한다.
2. LLM은 모아 둔 데이터로 분석 문장을 한 번 만든다. 실패하면 규칙 기반 리포트로 바꾼다.
3. 각 숫자에 근거 ID가 있는지 확인한다.
4. 조치 계획의 위험도는 규칙 파일과 코드가 판정한다. LLM이 적은 위험도는 최종 판정에 쓰지 않는다. 롤백 계획이 없는 변경은 더 엄격한 등급으로 올린다.

Zabbix 쪽 MCP는 조회 도구만 둔다. 셸, SSH, 임의의 HTTP로 서버에 직접 들어가는 경로는 막는다. 지식 검색 MCP는 과거 장애 기록과 런북을 찾는다. 도구 호출 기록은 리포트 근거와 연결된다.

## 🦮 4. 측정값을 읽는 법

안전 회귀 테스트 7개에서 위험한 동작이 잘못 통과한 경우는 0건이다. 정상 동작을 쓸데없이 막은 경우도 테스트 3개에서 0건이다. 이 숫자는 테스트 항목과 결과가 하나씩 맞을 때만 의미가 있다.

부하를 넣은 뒤 메일이 나가기까지 두 번 재었고, 둘 다 3분 안에 끝났다. 기록된 시간은 105초와 28초다. 같은 경로를 두 번 잰 것이지, 항상 그 시간 안에 끝난다는 보장은 아니다.

과거 사례 검색 94%는 “검색 결과가 그럴듯하다”는 뜻이 아니다. 평가 데이터에서 정답 사례가 상위 5개 안에 들어온 비율이다. 평가 건수와 정답의 기준이 같이 있어야 읽을 수 있다.

## 🦮 5. MCP까지, A2A는 이후에

지금 되는 일은 조회, 분석, 근거 연결, 미리보기, 메일이다. 서버를 고치거나 설정을 바꾸는 실행은 없다.

다음에 두려는 구조는 전문 에이전트 여러 개가 일을 나누는 방식이다. 오케스트레이터가 장애 대응을 나누고, Zabbix·AWS·지식 검색·티켓 담당 에이전트에 맡긴다. 각 에이전트는 자기에게 허용된 MCP만 쓰고, 결과는 근거와 함께 돌려준다. 마지막 정리는 오케스트레이터가 한다. 실행을 넣는다면 규칙 심사와 사람 승인을 따로 둔다.

서비스를 더할 때마다 시스템을 새로 만들지 않는다. 공통 엔진은 두고, 에이전트와 MCP, 분야별 규칙만 더한다. GPU 인프라나 제조도 이 방향의 계획이지, 이미 만든 범위는 아니다.

| 구분 | Zabbix | 장애 대응 시스템 |
|---|---|---|
| 하는 일 | 상태 수집과 장애 감지 | 감지된 장애의 원인 후보, 근거, 조치 미리보기 |
| 실행 | 알람까지 | 조회와 미리보기. 변경 실행 없음 |
| 판단 | 임계치 | LLM은 문장, 위험도는 규칙과 코드 |

MCP와 A2A는 역할이 다르다. MCP는 에이전트가 도구나 데이터에 닿는 통로이고, A2A는 에이전트끼리 일을 넘기는 통신이다. 지금은 MCP까지이고, A2A는 그다음이다.
