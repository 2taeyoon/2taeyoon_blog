## 🦮GEMO 프로젝트 API 설정과 연결

> 이번 프로젝트는 GEMO라는 이름으로 진행하는 간단한 웹게임 사이트입니다. 첫 단계로 워들 게임을 구현했으며, 이를 위해 사용된 API 설정과 관련된 부분을 정리해 보려고 합니다.

---

### 🦄 Repo 개요·목표
- 프론트: gemo-frontend — Next.js(App Router) + **NextAuth(구글 OAuth)** + **MongoDB** 게임용 유저 상태/통계 API를 **Route Handlers**로 직접 제공합니다.
- 백엔드: gemo-backend — **Spring Boot** 장기적으로 중앙 API/집계/어드민 처리 역할을 합니다.
- 목표: 로그인 → 세션 → 유저 초기화 → 출석 → 승/패 → 연승 → 레벨/XP 흐름을 일관된 규칙으로 유지하고 민감 API는 보호합니다.

---

## 🦮 인증·세션: NextAuth + Google OAuth + JWT

### 🦄 핵심 결정
- **세션 전략: JWT**: 서버 상태를 안 들고 가서 가볍고 API 라우트 어디서든 `getServerSession`으로 식별 끝
**MongoDBAdapter 미사용**. 이유:
  **스키마 변동 잦음**: 게임 통계 필드 계속 늘어날 수 있음.  
  **마이그레이션**: insert/update를 코드로 직접 컨트롤해야 디버깅·마이그레이션이 편함
# 🦄 NextAuth 설정 요지
rc/app/api/auth/[...nextauth]/route.ts`
```typescript
import NextAuth from 'next-auth'
import GoogleProvider from 'next-auth/providers/google'
import clientPromise from '@/lib/mongodb'

const handler = NextAuth({
  providers: [
    GoogleProvider({
      clientId: process.env.GOOGLE_CLIENT_ID || '',
      clientSecret: process.env.GOOGLE_CLIENT_SECRET || '',
    }),
  ],
  secret: process.env.NEXTAUTH_SECRET,
  session: { strategy: 'jwt' },
  pages: { signIn: '/login' },
  callbacks: {
    async jwt({ token, user }) {
      // 최초 로그인 시점에만 user 존재 → 그때 token.userId 설정
      if (user) token.userId = user.id
      return token
    },
    async session({ session, token }) {
      // 서버/클라 모두에서 session.user.id로 접근할 수 있게 동기화
      if (token?.userId && session.user) (session.user as any).id = token.userId
      return session
    },
    async signIn({ user }) {
      // 최초 로그인 시 유저 문서 커스텀 초기화
      const client = await clientPromise
      const db = client.db('gemo')
      const users = db.collection('users')

      const existing = await users.findOne({ email: user.email })
      if (existing) { user.id = existing._id.toString(); return true }

      const newUser = {
        name: user.name,
        email: user.email,
        image: user.image,
        emailVerified: null,
        createdAt: new Date(),
        updatedAt: new Date(),
        gameData: {
          level: 1,
          currentXp: 0,
          totalXp: 0,
          totalScore: 0,
          kodleGameWins: 0,
          kodleGameDefeat: 0,
          kodleSuccessiveVictory: 0,
          kodleMaximumSuccessiveVictory: 0,
          achievements: [],
          lastPlayed: null,
          lastAttendance: null,
          consecutiveAttendance: 0,
        },
        thema: 'light',
        notifications: true,
      }
      const res = await users.insertOne(newUser)
      user.id = res.insertedId.toString()
      return true
    },
  },
})

export { handler as GET, handler as POST }
```
- 이 코드는 **구글 로그인 연결**, **JWT 세션 운용**, **최초 로그인 시 유저 초기화**까지 담당합니다.
선택 이유: 유저 초기 상태부터 게임 통계 구조까지 한 번에 잡을 수 있습니다.

## 🦮 /api/user 네임스페이스 설계

### 🦄 공통 규칙
- 인증 필수 `getServerSession`
- `ObjectId.isValid` 체크로 잘못된 ID 요청 방어.
- 단순 카운팅은 `$inc`, 복합 계산은 코드에서 계산 후 **정확한 `$set`**.
- 응답 스키마 통일: `{ success, data?, error?, code? }`.

### 🦄 프로필
**GET** `/api/user/profile` — 로그인 사용자의 전체 프로필 반환
**PUT** `/api/user/profile` — 부분 업데이트 `updatedAt`는 서버에서 갱신

```typescript
// GET
const doc = await users.findOne({ _id: new ObjectId(userId) })
if (!doc) return NextResponse.json({ error: '프로필 없음' }, { status: 404 })
return NextResponse.json({ success: true, data: doc })

// PUT
const body = await req.json()
await users.updateOne(
  { _id: new ObjectId(userId) },
  { $set: { ...body, updatedAt: new Date() } },
)
return NextResponse.json({ success: true })
```
: 전체 덮어쓰기보다 안전하고 변경 이력 추적이 쉬움

### 🦄 출석(Attendance)
**POST** `/api/user/attendance` — 오늘 출석 처리. `KST 기준`으로 중복 방지.  
**GET** `/api/user/attendance` — 오늘 출석 여부/연속일수/최근 날짜 반환.

`오늘 날짜 문자열(KST, YYYY-MM-DD)`
```typescript
const today = new Date()
  .toLocaleDateString('ko-KR', { timeZone: 'Asia/Seoul' })
  .replace(/\. /g, '-').replace('.', '').replace(/\s/g, '')

```
#### 로직 개요
* lastAttendance === today → 400 (이미 출석)
* 어제와 연속이면 consecutiveAttendance + 1, 아니면 1로 초기화
* 출석 보상 XP → totalXp 반영 → level/currentXp 재계산
* lastAttendance = today 저장

이유: 서비스 기준 시간을 KST로 고정해서 “오늘” 정의를 일관되게 유지합니다.

### 🦄 승/패·연승(KODLE)
**POST** `/api/user/kodle-game-win` — 승리 처리: `wins++`, `successive++`, `maxSuccessive` 갱신, **승리 보상 XP 지급**
**GET** `/api/user/kodle-game-win` — 승리/연승/최다연승 조회(구 필드명 하위호환 포함 가능)
**GET** `/api/user/kodle-game-defeat` — 패배/연승 현황 조회
**POST** `/api/user/reset-win-streak` — 연승 초기화, `defeat++`

#### 승리 처리 개요
* 현재 wins/successive/max 값 읽기
* wins += 1; successive += 1; max = max(max, successive)
* 승리 보상 XP 지급 → totalXp 업데이트 → level/currentXp 재계산
* $set 저장(필요 필드만 정확히)

이유: 통계·레벨이 얽혀 있어 **원자성과 일관성**을 보장해야 함.

## 🦮 레벨·XP 계산 규칙

### 🦄 보조 함수(예시)
```typescript
function getRequiredXpForLevel(level: number) {
  return level < 10 ? 100 : level < 20 ? 150 : 200
}
function calculateLevelFromTotalXp(totalXp: number) {
  let level = 1, remaining = totalXp
  while (remaining >= getRequiredXpForLevel(level)) {
    remaining -= getRequiredXpForLevel(level)
    level++
  }
  return { level, currentXp: remaining }
}
```
이유: `totalXp` 기준으로 역산하면 레벨 테이블을 바꿔도 대응이 쉽습니다.

## 🦮 권한(RBAC): superAdmin 게이트

### 🦄 토큰·세션 동기화
```typescript
// jwt 콜백
if (user) {
  token.userId = user.id
  token.superAdmin = (user as any).superAdmin ?? false
}
// session 콜백
if (session.user) {
  (session.user as any).id = token.userId
  ;(session.user as any).superAdmin = token.superAdmin
}
```
### 🦄 라우트 보호 패턴
```typescript
const s = await getServerSession(authOptions)
if (!s?.user) return NextResponse.json({ error: '로그인 필요' }, { status: 401 })
if (!(s.user as any).superAdmin) {
  // 민감 리소스 은닉
  return NextResponse.json({ error: 'Not Found' }, { status: 404 })
  // 또는 App Router not-found로 rewrite
}
```
이유: 민감 API는 **존재 자체를 숨기는 게** 더 안전한 경우가 많아보였다.

## 🦮 프론트 UI 포인트

### 🦄 로그인 페이지
```tsx
// src/app/auth/Auth.tsx
"use client"
import { signIn, getProviders } from 'next-auth/react'
import { useEffect, useState } from 'react'

export default function AuthPage() {
  const [providers, setProviders] = useState<any>(null)
  const [loading, setLoading] = useState(false)

  useEffect(() => { getProviders().then(setProviders) }, [])

  return (
    <main>
      <h1>로그인</h1>
      {providers && Object.values(providers).map((p: any) => (
        <button
          key={p.id}
          disabled={loading}
          onClick={async () => { setLoading(true); await signIn(p.id, { callbackUrl: '/' }); setLoading(false) }}
        >
          {loading ? '진행 중...' : `${p.name}로 시작하기`}
        </button>
      ))}
    </main>
  )
}
```
이유: 프로바이더 목록을 런타임에 받아 버튼 자동화 → 설정 변경 시 UI 수정 최소화

### 🦄 보호된 화면에서 세션 사용
```tsx
import { useSession } from 'next-auth/react'

const { data: session, status } = useSession()
if (status === 'loading') return <Spinner />
if (!session?.user) return <LoginRequired />

return <Dashboard userId={(session.user as any).id} />
```
이유: 클라에서도 접근 제어를 이중화합니다(서버 가드 + 클라 가드)

## 🦮 에러·운영·성능

### 🦄 에러 포맷
- 통일: `{ success: false, error: 'MESSAGE', code: 'E_SOMETHING', details?: any }`
- 401/403/404/409/422/429/500 구분 명확히, 클라에서 분기 처리 쉬워짐.

### 🦄 인덱스
- `users.email`, `users._id` 기본.
- 조회 많은 `gameData.*` 필드(예: 승/패/연승 대시보드) 필요 시 보조 인덱스

### 🦄 중복 호출
- 출석/승리 API는 **같은 입력 반복 호출**을 방지(버튼 비활성, 서버측 재진입 방지)
- 자정 전후 경계에서 출석 두 번 찍히는 케이스 방어

### 🦄 로그
- userId, 액션, 변경량(+XP, wins→successive 등) 기록. PII 주의.


## 🦮 마무리
정리하면, GEMO 프로젝트의 API 설계는 로그인 → 세션 관리 → 유저 데이터 초기화 → 출석/승패/레벨 업 처리까지 흐름을 하나의 규칙으로 일관되게 관리하는 데 초점을 맞췄습니다.

NextAuth와 JWT를 활용해 인증을 가볍게 처리하면서도, MongoDB에 직접 접근해 커스텀 스키마를 유연하게 운영할 수 있게 구성했고, 각 API는 getServerSession 기반 가드를 통해 보안성을 확보했습니다.

이 구조는 단순한 워들 게임 이상의 확장을 고려한 설계이자, 앞으로 다양한 게임 모듈과 통계 집계 기능을 붙이더라도 안정적으로 동작할 수 있는 기반이 될 것입니다. ㅎㅎ 🤤🤤
