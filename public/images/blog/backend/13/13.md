## 🦮 행사 일정 UX: 등록형 행사는 직링크, 일반 일정은 팝업

> 이 글은 <strong>레거시 PHP + 서버 렌더링</strong> 환경에서 흔한 패턴을 정리한 것입니다.  

어떤 사이트는 관리자에 <strong>일반 행사 캘린더</strong>와 <strong>별도로 관리되는 등록·접수형 행사(컨퍼런스 등)</strong>가 공존합니다.  
사용자용 <strong>통합 일정 화면</strong>에서는 두 종류 데이터를 한 목록에 합쳐 보여 주는데, 예전에는 <strong>모든 행이 동일하게 "클릭 → 레이어 팝업"</strong> 이었습니다.

요구사항은 단순합니다. <strong>등록형 행사</strong>는 팝업 대신 <strong>상세 페이지(또는 설정된 외부 URL)로 바로 이동</strong>하고, <strong>일반 일정</strong>만 기존 팝업 UX를 유지하는 것.

## 🦮 판별 조건 (예시 필드명)

목록 루프에서 아래를 만족하면 "등록 모듈과 연동된 행"으로 본다고 가정합니다.

```text
$row['link_program'] === '1' && $row['program_id'] !== ''
```

- 실무에서는 DB 조인·플래그 컬럼·소스 테이블 이름 등으로 구분할 수 있습니다.
- 예: 목록 쿼리에서 `programs` 테이블 행을 합칠 때 위 필드를 채웁니다.
- 일반 일정만 있는 행은 플래그가 없음 → 팝업 분기.

UNION·`tbl_name` 컬럼으로 출처를 넘기는 경우에는 <strong>`$row['tbl_name'] === 'programs'`</strong> 같은 조건으로 같은 의미의 분기를 둘 수 있습니다.

<img src="/images/blog/backend/13/images1.webp"/>

### 🦄 PHP 루프에서의 분기 (개념 예시)

```php
foreach ($list as $row) {
    $isProgramRow = ($row['link_program'] === '1' && $row['program_id'] !== '')
        || ($row['tbl_name'] ?? '') === 'programs';

    if ($isProgramRow) {
        // 직링크용 href·target 계산 후 <a>만 출력
    } else {
        // 기존 js-popup-row + 숨김 팝업 마크업 출력
    }
}
```

핵심은 <strong>"이 행이 등록 모듈에서 온 데이터인가?"</strong>를 뷰 진입 시점에 한 번만 판별해 두는 것입니다.

## 🦮 상세 URL 규칙 (팝업 하단 버튼과 동일하게)

직링크의 `href`는 <strong>기존 팝업 안 "상세보기" 버튼</strong>과 같은 규칙을 복제하는 것이 안전합니다. (정책 이중 정의 방지)

<img src="/images/blog/backend/13/images2.webp"/>

1. <strong>내부 상세 모드</strong> (예: `link_mode == 2`)  
   → `?module=registration&action=detail&event_id={$row['id']}` 처럼 내부 라우트

2. 그 외 + 외부 URL 필드가 비어 있지 않음  
   → 그 URL로 이동, `Host` 비교로 `target` 은 `_self` / `_blank` 선택 (기존 로직 유지)

3. 폴백  
   → 내부 상세 URL + 현재 행 `id`

```php
// 개념 예시: 팝업 푸터 버튼과 동일한 href 빌더
function buildProgramDetailHref(array $row): array {
    if (($row['link_mode'] ?? '') == '2') {
        $href = '?module=registration&action=detail&event_id=' . urlencode($row['id']);
        return ['href' => $href, 'target' => '_self'];
    }

    if (!empty($row['external_url'])) {
        $target = (parse_url($row['external_url'], PHP_URL_HOST) === $_SERVER['HTTP_HOST'])
            ? '_self' : '_blank';
        return ['href' => $row['external_url'], 'target' => $target];
    }

    $href = '?module=registration&action=detail&event_id=' . urlencode($row['id']);
    return ['href' => $href, 'target' => '_self'];
}
```

속성 출력 시 `htmlspecialchars(..., ENT_QUOTES, 'UTF-8')` 로 이스케이프합니다.

## 🦮 수정한 뷰 계층 (역할만, 실경로 비공개)

실제 레포 구조 대신 <strong>역할 단위</strong>로만 적습니다.

<img src="/images/blog/backend/13/images3.webp"/>

### 🦄 1. 연간·다중 월 + 우측 리스트 템플릿

- 월별 `foreach` 안에서 `$isProgramRow`, `$detailHref`, `$detailTarget` 계산.

등록 연동 행

`<li class="list-item--program">` + 자식은 `<a class="program-direct-link" href="..." target="...">` 만.
팝업용 래퍼·숨김 영역(<strong>플레이스홀더 노드 + `.pa_contents` 류</strong>) <strong>출력 안 함</strong> → 팝업용 JS가 걸리지 않음.


일반 일정

기존 `<li class="js-popup-row" data-detail="...">` + 숨은 팝업 마크업 유지.

### 🦄 2. 목록 탭 템플릿

- 원래 등록형 분기는 `div.js-popup-row` + 설정에 따라 거대한 인라인 팝업 HTML.
- <strong>등록형</strong>: `div`·팝업 블록 제거 → `<a class="program-row-link">` 로 한 덩어리 링크.
- <strong>일반</strong>: 기존 `popDetail` / `goDetailPage` 클래스 토글 유지.

### 🦄 3. 표(게시) 형 목록

- `tbl_name === 'programs'`(가명) 이면 제목 셀만 `<a>` 직링크.
- 그 외는 기존 팝업 마크업.  
- 팝업 하단 버튼에서 등록형 전용 분기는 제거(이미 제목이 링크이므로).

### 🦄 4. 12칸 월별 보드형

- 동일하게 출처/플래그로 등록형이면 카드 전체를 `<a>` 로 감싼다.
- `yoil` 계산 등 공통 전처리는 분기 위로 올려 중복 제거.

### 🦄 5. 이번에 손대지 않은 것

- <strong>날짜 셀 하나에 여러 행이 들어가는 달력 팝업</strong>: 하루 단위 묶음이라 행별 직링크는 구조 변경이 필요해 별도 작업으로 둡니다.
- <strong>팝업 초기화 JS</strong>: `.js-popup-row` 델리게이션은 그대로. 등록형은 <strong>해당 클래스를 아예 출력하지 않음</strong>으로 분기.

## 🦮 왜 뷰(템플릿)만 나눴는가

<img src="/images/blog/backend/13/images4.webp"/>

- 팝업은 <strong>특정 클래스 + 숨겨진 HTML을 복제</strong>하는 스크립트에 의존하는 경우가 많습니다.
- 등록형 행에서 그 DOM을 빼면 <strong>JS 수정 없이</strong> 클릭 동작이 달라집니다.
- URL 규칙은 이미 서버에서 팝업 푸터에 있었으므로, <strong>같은 조건을 링크 `href` 계산에만 재사용</strong>합니다.

### 🦄 이 접근의 장점

- <strong>레거시 JS를 건드리지 않아</strong> 회귀 위험이 적습니다.
- <strong>URL 정책이 한곳</strong>에만 정의되어 운영·QA가 단순해집니다.
- 뷰 템플릿만 나누면 <strong>화면별로 점진 적용</strong>이 가능합니다.

---

## 🦮 확장 시 참고

- 일별 팝업 내부 루프마다 동일 플래그로 `<a>` / 인라인 요약 을 나누면 정책을 맞출 수 있습니다.
- 여러 뷰에 동일한 `href` 빌더가 반복되면 <strong>작은 PHP 함수나 partial</strong> 로 묶는 편이 낫습니다.

| 월별 보드 뷰 | 등록형: 카드 링크 / 나머지: 팝업 |
| CSS | 링크 행 레이아웃 보정 |

정리하면, <strong>"어떤 행은 팝업용 마크업을 출력하지 않는다"</strong>는 한 가지 원칙으로 레거시 팝업 스크립트와 충돌 없이 UX만 갈라 낸 예시입니다.

통합 일정 화면에서 데이터 출처가 다를 때는 <strong>클릭 동작까지 통일할 필요는 없습니다.</strong>  
등록형은 상세로 바로 보내고, 일반 일정은 가벼운 팝업으로 요약을 보여 주는 식으로 역할을 나누면 사용자 경험과 유지보수 모두 깔끔해집니다.
